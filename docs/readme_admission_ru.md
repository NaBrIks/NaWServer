# Квоты клиентов и физический резерв

Контракт03.11.2026. `Admission` — необязательная политика без heap; все обращения
к ней сериализует один владелец. Она не вызывает TCP и не содержит настроек демо.
`AdmissionMiddleware` выполняется после ограниченного HTTP head, до чтения тела
и до WS101/SSE200. TCP хранит только непрозрачное разрешение с временем жизни
запроса/потока; классификацию ключей и IP он не выполняет.

## Идентичность

`AdmissionMiddleware(policy, clock, key_header, resolver, context)` читает
ограниченный заголовок ключа (по умолчанию `X-Client-Key`). Известный защищённый
ключ получает свой профиль. Для остальных вызывается optional resolver.
Без resolver идентичностью служит значение заголовка; отсутствие — общая
анонимная идентичность. Это простой режим, не автоматический подсчёт браузеров.

`ClientIdentity` предоставляет режимы `PeerAddress`, `Page`, `AuthenticatedUser`
и `PeerAndUser`. В режиме Page ключ состоит из IP и метки `X-Page-Id`/`page_id`.
Метка ограничена `NAWSERVER_PAGE_ID_BYTES` (32 по умолчанию); разрешены буквы,
цифры, дефис, подчёркивание. Повторный query-параметр, конфликт query/header,
переполнение и дублирующий заголовок отвергаются. До появления метки bootstrap
запросы используют IP. Метка страницы не является секретом или аутентификацией.

User-режим требует уже проверенного `Principal`: поставьте AuthMiddleware перед
resolver в той же ранней цепочке. Учитывайте, что AuthMiddleware для публичного
маршрута не выполняет обязательную аутентификацию. Браузерные WS/EventSource не
позволяют произвольные заголовки; не помещайте секрет API в URL, page_id несекретен.

Генерация/хранение ключей в NVM, web/console управление ими и автоматическая
разметка frontend здесь не реализованы. Приложение предоставляет неизменяемые
профили, существующие до завершения всех разрешений. Ротация не должна менять
память ключа под активной policy. Квота ключа не подменяет права доступа.

## Защищённые профили

`AdmissionOptions::reserved_profiles` и `reserved_profile_count` задают несколько
ключей с индивидуальными `AdmissionLimits`. `reserved_key/reserved` — короткая
форма для одного ключа; одновременно два способа использовать нельзя.
По умолчанию `NAWSERVER_ADMISSION_MAX_RESERVED_KEYS=5`. Повторные/пустые ключи,
превышение размеров и невозможный бюджет разрешений делают policy невалидной.

`AdmissionLimits` содержит HTTP, WS, SSE и запросы/окно. Один ключ с HTTP=1,
WS=SSE=0 допускает один HTTP одновременно. Четыре таких ключа — четыре защищённых
места. Неиспользованный резерв не раздаётся общим клиентам. При upgrade HTTP
разрешение атомарно преобразуется в WS/SSE; ошибка сохраняет исходное разрешение.
Завершение/Drop освобождает его единожды. При keep-alive следующий запрос вновь
классифицируется; новое содержимое заголовков не наследует предыдущие права.

`stats()` возвращает активные HTTP/WS/SSE, активные защищённые разрешения,
общие занятые идентичности, приёмы и отказы capacity/rate. Это snapshot на владельце
policy, не самостоятельный thread-safe API. Счётчики насыщаются при переполнении.

## Расчёт ёмкости

Пусть N — общие клиенты, H/W/S — их параллельные HTTP/WS/SSE, а Hk/Wk/Sk —
защищённые профили. Минимум логических разрешений:

`P = N × (H + W + S) + sum(Hk + Wk + Sk)`.

Задайте `NAWSERVER_ADMISSION_MAX_ACTIVE >= P (по умолчанию32)`; shared capacity шаблона не меньшеN.
Физические ограничения считаются отдельно:

| Ресурс | Минимальный ориентир |
|---|---|
| HTTP workspaces | `N×H + sum(Hk)`; защищённые `http_memory.reserved_requests >= sum(Hk)` |
| WS sessions | `N×W + sum(Wk)` |
| SSE sessions | `N×S + sum(Sk)` |
| Сокеты | Активные HTTP+WS+SSE + idle keep-alive + ingress/отказ + listener |
| TX | Дескрипторы и payload для одновременно обслуживаемых потоков; отдельный reserve не возникает из policy |
| RAM | Policy + workspaces + WS/SSE + TX + parser/ingress + stack + SDK TCP buffers + запас |

Например2общих клиента с H=2,W=1,S=1 и4защищённых HTTP-ключа дают P=12:
8HTTP мест (4защищённых),2WS,2SSE. Плюс2idle и2ingress иlistener — ориентир17socket.
Это расчёт конфигурации, не гарантия против SYN flood или полного исчерпания RAM.

| Пример payload-бюджета | Байты |
|---|---:|
| 8 HTTP body blocks по1024 | 8192 |
| 8 response blocks по4096 | 32768 |
| 2 WS arenas по16384 | 32768 |
| TX payload по выбранному общему лимиту32КиБ | 32768 |
| Всего только перечисленный payload | 106496 |

Добавьте реальные metadata/header entries, policy `sizeof`, SSE, alignment и
служебные структуры. Начальный минимум и максимум — разные величины; dynamic
blocks освобождаются после использования. `reserved_requests` входят в
`initial_requests`, не добавляются поверх них. Они резервируют HTTP buffers,
но не создают автоматически сокеты, TX slots или отдельный канал Wi-Fi.

## Отключение и ранний отказ

`NAWSERVER_CLIENT_QUOTAS=0` исключает middleware/состояние разрешений из сервера;
`NAWSERVER_AUTH=0` отдельно исключает аутентификацию. Управление physical I/O
включается `NAWSERVER_TCP_MANAGED` (host: `NAWSERVER_HOST_TCP_MANAGED`), независимо
от policy; экземпляр использует `http_memory.enabled`/`keep_alive.enabled`.

Capacity/rate отказ middleware —503/429 с Retry-After. Собственная ранняя policy
может вернуть `Result::Drop`: без ответа, без flush старого TX, закрытие владельцем
I/O. Ранний ответ ограничен `NAWSERVER_HEADER_REPLY_MAX_BYTES` (512 по умолчанию).
До заголовков доступны только глобальные physical limits/timeouts; при их
исчерпании осмысленный HTTP-отказ не гарантирован. Никакой IP-квоты TCP accept нет.
