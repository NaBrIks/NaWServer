# Ключи API, хранение и страницы

Общий модуль `NaWServer::keys` не зависит от ESP-IDF или FS. Приложение предоставляет
Storage (две записи, durable write/read) и Random (заполнение случайными байтами).
Store ограничен NAWSERVER_API_KEYS_MAX (по умолчанию4), label —24байта. Флаг
NAWSERVER_API_KEYS=0 / factory NO_API_KEYS исключает модуль; AUTH и CLIENT_QUOTAS
независимы. Ключ резервирует квоту, а права маршрута задаёт отдельная авторизация.

Платформы: Windows/Linux — FileStorage + SystemRandom; ESP-IDF — IdfStorage
в отдельном NVS namespace + IdfRandom; Pico — demo KeyStorage поверх LittleFS и
Pico SDK random с включённым RP2350 TRNG. Адаптер приложения можно заменить,
например на собственный Flash/EEPROM. Библиотека не монтирует FS и не меняет разметку.
Windows использует BCrypt и ACL владельца/System; Linux getrandom и файлы0600.
Каталог принадлежит приложению. ESP-IDF RNG требует активного RF источника энтропии;
генерацию в демо выполняют после запуска сети. RP сохраняет два файла web.api-keys.*,
сохраняя прежние settings/NVS и остальные файлы.

Store: load/create/rotate/revoke/authenticate/metadata; вызовы сериализует владелец.
Секрет256бит в виде64hex символов выдаётся только созданием/вращением. Metadata
не содержит секрет. Имена не могут содержать управляющие символы. RNG ошибку,
нулевой или повторённый ключ отвергают. Несколько ключей имеют разные постоянные
внутренние identities; после вращения активные разрешения продолжают завершаться
без изменения заимствованных строк. Новые запросы проверяют текущий секрет.

Две записи содержат schema/generation/checksum. Новая версия пишется в неактивную,
читается обратно, затем публикуется в RAM. Ошибка записи/readback закрывает сервис
ключей до load; неуспешная операция секрет не выдаёт. При одной повреждённой записи
load выбирает исправную; при двух повреждённых не сбрасывает настройки в пустую
таблицу. Возврат к предыдущей записи после повреждения может вернуть предыдущую
версию ключей; это восстановление данных, не защита от умышленного rollback Flash.
Шифрование at-rest здесь не добавлено; CRC обнаруживает повреждение, не подмену.

Демонстрационный web: раздел «Доступ», панель ключей. GET /api/v2/keys возвращает
CBOR slots(slot,name,active,revision), maximum_slots; неготовое хранилище отвечает503. POST той же точки:
{action:'create',name}, {action:'rotate',slot}, {action:'revoke',slot}. Нумерация API
с нуля. Create/rotate возвращает {slot,secret}; секрет видно в отдельном окне до
закрытия, без localStorage/sessionStorage и без query-параметров. Операции требуют
существующую административную BasicAuth демо. Origin проверяется при наличии.
TLS в этой работе не добавлен: HTTP/BasicAuth и ключи передаются без шифрования.

USB-консоль: `:keys list`, `:keys create NAME`, `:keys rotate SLOT`,
`:keys revoke SLOT` с переводом строки. Только явная команда создания/вращения
печатает новый секрет. Фоновые логи и list его не содержат. При отзыве новые
запросы старым ключом отклоняются; уже начатые bounded операции не обрываются.

AdmissionMiddleware с authoritative resolver (`resolve_all_keys=true`) сначала
проверяет секрет, затем получает внутренний slot-id. Прямая отправка public slot-id
никогда не даёт резерва. В демо4ключа имеют по1HTTP, без WS/SSE. Пулы физических
HTTP buffers резервируются отдельно. Пределы страниц/HTTP/WS/SSE считаются по
формуле в readme_admission_ru.md. Bootstrap без page-id получает отдельный внутренний профиль HTTP3: HTML/CSS/JS могут загружаться при заполненных квотах страниц. Всего в демо5профилей резерва и7защищённых HTTP buffers,на Pico2общие идентичности H3/W1/S1 (P=17), на C3одна (P=12), при лимите32. Bootstrap не даёт административных прав.

Каждый документ браузера лениво создаёт16случайных байт page-id. Все DeviceClient
документа используют один ID: X-Page-Id для HTTP, page_id для WS/EventSource.
Reload и дублированная вкладка получают новый ID; persistent browser storage не
используется. `pageIdentity:false` отключает механизм в переиспользуемом клиенте.
Метка не является паролем и не доказывает физическую уникальность браузера.

Количество страниц, bootstrap HTTP, начальный и максимальный HTTP pool заданы NAWSERVER_DEMO_SHARED_CLIENTS, NAWSERVER_DEMO_SHARED_HTTP, NAWSERVER_DEMO_BOOTSTRAP_HTTP, NAWSERVER_DEMO_HTTP_RESERVED_REQUESTS, NAWSERVER_DEMO_HTTP_INITIAL_REQUESTS, NAWSERVER_DEMO_HTTP_MAXIMUM_REQUESTS. Это профиль полной демо, не минимальные требования библиотеки. C3 входящее тело ограничено1КиБ; собственные stream-маршруты могут задавать отдельные пределы. Для скромного приложения пересчитайте P и физические места под реально используемые HTTP/WS/SSE.

Проверки03.11.2026: Windows65активных, Linux68, frontend37 тестов PASS;3 прежние STL probes отключены только наMSVC. FileStorage реально проверен наWindows/Linux, включая Linux0600; API_KEYS0 исключает исходники/символы. Ключи наC3/Pico проходят create→перезапуск→authenticate→rotate→старыйнепринимается→revoke. USB-консоли обеих плат проверены созданием, чтением и отзывом; тестовые ключи отозваны. Браузерная проверка включает сохранение геометрии при401/успехе, разные метки reload/tab и отсутствие секретов вbrowserstorage.

В ходе проверки исправлены два обнаруженных дефекта: перенос1536байт CBORworkspace из стекаHTTP в ограниченныйServiceworkspace (кадр1760→256байт, защитаNVS-операций наC3); таймерHTTP теперь учитывает реальную передачу конкретногоTCPсоединения при заполненнойTXочереди. Детерминированный медленный транспорт воспроизводит обрезанныйContent-Length на прежнем варианте и проходит после исправления. Дополнительная таблица TXprogress занимает512байт на64соединения и8байт наHTTPjob.

Финальная аппаратная проверка: C3 — одна страница WS+SSE,10 копий новогоJS233151байт с одинаковымSHA-256,101WSсообщение/48pong,10SSE; Pico — две страницы,10 копийJS236511байт,115WSсообщений/57pong накаждый,11SSE. НетнеожиданныхWSзакрытий/HTTPошибок. Это короткая функциональная приёмка, не долговременный stress. C3две страницы отвергнуты как небезопасный профиль: прежний замер показал минимум1352байтаheap. Текущая реальная web-панель C3 сWS/SSE показывает около29–31КиБ свободнойheap. СчётчикиRPFreeRTOSheap не включают отдельнуюC++/lwIPnewlibheap, их нельзя сравнивать сC3общейheap напрямую.

S3MAIN, разметка Flash, существующие settings и файлы не заменялись. Секретов, приватных снимков, диагностических дампов и прошивок вкоммите нет. Сгенерированный C3assets.hpp обновлён, поскольку этот ресурс уже хранится врепозитории и используется при прошивочной сборке.
