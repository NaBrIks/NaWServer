# 27.10.2026 — REST dial timeout и закрытие WebSocket на C6/S3

Итог: исправление находится в публичном TCP backend; зависимости от демо нет.
Окружение и SDK не обновлялись. Ветка `codex/http-backend-adapters`, основа
`632dafdb3575b7f08e1639efaee956f583bfc59e` + текущие незакоммиченные изменения.

## Причины и изменение

| Эпизод | Доказательство | Что изменено |
|---|---|---|
| REST dial timeout | Новый SYN получает ACK со старым sequence/ack вместо SYN-ACK; повтор через секунду получает тот же ACK. Наблюдалось на C6 и S3; на S3 совпало с ошибкой managed REST | ESP-IDF sockets используют `TCP_NODELAY`; HTTP/WS получают ограниченный grace закрытия 250 мс вместо 50 мс, чтобы peer FIN успевал после полного ответа |
| WS 1009 не доходит за 4 с | USB сообщает successful send Close за 1–2 мс, но на проводе виден только заголовок незавершённого обычного кадра, затем RST | Немедленная отправка малых частей; входной слив увеличен с 4096 до 8192 Б. Отвергнутый masked payload 4097 оставлял 4101 Б после extended length: прежний слив оставлял 5 Б и lwIP сбрасывал соединение с потерей TX-очереди |
| Reload-перегрузка | После изменения всё ещё есть HTTP/WS timeouts при stable boot и recovery 200 | Не объявлена исправленной. Синхронный HTTP/WS owner и крупные assets остаются отдельным ограничением |

Новые публичные параметры: `TcpOptions.close_timeout_ms=250`,
`close_drain_bytes=8192`; ноль отклоняется при старте. Работают на уровне общего
TCP HTTP/WS, настраиваются приложением. Слив не выделяет 8 КиБ: HTTP использует
scratch256 Б, WS повторно использует свой RX. HTTP также ограничен оставшимся
exchange/no-progress deadline. WS читает порциями без повторного входа в callbacks.
Отдельный SHUT_WR не возвращён; native close остаётся у единственного владельца.

Увеличенный grace — верхняя граница, а не дополнительный sleep каждого запроса.
Если клиент ждёт TCP EOF, окно может использоваться целиком: это видно в WS EOF
замерах ниже. TCP_NODELAY увеличивает число малых пакетов; p95 S3 не объявляется
низким только из-за исчезновения timeout.

Ранний повтор того же TCP four-tuple при ещё сохранённом состоянии закрытия,
включая TIME_WAIT, остаётся ограничением lwIP. Исправление уменьшает преждевременный
active close и его накопление; правила TCP/SDK для произвольного повторного SYN
не изменены. Таймауты/повторы клиента не увеличивались и не добавлялись.

## Обычная REST-автоматизация — отдельно от перегрузки

Каждая строка —60 с, один последовательный GET/с на клиента:9 summary +1 INFO
за 10 циклов; без assets/MCP/WS/SSE и команд установки. Клиентские bounds прежние:
dial2 с, HTTP headers2 с, весь запрос 4 с. Источник ПК `192.0.2.3`, без proxy.
После первой серии 1→2→3 выполнены WS/negative/overload, затем вторая серия 3→2→1
без reset. Фоновые пользовательские вкладки и существующие WS/SSE сохранены;
у C6 продолжался существующий цикл LCD. RAM наблюдатель читает summary/tasks
раз в 10 с. `p95` относится к завершённым запросам; штатная отмена на границе
длительности не входит в error counter.

## WebSocket и отказ по пределам

| Плата | Полные Close + TCP EOF | Максимум до Close | Максимум до TCP EOF | Отказы по пределам |
|---|---:|---:|---:|---|
| C6 | 10/10 | 38.2 мс | 295.2 мс | 400 / 431 / 1009 / 503 PASS |
| S3 | 10/10 | 397.9 мс | 649.0 мс | 400 / 431 / 1009 / 503 PASS |

`ws-close` делает 5 закрытий кодом 1000 и 5 отказов 1009 на 10 последовательных
собственных соединениях. Длительность измеряется от записи клиентского кадра;
лимит чтения 4 с сохранён. Close frame и EOF проверяются раздельно. До исправления
1009 повторно не доходил за 4 с на обеих платах; промежуточный NODELAY+8KiB/50ms
дал 10/10 на каждой, но один REST dial timeout C6 сохранился — этот результат
не удалён. Итоговая таблица относится к образу с настраиваемым 250ms grace.

Negative: HTTP body4097/limit4096 →400 (прежний контракт), headers over limit →431,
WS4097/4096 →1009, превышение WS clients4 →503; при одном фоновом WS открылись
три собственных. У бесконечного/существенно большего входного потока слив
ограничен, поэтому получение Close перед принудительным закрытием не обещается.

## Отдельная перегрузка —30 секунд

4 логических клиента:2 WS +2 SSE, HTTP pool3, период 250 мс, непрерывное повторное
чтение JS/CSS + MCP. Это не «четыре обычные REST-автоматизации».

| Плата | HTTP / WS echo / SSE | Errors / timeout | Min sampled internal / largest, Б | Min sampled PSRAM, Б | Recovery |
|---|---:|---:|---:|---:|---|
| C6 | 260 / 97 / 59 | 3 / 3 | 169816 / 116736 | — | health/info200; boot stable |
| S3 | 108 / 40 / 53 | 5 / 5 | 61183 / 19456 | 5341396 | health/info200; boot stable |

Ошибки — HTTP response-header/read и WS read timeout; в этих итоговых overload
не было dial timeout. `exit=0` старого stress runner означает завершённый сбор
и cleanup, а не строгую приёмку при ненулевых errors. WS echo counters учитывают
только успешный обмен; равенство sent/received не доказывает отсутствия потерь.

Минимумы RAM в таблицах — **минимум реально снятых текущих free**, с шагом 10 с;
между отсчётами возможны более глубокие пики. SDK historical min является суммой
минимумов разных регионов: итог S3 `min_free_bytes=8324` **не означает одновременно
свободные 8324 Б**. После всех прогонов S3 internal free 86423 Б,
PSRAM free 5350772 Б; C6 internal free 191708 Б. Минимум остатка стека
HTTP: C6 — 2528 Б, S3 — 1756 Б. Признаков panic/assert/boot change в UART
и идентификаторах нет. Старые eFuse MAC_CUSTOM сообщения S3 к новой ошибке не отнесены.
