## План и состояние

| Этап | Состояние | Проверка готовности |
|---|---|---|
| bounded и yyjson | Дневные проверки завершены | Общий corpus, IDF5/6, C6 runtime, S3 bounded runtime |
| RapidJSON | Host corpus/ASan и IDF5/6 сборки прошли; проверяются на плате | Настоящий SAX reader, фиксированная арена, строгий общий corpus |

Измерения выполняются скриптами. Простые изолированные задачи делегированы
младшим агентам; реализация parser — отдельно. Общая интеграция и аппаратные
операции выполняются одним владельцем процесса, чтобы не прошивать плату во
время её нагрузочного теста. Ночная heartbeat-проверка `nawserver-json` каждые
30 минут продолжает незавершённые этапы; после завершения её нужно остановить.

## Аппаратные границы и продолжение

- C6: COM13, MAC `DEVICE-MAC`, последний IP `192.0.2.1`.
- S3: UART COM11, MAC `DEVICE-MAC`, последний IP `192.0.2.2`.
- IP/порт требуют живого подтверждения. Перед каждой прошивкой — vendor chip/MAC
  и проверка диапазонов; без backup/readback, штатная vendor verify. USB_SEL не менять.
- Источники SDK — существующие local packages 5.5.6 и 6.1.0. Не устанавливать зависимости.
- Секреты и сырые логи/бинарники остаются ignored в `local/night26` и прежних `local`.
- Тесты не меняют сеть ПК, настройки AP и пользовательские вкладки. Не занимать 443.
- Сначала короткий smoke, затем этапы по 10–30 минут и длительный soak. Сравнивать
  одинаковые backend/JSON/clock/compiler/frontend. При panic/boot change сохранить
  UART, остановить нагрузку, установить причину; не считать таймаут доказательством Wi-Fi сбоя.
- После ночи восстановить стабильные обычные демо, остановить тесты/эксперименты.

Активные задания, их PID и результаты фиксируются в `local/night26`. Перед
продолжением проверять фактические процессы и сообщения агентов, не запускать
дубликаты. C6 и S3 можно нагружать параллельно, но перепрошивка каждой платы
только после остановки её клиентов и освобождения serial port.

## Результаты

Новые завершённые измерения приведены ниже и в
[автоматически собираемой матрице](readme_json_matrix_ru.md). Дневной результат
не переносится автоматически на новые библиотеки, изменённый Wi-Fi или длительную нагрузку.

### Уточнение владельца: слабый сигнал и reset через 20 секунд

Владелец подтвердил, что плата находится в закутке и Wi-Fi туда доходит плохо;
reset с нескольких попыток помогает. Новое прямое правило: если за 20 секунд
нет подключения, выполнить reset. Для идентифицированной S3/COM11 это реализовано
как 20 секунд **до получения IP**, а не только ассоциации. Повторные disconnect
не продлевают окно; GOT_IP отменяет таймер. При последующей потере IP/связи
начинается новое окно. Используется программный `esp_restart`, NVS не стирается,
параметры безопасности AP/ПК не меняются. Правило принадлежит S3-демо, не общей
HTTP/JSON-библиотеке. Дополнительные диагностические scans из временной проверки
удалены из конечного профиля, чтобы не расходовать это окно.

Исходная консоль: три старта с NO_AP_FOUND201. Однократный directed hidden-SSID
scan вернул0 записей. Затем в пассивной консоли наблюдался POWERON и ассоциация
на channel6, WPA3-SAE, RSSI−72 dBm; до IP не дошло, далее beacon timeout.
Причина POWERON по одному этому логу не установлена. Это не заявляется
устранённым сетевым отказом и не считается падением MCP.

Все три reader прошли общий CTest4/4 после добавления четырёх числовых регрессий
(164 основных +33 demo +29 настройки для каждого reader). RapidJSON прошёл
ASan-корпус50000 мутаций с тем же результатом, что bounded:9898 принятых,
digest5714745342163340789. Требуемая raw-number поправка сохранена отдельно.
Дополнительная x86 Debug benchmark-попытка MSVC остановилась на warning C4324
в alignas Arena yyjson при /WX; x64 основной контрактный профиль прошёл. Эти
разные toolchain-профили не объединяются в blanket PASS.

не считается отдельно проверенной на этой новой прошивке.

Все три reader дали одинаковый результат ASan-корпуса50000 мутаций:
9898 принятых документов, digest5714745342163340789, различий acceptance-трасс0.

runtime-приёмка каждой комбинации.

### Нагрузочные этапы и критерии

Go harness `tools/load` проверяет настоящие JS/CSS (gzip с bounded decode),
MCP list/echo/invalid, точные бинарные CBOR WS echo вместе с unsolicited summary,
SSE progress и recovery после закрытия всех своих сокетов. Первая отладка harness
выявила его собственные ошибки: неверную длину WS key, отсутствие CBOR floats,
учёт штатной отмены как network error. Эти неудачные smoke-логи сохранены;
они не объявляются багами firmware. Регрессии проверяются через net.Pipe и corpus.

После этих исправлений короткий4-client прогон показал реальные timeouts:
C6 —2 WS read timeout, S3 —17 HTTP/WS timeout за20 секунд; boot ID не менялся,
health/info recovery200, повреждений payload не было. Условия: 2 WS +2 SSE +
пул максимум3 HTTP sockets, cadence250 мс/логический клиент, HTTP header deadline2 с,
WS echo deadline3 с; параллельно могли оставаться пользовательские вкладки.
Строгие deadlines в отчёте не ослабляются ради PASS; долгие этапы сравнивают
очереди/задержки/память разных reader и HTTP backends. Причина этих timeouts
пока не локализована одной этой проверкой.

План автоматического runner `local/night26/run-matrix.ps1`: отдельно на каждой
плате TCP RapidJSON/yyjson/bounded, затем native HTTPD RapidJSON/yyjson/bounded.
Каждый вариант проходит fresh chip/MAC + диапазоны + обычную vendor verify,
проверку ELF, короткий MCP probe, затем2 клиента120 с и, при чистом нормальном
этапе,4 клиента600 с (native300 с). В конце — обычная TCP+bounded демо,
чистый normal gate и4-hour4-client soak. При UART panic или изменении boot ID
нагрузка прекращается, сокеты закрываются, выводится recovery; ошибки сохраняются.
Если firmware недоступна180 с, этап отмечается connectivity_unavailable.

Параллельно снимаются UART и минутные heap/stack snapshots; helper-процессы
завершаются sentinel-файлами. Статусы/PID: `local/night26/{c6,s3}-state.json`,
история фаз: `{c6,s3}-history.jsonl`; сырые результаты ignored. Перед любым
продолжением проверить PID и не запускать второй runner на ту же плату.
Утренний отчёт генерируется `node tools/json_bench/report.mjs`. После обоих
runner нужно проверить ошибки/восстановление/активные процессы, заново извлечь
memory maps при необходимости, обновить таблицу и остановить heartbeat.

После исходной reload-матрицы отдельно поставлен **cached UI soak**: новый
`mixed-load-steady.exe -asset-mode cached` один раз заранее читает JS/CSS,
затем в asset-позициях выполняет маленькие summary-запросы с той же cadence.
MCP/WS/SSE и строгие2/3-секундные deadlines сохраняются. Это отдельный
профиль нагрузки, исходные reload failures остаются в истории. У cache-профиля
есть `asset_mode` и `asset_prefetch_ms` в каждом JSONL. Предварительная загрузка
выполняется до открытия worker streams и входит в recorded prefetch time.
Она не выдаётся за проверку четырёх одновременных cold page loads.

Для каждого board отдельный `start-steady-after.ps1` ждёт завершения именно
предыдущего runner; затем запускает `run-matrix.ps1 -SteadyOnly`, восстанавливает
TCP+bounded, проверяет ELF/MCP и короткий cached gate, после него планирует
четырёхчасовой4-client cached soak. Одновременно две нагрузки на одной плате
не запускаются; runner дополнительно удерживает exclusive file lock. Состояние
очереди в `local/night26/steady-queue.json`, PID нового runner после запуска
в `{c6,s3}-steady-runner.json`, актуальная фаза по-прежнему в board-state.json.
Heartbeat нельзя останавливать сразу после первого runner: нужно дождаться
этой очереди и проверить её результаты или явно записанный отказ gate.
