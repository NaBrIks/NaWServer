# Рекомендуемое окружение ESP32-проектов

Это **желаемая воспроизводимая конфигурация по умолчанию**, а не обязательная
структура диска и не запрет на другие пути, версии или изолированные окружения.
Альтернативная конфигурация допустима при явном выборе и отдельной проверке.
Версии в штатных профилях закреплены для повторяемости; это не требование
переустанавливать уже работающую систему или автоматически удалять другие SDK.

## Каталоги без привязки к имени пользователя

`<sources-root>` — любое выбранное место для исходников. Репозитории желательно
размещать рядом: примеры используют соседний компонент NaWServer.
`<pio-core>` по умолчанию — `~/.platformio`; в Windows это
`%USERPROFILE%\.platformio`, в PowerShell — `Join-Path $env:USERPROFILE '.platformio'`.
`<pio-packages>` по умолчанию — `<pio-core>/packages`.

```text
<sources-root>/
  NaWServer/
  NaCBORUIforLVGL/
  NaBTools/

<pio-core>/
  penv/                         PlatformIO CLI и его Python
    Scripts/pio.exe             Windows
    .espidf-5.5.6/              Python-зависимости IDF 5.5.6
    .espidf-6.1.0/              Python-зависимости IDF 6.1, если используется
  platforms/                   Платформы, управляемые PlatformIO
  packages/                    Общий набор SDK и инструментов
    framework-espidf-v5.5.6/    Исходники SDK + подмодули + package.json
    framework-espidf-v6.1/      Пакет SDK 6.1, если используется
    <toolchain packages>/      Имена/суффиксы каталогов назначает PlatformIO
    <cmake, ninja, tools>/
  .cache/                      Восстанавливаемые кэши загрузок
```

На отдельной машине не нужно повторять чужой абсолютный путь или имя учётной
записи. SDK желательно хранить один раз в общем packages, без копий по проектам;
иная организация допустима, если ссылки в конфигурации указывают на неё явно.
Python-окружение и скомпилированные `.pio`-объекты не являются копиями SDK.

В проектах: `src/`, `include/`, `backends/`, `integrations/` — исходники по
назначению конкретной библиотеки; `examples/` — приложения; `tools/` — команды;
`docs/` — руководства. `.pio/`, `managed_components/` и ignored `local/` содержат
генерируемые зависимости, сборки и локальную проверку. Секреты и частные журналы
не переносятся в публичную документацию и не коммитятся.

Это профиль воспроизведения, не список единственно разрешённых версий.
Не следует автоматически уравнивать различающиеся Xtensa-профили: их текущие
точные версии указаны выше и в соответствующих `platformio.ini`.
Другие сочетания можно выбрать явно; успешная сборка одного сочетания сама
по себе не доказывает совместимость другого или работоспособность на устройстве.

## Подготовка другого рабочего места

1. Клонировать нужные репозитории рядом в `<sources-root>`. Для примеров
   NaCBORUIforLVGL и NaBTools research нужен соседний NaWServer.
2. Установить PlatformIO Core и совместимый Python. При необходимости frontend
   установить Node.js и выполнить `npm ci` в указанном проектом каталоге.
3. Подготовить SDK в выбранном `<pio-packages>`:
   - 5.5.6 — официальный тег Espressif `v5.5.6` с рекурсивными подмодулями;
   - 6.1 — пакет `platformio/framework-espidf@4.60100.0`, если нужны IDF 6-профили.
   В базовой схеме каталоги называются `framework-espidf-v5.5.6` и
   `framework-espidf-v6.1`. При переносе пакета сохранять его `package.json`
   и имеющиеся метаданные `.piopm`; не накладывать SDK на существующую версию.
4. Для git-установки 5.5.6 добавить PlatformIO-метаданные `package.json`:

   ```json
   {"name":"framework-espidf","version":"3.50506.0"}
   ```

   Это версия упаковки для PlatformIO; сама SDK остаётся ESP-IDF 5.5.6.
   `symlink://` в штатных профилях ссылается на этот каталог без копирования SDK.
5. Установить указанные в профилях инструментальные пакеты через PlatformIO.
   На новом месте установка зависимостей может потребовать сеть; при проверке
   уже подготовленного места сначала проверить наличие нужных пакетов.
6. Собирать нужный явный профиль командами из руководства своего проекта.
   Проверять `PACKAGES` в выводе и `idf_path` в `project_description.json`.
   Восстанавливать credentials отдельно; сборка не означает разрешение на flash.

## Другие пути и версии

Штатные INI используют стандартные значения PlatformIO, поэтому пути можно
переопределить без имени пользователя и без редактирования общих файлов:

```powershell
$env:PLATFORMIO_CORE_DIR = '<chosen-pio-core>'
$env:PLATFORMIO_PACKAGES_DIR = '<chosen-pio-packages>'
# Далее запускать обычную команду сборки своего проекта.
```

Без `PLATFORMIO_PACKAGES_DIR` используется `packages` выбранного Core.
PowerShell-обёртки с `-CoreDir` принимают другой Core; CLI берётся из него,
если установлен там, иначе из стандартной пользовательской установки.
Прямой `pio` может быть установлен отдельно и найден через PATH.
Скрипты `.ps1` и пути `Scripts/*.exe` в примерах относятся к Windows;
для другой ОС использовать её установку CLI и соответствующие команды.

Если меняются имя каталога SDK, версия SDK или toolchain, явно изменить
`platform_packages` в выбранном профиле либо использовать отдельный конфиг
через `pio run --project-conf <configuration.ini>`. Старые журналы не являются
инструкцией незаметно возвращать прежнюю SDK. Выбранные отклонения и результаты
проверки описывать отдельно; не считать эту базовую схему жёстким ограничением.
