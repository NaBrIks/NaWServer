# Автоматизированная матрица ресурсов и нагрузочных проверок NaWServer

Дата: 2026-10-25.
Статус: идея и пожелание владельца для последующего проектирования.
Новые прогоны или результаты этим документом не объявляются выполненными.

## Цель

Измерять расходы именно нашей библиотеки на CPU, RAM и Flash на доступных
контроллерах. Сравнивать варианты стека, включённых возможностей и SDK при
одинаковых сценариях. Продумать функциональные, нагрузочные и стрессовые наборы
и максимально автоматизировать весь прогон одним `.cmd`/`.bat`.

Полная Showcase полезна как прикладной сценарий, но её UI, телеметрию, LED и
вычислительные эксперименты нельзя выдавать за собственные расходы NaWServer.

## Оси матрицы

| Ось | Предлагаемые варианты |
|---|---|
| Контроллер | Реально доступные платы с указанными SoC, ревизией, RAM/PSRAM, Flash и сетевым подключением |
| Серверный backend | Native IDF HTTPD / общий TCP |
| Возможности | HTTP, WS, SSE, MCP: валидные комбинации флагов, включая минимальный и полный варианты |
| SDK | Точные проверяемые версии веток IDF 5 и 6, с версией toolchain и настройками сборки |
| Прикладная нагрузка | Минимальные одинаковые handlers / отдельно реальная демка |

Комбинации выбирать по реальным зависимостям: WS upgrade, SSE и MCP могут
требовать HTTP-механизмов. Не считать все комбинации битов автоматически
работоспособными. Нереализованные возможности, включая будущий embedded MCP,
отмечать как `not implemented`, несовместимые — как `unsupported`; не считать
их расход нулевым и не записывать как PASS. Выбор JSON-backend для MCP учитывать
отдельной осью, когда появятся реализации.

Сейчас действующий аппаратный стенд и приоритет разработки — разрешённая C3.
Эта идея не утверждает результаты других SoC и не запускает расширенную матрицу
сегодня. Состав доступных плат и порядок дальнейшей аппаратной работы уточнить
перед реализацией стенда.

## Как отделять библиотеку от остальной прошивки

- Подготовить воспроизводимый базовый образ с теми же SDK, сетью и настройками,
  затем образы с NaWServer и разными возможностями; публиковать абсолютные
  значения и разницы относительно явно указанного baseline.
- Учитывать Flash sections, static data/BSS, создание runtime, heap current/min,
  largest free block, стеки задач, очереди, пулы, сетевые буферы и зависимости.
  Различать выделенный объём, фактическую занятость и минимальный запас стека.
- Измерять CPU в покое и под одинаковой полезной нагрузкой. Отдельно учитывать
  наши задачи/обработчики, HTTPD, lwIP/tcpip и Wi-Fi/SDK. Дельта общего CPU сама
  по себе не является точной атрибуцией библиотеке.
- Учитывать влияние сборщика метрик и генератора нагрузки. Передавать подробные
  результаты после измеряемого интервала, где это возможно; не забивать тот же
  канал диагностикой во время замера.
- Фиксировать длительность, прогрев, число повторов, параметры сети, размеры
  сообщений и клиентов. Сравнивать полезный throughput, latency и отказы вместе
  с CPU/памятью; KiB-scale расходы объяснять по источникам.

## Кандидаты наборов тестов

1. **Сборка и состав:** валидность флагов, размер образа, наличие только выбранных
   компонентов; отдельно проверка TCP-only без HTTPD и выключенных возможностей.
2. **Покой и lifecycle:** baseline до/после запуска, подключения/отключения,
   повторные start/stop, освобождение ресурсов и длительный idle.
3. **Обычная работа:** 1, 2 и 4 клиента в пределах лимитов конкретной платы;
   HTTP-ответы/тела/статика, WS text/binary/CBOR, SSE, будущие MCP-запросы.
4. **Смешанный режим:** HTTP + WS + SSE + MCP в доступных сочетаниях, одновременно
   короткие ответы и передача статических ресурсов; сверка целостности данных.
5. **Границы ресурсов:** пределы размеров, очередей, пулов, числа соединений;
   отказ лишним клиентам, прекращение чтения/записи, timeout и восстановление.
6. **Стресс:** bursts, частые переподключения, неполные/некорректные сообщения,
   контролируемое исчерпание ресурсов. Конкретные сценарии и бюджеты подобрать
   по возможностям МК, без бесконтрольного роста нагрузки.
7. **Длительная устойчивость:** стабильная и меняющаяся нагрузка, тренды heap и
   фрагментации, утечки, task/stack margins, reconnect и корректная остановка.

Для каждого набора заранее задать критерии успеха, ограничения времени/ресурсов,
ожидаемые управляемые отказы и условия немедленного прекращения. Тесты должны
проверять корректность ответа и освобождение ресурсов, а не только отсутствие
перезагрузки. Существующий открытый P6 reconnect edge включить в регрессии;
новая идея не заменяет и не закрывает P6/P7.

## Один запуск

Будущий `.cmd`/`.bat` — единая точка входа, которая читает manifest стенда и
последовательно выполняет подготовку, фоновые SDK-сборки, проверку образов,
разрешённую прошивку, захват загрузки, тесты, сбор метрик и сводный отчёт.
Внутренние небольшие утилиты — Go; не добавлять Python glue. Vendor SDK tools
остаются штатными зависимостями сборки/записи.

Предусмотреть короткий smoke, выбранную ячейку, полный прогон и продолжение с
контрольной точки. Все режимы должны сохранять точные flags/config, commit и
dirty-source fingerprint, SDK/toolchain, image hash, параметры теста и причины
`PASS` / `FAIL` / `SKIP` / `unsupported`. На выходе — машиночитаемые данные и
человеческая сравнительная таблица с абсолютными значениями, дельтами и единицами.

Автоматизация не должна обходить аппаратные границы: эксклюзивный доступ к плате,
повторная идентификация разрешённого устройства перед каждой записью, проверка
write/erase ranges, без backup и дополнительных post-flash readback/hash passes.
Секреты, образы и raw serial остаются ignored. При остановке — завершить только
собственные процессы, освободить порт и сохранить точку продолжения.

Windows и изолированный Linux использовать для разработки стенда и генерации
нагрузки. Предельную нагрузку/fuzz/OOM выполнять на изолированном стенде; на
машине ioBroker — только отдельный ограниченный процесс по действующему runbook.
Длительные прогоны выделить в явный режим. Во время разработки стенда достаточно
коротких проверок; полный набор запускать после готовности кода.

Следующая работа — инвентаризация стенда, выбор baseline и валидных ячеек,
пилотные измерения C3, затем исполняемый manifest и единый launcher. При записи
этой идеи сборки, прошивки, тесты и реализация автоматизации не выполнялись.
