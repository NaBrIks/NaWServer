# Опциональные HTTPS и WSS

Статус: идея от 2026-10-18. Владелец отнёс HTTPS на следующий этап.
Текущий backend остаётся HTTP/WS; TLS в NaWServer не реализован и на C3 не измерен.

## Зачем и когда

HTTPS защищает передаваемые данные и учётные данные от чтения в сети. Он полезен
и для локального устройства, но требует памяти, сертификатов и понятного подключения
из браузера телефона. Закончить HTTP core и его ограничения ресурсов можно раньше;
при проектировании transport уже сейчас учитывать возможность TLS.

## Предлагаемая граница

- Отдельная фича сборки, условные исходники и зависимость `esp_https_server`.
  Название вроде `CONFIG_NAWSERVER_HTTPS` пока предложение, такой настройки нет.
- Использовать ESP-IDF `httpd_ssl_start`/`httpd_ssl_stop`, сохранив Route, pipeline,
  policies и прикладные endpoints. Не создавать универсальную transport HAL.
- Один выбранный режим сервера. Параллельные HTTP и HTTPS listeners не обязательны
  и не должны появляться по умолчанию.
- Приложение предоставляет сертификат и закрытый ключ, управляет их хранением,
  сроком действия и обновлением. Конструкторы связывают параметры, I/O выполняет init.
  Ключи и реальные сертификаты устройства не добавлять в репозиторий.
- WSS включать вместе с TLS transport. Авторизация до WS upgrade — отдельная задача;
  само шифрование не реализует пользователей, роли или права на маршруты.

## Что учитывать в transport уже сейчас

ESP HTTPS Server использует HTTPD callbacks отправки/приёма/pending, transport context
и `open_fn` для TLS. Официальная документация запрещает внешнему коду занимать эти
механизмы при работе HTTPS. Реализация deadline и отключения медленного соединения
должна учитывать эту границу; нельзя считать plaintext socket override универсальным.

## Стоимость и подключение

В описании ESP-IDF defaults указано около 40 КБ RAM на TLS socket и уменьшенный
default до четырёх сокетов. Это ориентир SDK, не результат нашего замера C3.
Число сокетов не равно числу людей: одна страница может держать HTTP и WSS соединения.
Handshake также потребляет время и память; бюджеты определить измерениями конкретной
сборки, включая одновременное открытие страницы с телефона.

Самоподписанный сертификат требует решения о доверии браузера и имени устройства.
Перед реализацией выбрать сценарий: тестовый сертификат для стенда, собственный CA
или другой способ выдачи доверенного сертификата. Автоматический ACME, управление
центром сертификации и mTLS не входят в начальную фичу.

## Условия перехода к реализации

1. Завершены простые лимиты HTTP/WS и освобождение ресурсов при закрытии/stop.
2. Выбран сценарий сертификатов для локальной сети и телефона.
3. Добавлен отключаемый TLS backend с тем же контрактом маршрутов и middleware.
4. Сравнены HTTP и HTTPS: flash, свободный/minimum heap, handshake, обычный запрос,
   HTTP+WSS, reconnect и освобождение памяти после отказа/timeout на C3.
5. Выполнены сборки выбранных ESP32 targets; runtime утверждения относятся только
   к реально проверенным платам. Новый код не переключает основной TPMS автоматически.
