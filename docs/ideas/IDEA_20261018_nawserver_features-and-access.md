# Опциональные фичи, пользователи и стоимость конфигурации

Статус: предложение от 2026-10-18 для обсуждения и последующей реализации.
Названия `CONFIG_NAWSERVER_*` ниже проектные: таких настроек в текущем компоненте ещё нет.


Принятое уточнение владельца: новый API поддерживает статическую композицию и не
обеспечивает legacy-совместимость. Статические route descriptors и ограниченное
изменяемое состояние ролей совместимы. Runtime builder/new не должны быть обязательны.
См. [принятое решение](../adr/ADR_20261018_nawserver_static-composition-and-clean-api.md).
Названия конкретных будущих API ниже остаются предложением.
## Выбор при сборке

Нужный механизм — Kconfig → `sdkconfig.h` → `CONFIG_*` и условный список исходников и
зависимостей CMake. Публичная конфигурация должна быть одной для компонента и приложения.
Локальный `#define` в одном `.cpp` не меняет уже собранную библиотеку и опасен для
согласованности объявлений/ABI. См.
[ESP-IDF build system](https://docs.espressif.com/projects/esp-idf/en/v5.4/esp32c3/api-guides/build-system.html).

Управлять размером следует на трёх уровнях:

1. Не выбирать ненужный модуль/компонент и его SDK dependencies.
2. Не компилировать его `.cpp`, скрыть/проверить соответствующий API в заголовках.
3. Использовать устранение неиспользуемых секций при финальной линковке.

В существующем `build.ninja` уже есть `-ffunction-sections`, `-fdata-sections` и
`--gc-sections`, а также `-Og`/`-fno-lto`. Поэтому размер архива не равен стоимости
фичи в firmware. Ссылки из vtables, callbacks, регистраций и общих функций могут
сохранить дополнительные секции. Об изменении уровня оптимизации нужно говорить
отдельно, чтобы не приписать его экономию выключенной фиче. См.
[ESP-IDF binary size](https://docs.espressif.com/projects/esp-idf/en/v5.4/esp32c3/api-guides/performance/size.html).

## Что сейчас мешает чистым профилям

- `CMakeLists.txt` всегда компилирует восемь `.cpp`, включая `handler_ws.cpp` и container.
- `handler_ws.*` прямо использует WS API SDK. Отключить только `HTTPD_WS_SUPPORT`
  недостаточно: эти исходники/объявления тоже должны исключаться или иметь guards.
- Basic находится в общем `web_request.cpp`; там же подключён `esp_tls_crypto.h`.
  Сейчас `esp-tls` объявлен private dependency всего компонента.
- Compile-check и minimal ссылаются на WS; для HTTP-only нужен отдельный маленький
  потребитель, который действительно не использует WS API.
- SSE уже исключён из сборки, но это карантин незавершённого кода, а не рабочая опция.
- JSON/CBOR, Wi-Fi, filesystem и страницы демо не должны становиться обязательными
  зависимостями HTTP ядра.

Разделить Basic implementation, WS transport и convenience container по исходникам;
SDK-specific providers вынести за транспортное ядро. Удаление одной зависимости не
гарантирует удаление криптобиблиотеки из всей прошивки: её может использовать Wi-Fi,
WS или другой компонент. Это проверяется по финальному map.

## Предлагаемые переключатели и ограничения

| Блок | Настройка | Правило |
|---|---|---|
| HTTP/request/response | Основа компонента | Без принудительных Wi-Fi/storage/UI |
| Статические handlers, form parsing, convenience container | Отдельные опции при ощутимой стоимости | Для мелких helpers достаточно linker GC; не плодить сотни макросов |
| WS | `CONFIG_NAWSERVER_WS` | Требует WS capability выбранного SDK/backend |
| SSE | Отдельная будущая опция, по умолчанию off | Включать после lifecycle/backpressure tests |
| Authentication | `CONFIG_NAWSERVER_AUTH` и выбранные schemes | При off не собирать guards реализации, crypto/session/user-store код |
| Permissions / роли | `CONFIG_NAWSERVER_PERMISSIONS` | Требует auth; простой вход без ролей возможен отдельным профилем |
| Backend пользователей | Kconfig `choice`: static / NVS / FS / custom | Один backend для простого профиля; несколько — только при реальной потребности |
| Управление пользователями/ролями | Отдельная опция | Static read-only store не объявляет CRUD; dynamic roles требуют writable policy store |
| Diagnostics/demo | Отдельные модули/examples | Страницы, генераторы данных и тестовые пользователи не входят в ядро |
| TLS / HTTPS | Отдельный adapter/capability | Это существенная отдельная стоимость; шифрование хранения не заменяет канал |

Не следует жёстко `select`-ить сложные SDK опции без учёта их зависимостей.
Невозможные комбинации отклонять Kconfig/CMake проверкой, а окончательные capability
и конфигурацию маршрутов — до запуска. Сборка с auth=off не должна молча превращать
объявленный protected route в public.

Дополнительно конфигурируются пределы: число клиентов, body/frame bytes, pending на
клиента, общий byte/job budget, users, roles, sessions, длины имён и timeouts. Это
лимиты ресурсов, а не отдельные новые реализации. Например, 4 клиента × 4 pending ×
4096 байт = 65536 байт одних payload; 4 × 2 × 512 = 4096 байт. Это расчёт для
предлагаемых ограничений, не измерение текущего heap. Нужен общий лимит и учёт jobs
закрытых сессий, а не только число живых клиентов. Добавляются stack, объекты, TCP
buffers, TLS и входящие сообщения.

## Профили сборки и проверки

| Профиль | Нужный набор |
|---|---|
| `http_min` | HTTP, custom route; без auth, WS/SSE и store |
| `telemetry` | Публичные показания; HTTP polling либо выбранный один realtime transport |
| `fixed_access` | Auth, фиксированные verifier records/роли, без writable storage/CRUD |
| `managed_access` | Auth + sessions + permissions, фиксированные роли, пользователи в NVS |
| `dynamic_access` | Дополнительно ограниченное редактирование role→permissions и policy persistence |
| `showcase` | Доступные фичи и UI, честные capability indicators; отдельный example |

Начать с HTTP-only, HTTP+Basic compatibility и HTTP+WS. Затем auth/NVS и realtime
профили. Не обещать тест всех комбинаций независимых bool: хранить небольшой набор
поддерживаемых профилей, проверять запрещённые зависимости и добавлять комбинации по
реальным потребителям. Переключение должно убирать также источники, dependency paths,
runtime allocation и задачи. Проверки отсутствия symbols полезны вместе со сборкой
минимального потребителя; одной проверки размера недостаточно.

## Пользователи и роли на контроллере

Требование публичных показаний и защищённого управления естественно для MCU.
Фиксированные permissions и изменяемые пользователи также разумны. Полностью
редактируемый RBAC полезен, когда владелец действительно создаёт роли без обновления
прошивки; иначе это дополнительный UI, миграции, проверка целостности и тестовая матрица.

| Хранение | Применение | Ограничения |
|---|---|---|
| Static `const` verifier table | Фиксированный состав, лабораторный/специальный профиль | Изменения требуют provisioning/прошивки; нет user CRUD |
| NVS | Небольшой редко меняющийся набор пользователей и назначений | Выделение места, ошибки commit/полного раздела, версия формата и целостность |
| Файл в выбранной FS | Документная конфигурация, import/export, более крупные таблицы | Bounds parser, mount/format ownership, crash-consistent обновление и восстановление |
| Custom / внешний provider | Централизованный доступ или специальная память | Timeout, недоступность, cache и поведение offline задаются явно |

В первой итерации предпочтительны роли в коде и пользователи/назначения в NVS,
backend выбирается при сборке. Pure virtual `IUserStore` либо compile-time выбранный
конкретный тип оба допустимы. Интерфейс не требует собирать все реализации; templates
не гарантируют меньший бинарник. Сравнить два варианта можно после появления реального
API, а не по предположению о стоимости virtual вызова.

Каталог операций/permission bits фиксируется прошивкой. Изменяемая роль задаёт имя и
набор известных прав; она не добавляет новый handler или операцию. Записи пользователей
должны иметь стабильные IDs, enabled/revision и ссылки на существующие роли. Обновление
не должно оставлять устройство без административного восстановления. Число users/roles
строго ограничено. Users cache и sessions живут в RAM; не обновлять flash на каждое
чтение показаний, не сохранять каждый session last-seen.

NVS ориентирован на небольшие key/value, имеет wear levelling и восстановление после
потери питания. Но произвольное обновление нескольких ключей не следует считать
транзакцией user+roles. Нужен версионированный bounded snapshot либо согласованная
схема поколений с проверкой восстановления. Namespace не означает отдельную физическую
память; для отдельного раздела нужна явная partition configuration. См.
[NVS ESP-IDF5.4](https://docs.espressif.com/projects/esp-idf/en/v5.4/esp32c3/api-reference/storage/nvs_flash.html).

Сохранять salt/verifier и версию KDF, не открытые пароли. Выбор backend через define
не требует помещать настоящие пароли в макросы. Static профиль может содержать заранее
подготовленные verifier records в `const` таблице. Время/память KDF надо измерить на C3,
ограничить частоту попыток и число одновременных проверок. Mbed TLS предоставляет
[PBKDF2 API](https://mbed-tls.readthedocs.io/projects/api/en/v3.6.3/api/file/pkcs5_8h/);
конкретный алгоритм/work factor здесь ещё не выбран. Обычный быстрый SHA пароля не
следует выдавать за полноценный password KDF.

Encryption at rest — отдельное свойство provider и конфигурации устройства. NVS
encryption описан у [Espressif](https://docs.espressif.com/projects/esp-idf/en/v5.4/esp32c3/api-reference/storage/nvs_encryption.html).
В ходе этого исследования flash encryption, Secure Boot и eFuses не менялись.

## Исходные размеры, не экономия фич

Ранее собранный `examples/minimal`, target C3, espressif32@6.10.0 / IDF5.4,
GCC14.2+20241119: отчёт PlatformIO — **RAM 29264 байта, Flash 865446 байт**.
Он включает Wi-Fi, SDK, self-tests и прикладной пример. Это данные имеющегося build
log, не свежая профильная сборка и не пиковая динамическая память.

Прямой GNU `size -t` существующего архива библиотеки, прочитанного 2026-10-18:

| Объект до финальной линковки | text+data+bss, байт |
|---|---:|
| `handler_ws.cpp.o` | 8352 |
| `web_request.cpp.o` | 8005 |
| `web_server_container.cpp.o` | 2434 |
| Весь архив, восемь объектов | 36396 |

Это не размеры отключаемых фич в прошивке: общий код, vtables, template instantiations,
SDK symbols и linker GC меняют итог. Нельзя обещать «WS off = минус 8352 байта».
Общая GNU `size` сводка ELF со специальными ESP linker sections также не заменяет
memory-region отчёт IDF/PlatformIO.

Для реальных дельт: одинаковые target/compiler/optimization/sdkconfig основы и UI,
отдельные build dirs, hash исходников, сборка каждого профиля, финальный map и region
sizes. Затем boot heap, minimum free heap, largest free block, task stacks и поведение
при заданном числе клиентов. Нагрузку/прошивку C3 выполнять после согласованного API
и готового демо; исходный TPMS остаётся на своей библиотеке до отдельной команды.


## Какие middleware нужны первыми

| Назначение | Место и форма |
|---|---|
| Body/header/frame bounds и timeout | Базовый transport contract до пользовательского handler; защищает также публичные маршруты |
| Authentication и permissions | Route guards; отдельные отключаемые модули, порядок задан явно |
| Origin / CSRF | Условные guards для браузерных cookie/изменяющих операций; CORS не заменяет эту защиту |
| Ограничение попыток входа | Bounded RAM-состояние и общий лимит вычислений KDF; не только по присланному username |
| Метрики и timing | Наблюдатель завершения запроса с гарантированным cleanup; счётчики в RAM, без записи flash на каждый запрос |
| Заголовки ответа и CORS policy | Явная политика приложения/маршрута; не разрешать все origins автоматически |
| Логи | Ограниченный observer с редактированием Authorization/cookie/tickets; полные bodies по умолчанию не записываются |
| Parse/validation payload | Форматный adapter и прикладной handler; domain validation не становится глобальным HTTP middleware |

Сжатие статики лучше начать с подготовленных ресурсов и корректных headers. Генерировать
gzip на контроллере для каждого ответа стоит только при доказанной пользе. Статистика,
headers и body limits не требуют сложной цепочки next(); transport invariants, guards,
observers и прикладные handlers имеют разное назначение.


Выбранное направление middleware: статический next pipeline с route policies и
плоскими resource handlers. См. [новое решение](../adr/ADR_20261018-2_nawserver_static-next-pipeline.md).
Guard-only engine больше не является предпочтительным направлением; checks остаются
логикой внутри pipeline. Chain<N> не запрещает динамические роли как bounded данные.
