# Формы Chain и политика отстающего получателя

Дата: 2026-10-18. Статус: интерфейсные пожелания владельца и предложение к реализации.
Код нового pipeline/transport в этом документе не объявляется реализованным.


Уточнение владельца: сложное обслуживание медленных клиентов не требуется.
Индивидуальный timeout/overflow приводит к disconnect; лимиты задаются в коде.
Разделы политик ниже — история предложения, не действующее требование ядра.
Актуальное решение: [локальные лимиты](../adr/ADR_20261018-3_nawserver_local-device-limits.md).
Три формы Chain и общий engine остаются актуальными.
## Три формы, один engine

Владелец предпочитает typed Chain и makeChain и хочет сохранить все три формы для
практического выбора. Предлагаемые объявления:

```cpp
Chain<AuthMiddleware, AccessMiddleware> typed{auth, access};
auto privateChain = makeChain(auth, access);
auto loggedChain = makeChain(log, auth, access);
FixedChain<2> counted{middlewareRef(auth), middlewareRef(access)};
```

Chain с типами и Chain с числом параметров нельзя предоставить как один перегруженный
class template с одинаковым именем. Для формы с числом нужно другое имя, например
FixedChain<N>. Имена API пока проектные.

makeChain возвращает тот же typed Chain, который можно записать явно. Typed Chain и
FixedChain хранят фиксированный массив non-owning MiddlewareRef и дают borrowed view
единому engine. Их различия — построение и проверки типов/длины, не отдельная реализация
порядка вызовов, Context, Next, обработки ошибок или ответа.

Зависимости middleware живут дольше сервера, данные запроса находятся в Context.
Фабрика не копирует auth/logger/store и по умолчанию не принимает временные middleware,
которые сразу станут dangling references. Сам Chain также живёт дольше заимствующего
его server/route. Пустая цепочка поддерживается. Allocations per middleware/request
не требуются самим engine. Общие проверки поведения должны выполняться для всех форм.

## Что означает медленный клиент

Получатель/сетевой путь временно не успевает за выбранным темпом и бюджетами сервера.
Причиной бывают плохая связь, перегруженный канал, ограничения принимающей стороны
или прекращение чтения. Медленное получение не обязательно означает медленный CPU.

Наблюдаемые критерии разделяются:

- queued jobs/bytes и возраст старейшего ожидающего сообщения;
- время socket write и отсутствие прогресса записи;
- прикладное подтверждение последнего sequence, если оно нужно протоколу;
- глобальные занятость executor/worker pool и очередь других клиентов.

Одновременный рост возраста у всех клиентов может означать занятый HTTPD handler,
а не множество медленных получателей. Нынешний pending отражает jobs библиотеки,
не весь TCP backlog и не необработанные события JavaScript в браузере.

TCP регулирует поток принимающим окном, в том числе нулевым. Успешная запись и TCP
ACK не являются прикладным подтверждением обработки команды/UI. Если это требуется,
нужен bounded protocol sequence/ACK. См.
[RFC9293](https://www.rfc-editor.org/rfc/rfc9293.html#section-3.8.6).

Условный расчёт: 10 snapshots/s по 100 байт дают 1000 B/s. При устойчивой возможности
передавать 200 B/s сохранение всех snapshots создаёт 800 B/s прироста backlog. Этот
расчёт иллюстрирует политику, а не измеренные показатели C3 или фактические TCP buffers.

## Предлагаемые политики

| Данные | При отставании |
|---|---|
| Полный snapshot показаний | Latest per key/stream: заменить ещё не начатое старое сообщение свежим; bounded число ключей/байт |
| Delta/history события | Не терять молча; bounded очередь, явный Full/gap, затем replay/resync по протоколу приложения |
| Ответы управления | Не coalesce; явное состояние принятия/исполнения/доставки; при невозможности ответа не заявлять доставку |
| Диагностические логи | Опциональный best-effort с лимитом и счётчиком потерь |
| HTTP/FS файл | Ограниченный буфер и concurrency, no-progress timeout и общий transfer deadline |

Заменять можно только ещё не начатое сообщение и только когда семантика данных это
разрешает. Частично отправленный WS frame нужно корректно закончить или закрыть
соединение; нельзя удалить его остаток и начать новый frame в том же TCP stream.

Producer получает Accepted/Replaced/Full/Closed/TooLarge/Error; Accepted обозначает
владение принятой копией/job, не получение или выполнение клиентом. Нужны лимиты на
клиента и общий byte/job budget, включая jobs уже закрытых sessions.

## Начальные параметры для стенда, не принятые универсальные значения

- Live snapshots: один ожидающий snapshot на stream/key, целевая свежесть порядка
  0.5–1 секунды как начальный стендовый профиль; старые неотправленные заменяются.
- Отсутствие прогресса передачи порядка 3–5 секунд — кандидат на закрытие stalled
  соединения, если политика потока не задаёт иначе. Это не разрешение удерживать
  общий HTTPD executor все эти секунды одним блокирующим send.
- Файлы: общий deadline выбирается по назначению/размеру; фиксированный короткий
  timeout не должен ошибочно запрещать полезную передачу большого файла с прогрессом.
- Socket step timeout, очередь и число workers определяются backend и стендовыми
  измерениями; численная гарантия realtime пока не задана и не доказана.

Публичный send_wait_timeout HTTPD задаётся в секундах и ограничивает ожидание send,
но не заменяет общий deadline передачи или freshness policy. См.
[HTTPD config](https://docs.espressif.com/projects/esp-idf/en/v5.4.2/esp32c3/api-reference/protocols/esp_http_server.html#_CPPv414httpd_config_t).

## Исполнение и проверка

Небольшие ресурсы сохраняют простой fast path. Долгие HTTP/FS передачи, если это
нужно для требуемой отзывчивости, используют публичный async-request lifecycle и
ограниченный worker pool. При исчерпании slots/jobs нужен явный Busy/Full, без роста
числа задач. WS sender также обязан иметь bounded сетевой шаг: одна очередь сама
по себе не исключает блокировку HTTPD медленным socket write. Конкретный backend
механизм ещё предстоит реализовать и проверить.

На C3 измерить producer enqueue latency, время в очереди, socket send duration,
получение sequence клиентом, heap/pools и задержку прикладной задачи одновременно
с загрузкой UI. Отдельные сценарии: normal, throttled reader, no-reader, несколько
клиентов, перегрузка publish, заполнение pool и reconnect. Затем уточнить параметры.
Backpressure относится к transport; число форм Chain не создаёт разные transport
политики или отдельные engines.
