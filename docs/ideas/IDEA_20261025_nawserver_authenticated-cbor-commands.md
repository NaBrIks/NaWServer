# Аутентификация CBOR-команд: HMAC и цифровые подписи

Дата: 2026-10-25.
Статус: идея владельца для последующей проработки. Не ADR, не утверждённый
криптографический протокол и не описание реализованной функции.

## Задача

Предусмотреть отдельный режим `AUTHENTICATED` для проверки целостности и
происхождения команд в CBOR-стеке. Рассмотреть работу без TLS там, где достаточно
аутентификации отдельных сообщений и не требуется конфиденциальность.
Имена режима и будущих API пока проектные.

Предложение не отменяет отдельные проверки прав на выполнение операции.
Подлинное сообщение ещё не означает разрешённую команду.

## Два варианта

| Свойство | HMAC-SHA256 | Ed25519 / ECDSA |
|---|---|---|
| Шифрование данных | Нет | Нет |
| Проверка целостности | Да, при корректном протоколе и ключах | Да, при корректном протоколе и ключах |
| Основание доверия к источнику | Знание общего секрета | Подпись закрытым ключом и доверенная привязка открытого ключа к отправителю |
| Проверка без секретного ключа | Нет | Да, открытым ключом |
| Ожидаемые расходы на МК | Кандидат с небольшими расходами; измерить | Ожидаются выше; отдельно измерить выбранные алгоритмы и операции |
| Исходный сценарий | Контроллер и доверенный сервер | Независимые отправители с отдельными ключами и публично проверяемым аудитом |

Предварительное предпочтение: HMAC-SHA256, если достаточно утверждения «команду
сформировал участник, знающий общий секрет». Если один секрет разделяют несколько
участников, HMAC не доказывает, кто именно из них создал сообщение: любой держатель
секрета способен создать такой же MAC. Идентификатор отправителя сам этого не меняет.

Если требуется проверять подпись конкретного контроллера, оператора или сервера
без выдачи проверяющей стороне возможности подписывать команды, рассмотреть
отдельный закрытый ключ каждого отправителя. Привязка ключей к участникам,
хранение ключей, их отзыв и достоверность аудита требуют отдельного проекта.
Ed25519 и ECDSA — самостоятельные кандидаты, а не уже выбранный общий backend.

## Формат и защита от повторов

Исходная идея — использовать стандарт COSE для CBOR-сообщений, в частности
`COSE_Mac0`, и реализовать только необходимый ограниченный поднабор вместо
собственного криптографического контейнера. Отправная ссылка владельца:
[COSE, RFC 9052](https://www.rfc-editor.org/rfc/rfc9052.html).
Применимость, алгоритмы и точный поднабор предстоит отдельно изучить; стандарт
в рамках записи этой идеи не исследовался.

Для будущего контракта проработать:

- Идентификатор отправителя/ключа и его защищённую связь с проверяемым сообщением.
- Защиту от повторов: счётчик, nonce или иной явно выбранный механизм; поведение
  при перезагрузке, потере состояния, смене ключа и отсутствии надёжных часов.
- Привязку команды к получателю, назначению/операции и направлению обмена,
  чтобы корректное сообщение нельзя было применить в другом контексте.
- Какие именно CBOR-байты аутентифицируются, ограничения вложенности и размеров,
  обработку неоднозначных/некорректных структур до исполнения команды.
- Явные ограничения ключей, отправителей, replay-state и временных буферов;
  минимальное копирование и безопасное владение входными данными.
- Разделение общего механизма проверки и прикладного предоставления ключей,
  хранения replay-state, политик доступа и исполнения команд.
- Тесты изменения сообщения/контекста, неверного ключа, повтора, перезагрузки,
  конкурентных команд и исчерпания ограниченных ресурсов.

Режим без TLS не скрывает команды и ответы и не защищает автоматически всё
соединение, HTTP-заголовки или другие сообщения. Его назначение — проверка
аутентифицированных сообщений в явно описанной модели угроз. Где необходимы
конфиденциальность и защита соединения, TLS рассматривается отдельно.

## Дальнейшая работа

Сначала уточнить сценарии и модель доверия, затем выбрать формат/алгоритмы,
подготовить проверяемый контракт и измерить Flash, RAM и CPU на разрешённой C3.
Сравнение ресурсов связано с отдельной
[идеей автоматизированных измерений](IDEA_20261025_nawserver_resource-and-stress-matrix.md).
При записи этой идеи код, зависимости, ключи и конфигурация устройства не менялись.
