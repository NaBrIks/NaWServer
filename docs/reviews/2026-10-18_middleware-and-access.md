# Разбор handler_middleware.h и модели доступа

Снимок исследования от 2026-10-18 независимого `проект до переименования`, до переделки API.
Документ фиксирует наблюдения и варианты; он не объявляет новый код реализованным.

## Как работает сейчас

`src/handler_middleware.h` содержит `MiddlewareHandler : HandlerBase`. Он заимствует
`next_` и перенаправляет методы следующему handler. `AuthMiddlewareHandler` дополнительно
заимствует `Credentials*`, проверяет Basic и либо отвечает 401, либо вызывает next.
Это декоратор обработчика, пригодный для небольшой синхронной HTTP проверки.

`WebServerContainer::add_handler` оборачивает каждый handler одной общей парой
credentials. Пример minimal выбирает прямой `IDFWebServer`: `/private` обёрнут явно,
а `/health` и `/ws` остаются публичными. Смешанный доступ уже возможен вручную.

| Наблюдение в коде | Значение для переделки |
|---|---|
| `authenticate` возвращает true при пустом username или null credentials | Публичность следует задавать явно; ошибочный protected config должен оставаться закрытым |
| Credentials и next — borrowed pointers | Нужны проверка конфигурации, явное время жизни; references исключают null, но не dangling lifetime |
| `handleBody/handleUpload` перенаправляются и повторяют auth | Нынешний IDF dispatcher их не вызывает: это след старого API, не готовая потоковая обработка |
| Body читается до `canHandle` и auth | Новый pre-body guard потребует маршрутизации по method/path/headers до чтения body |
| `canHandle` пользовательский | Нельзя молча перенести все старые predicates до body: некоторые могут читать form args |
| Native WS upgrade раньше callback | HTTP wrapper не становится pre-handshake guard; нынешний startup reject нужен |
| Нет Principal, permissions, store и отзыва | Всё это отдельные контракты, а не ещё одна строка сравнения пароля |
| Ответы и guards сейчас `void`/`bool` | Нужно явно различать продолжение, уже отправленный отказ и внутреннюю ошибку |

## Возможные способы устроить middleware

| Подход | Когда уместен | Ограничение |
|---|---|---|
| Сохранить декораторы | Небольшая цепочка вокруг legacy HTTP handlers | Трудно выразить фазы, public/protected правила и общий контекст запроса |
| Guards/policies маршрута | Auth, permissions, Origin и ограничения перед endpoint | Требуется явное описание маршрута и аккуратная миграция predicates |
| Полный pipeline с `next()` | Много интеграций, необходим общий before/after протокол | Порядок, re-entry, captures и async lifetime становятся отдельной сложной системой |
| Статическая template цепочка | Очень маленький фиксированный набор конфигураций | Инстанцирования могут увеличивать код, API усложняется; размер надо измерять |

Рекомендация для этого проекта: небольшие route guards, отдельные наблюдатели для
метрик/логов и временный адаптер старого декоратора. Не переносить весь ASP.NET pipeline
в контроллер. Это рекомендация, окончательное решение и изменение ABI ещё впереди.

## Границы предлагаемого API

**Route policy** описывает `Public`, `Authenticated` либо требуемое permission.
Политика применяется на сервере для выбранной операции; скрытая UI кнопка не защита.
Public без необязательной identity может вообще не запускать authenticator. Режим
optional identity, если понадобится, должен отдельно определить реакцию на испорченный
token. Ненастроенный provider защищённого маршрута — ошибка конфигурации.

**Authenticator** получает доказательство личности и возвращает небольшой Principal
или явный результат ошибки. Неверные/отсутствующие credentials — 401, недоступный
backend не маскируется под успешный вход. Password KDF нужен при входе, затем обычно
проверяется ограниченная сессия. Он не должен повторяться на каждом WS кадре.

**Authorizer** проверяет операцию: обычно достаточно функции над permission mask,
для resource rules возможен пользовательский callback. Известный пользователь без
права получает 403. Динамический интерфейс не нужен каждой простой функции.

**UserStore** отвечает за чтение/сохранение записей. Чисто виртуальный абстрактный класс
C++ с виртуальным деструктором — возможный аналог C# interface. Его можно внедрять
ссылкой, сохраняя владение в composition root. Один скомпилированный backend не требует
создания всех остальных. Не нужны service locator и неограниченный DI container.

**Контекст** живёт в рамках запроса; передавать в долгую работу надо значения/безопасные
handles, не указатель на stack request. Результат guard должен исключать двойной
ответ и вызов endpoint после отказа. Deferred execution допускается только при реально
реализованном async lifetime, а не добавлением значения enum без поддержки backend.

Предлагаемый порядок: match route → ограничить/проверить headers → authenticate →
authorize → прочитать допустимый body → handler → финальная метрика/cleanup.
При этом ограничения размера/timeout должны действовать и до аутентификации.
Совместимость со старыми body-dependent predicates нужна явно, поэтапно.

Для WS дополнительно нужны pre-upgrade admission и command/subscription guards.
Отзыв/смена прав инвалидирует сессию или заставляет обновить разрешения по revision.
Для SSE auth должен предшествовать старту event-stream; срок и отзыв проверяются и
для уже открытого потока. Storage не следует читать с flash при каждом событии.

## Что не выбрано и не реализовано

Backend защищённого WS, конкретные имена новых C++ API, KDF/work factor, схема сессий,
формат UserRecord и механизм атомарного обновления пока не приняты. Dynamic RBAC
остаётся опциональным расширением. Нагрузочная проверка нужна после реализации и
интеграции демо. См. [профили и хранение](../ideas/IDEA_20261018_nawserver_features-and-access.md)
и [realtime](../readme_realtime_ru.md).
