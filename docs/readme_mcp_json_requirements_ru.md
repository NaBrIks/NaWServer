# Требования к автономному MCP и общему JSON-интерфейсу

Дата: 2026-10-25. Основание — прямые уточнения владельца в текущей работе.
Статус на 26.10.2026: автономный MCP и bounded JSON реализованы опциональным
модулем. Поддерживаемые операции, ограничения и проверенные конфигурации описаны
в [отчёте реализации](readme_mcp_implementation_ru.md). Ниже сохранены требования.

## Автономность и границы

1. MCP-сервер полностью работает в прошивке контроллера. Стандартный MCP-клиент
   подключается непосредственно к контроллеру. Для runtime не нужны Node.js,
   отдельный процесс-посредник, открытая веб-страница или компьютерный сервер.
2. Общая C++-часть над HTTP отвечает за MCP-протокол, реестр инструментов,
   ограниченный разбор запросов, оформление результатов и ошибок. Она не содержит
   бизнес-логику, LVGL, конкретные страницы, GPIO или продуктовые действия.
3. Конкретная программа предоставляет статические описания инструментов,
   схемы аргументов, обработчики и явно переданные прикладные зависимости.
   Не требуются heap-фабрики, изменяемая runtime-регистрация или DI-контейнер.
4. Существующий Node.js MCP-адаптер NaCBORUIforLVGL — источник описаний и семантики
   операций, но не целевая архитектура автономного MCP. Его текущая реализация
   не означает, что MCP уже есть на МК. Удаление адаптера этим документом не выполняется.
5. HTTP/WS/SSE остаются отдельным транспортным слоем NaWServer. MCP использует
   существующие маршруты и middleware, не создаёт универсальную HAL и не меняет
   существующий прикладной CBOR-контракт.

## Включение при сборке

6. Модуль MCP включается и выключается define-флагом. Владелец предложил примеры
   имён: `NAWSERVER_MCP` для модуля и `NAWSERVER_MCP_CJSON` для JSON-backend.
   Регистр этих имён сохраняется. Пример CJSON не является выбором библиотеки.
7. Семантика конфигурации должна быть однозначной: флаги 0/1; отсутствие главного
   флага соответствует выключенному модулю. Обычный compiler `-DNAWSERVER_MCP`
   соответствует значению1. Выбор backend сам по себе не включает MCP.
8. При выключенном MCP NaWServer не подключает его implementation, маршруты,
   реестр, рабочие буферы и JSON-зависимость, нужную только этому модулю.
   Независимые зависимости самого приложения остаются ответственностью приложения.
9. При включённом MCP выбирается один поддерживаемый JSON-backend при сборке.
   Отсутствующий или неоднозначный выбор должен давать понятную ошибку, а не
   неявно подключать большую библиотеку. Default и окончательные имена остальных
   backend-флагов определяются после сравнения кандидатов.
10. Смысл флагов одинаков на Windows, Linux и ESP32. Возможная интеграция с
    Kconfig/CMake не должна менять публичную семантику включения и выбора.

Пример обозначений, не готовая конфигурация реализованного модуля:

```cpp
#define NAWSERVER_MCP 1
#define NAWSERVER_MCP_CJSON 1
```

## Общий JSON-контракт

11. Чтение и запись JSON отделяются интерфейсом от конкретной библиотеки и MCP.
    Публичный контракт не раскрывает типы стороннего DOM/parser и не требует
    привязки к Arduino, ESP-IDF, FreeRTOS или конкретной ОС.
12. Backend выбирается при сборке. На host допустим более тяжёлый вариант,
    но результат чтения и записи в одном ресурсном профиле должен соответствовать
    тому же контракту, что на МК. Различия библиотек нельзя скрывать потерей данных.
13. Обязательны вложенные objects/arrays, boolean/null, UTF-8, корректное
    экранирование и декодирование строк, точные int64/uint64 и double.
    Переполнение не превращается в округлённое число или успешный результат.
14. Raw JSON string view и декодированная строка различаются явно. Строки и ключи
    используют длину, не только завершающий NUL. Unicode escapes, surrogate pairs,
    встроенный NUL и обычный UTF-8 входят в общий набор проверок.
15. Единые правила для malformed input, числовой грамматики, trailing bytes,
    duplicate keys, depth/capacity overflow, NaN/Infinity и ошибок вывода должны
    быть определены до реализации адаптеров и проверяться одним corpus.
    Поддержка root primitives и политика дубликатов также фиксируются явно.
16. Ограниченная реализация не означает нестрогий JSON или произвольный
    JavaScript-подобный синтаксис. Неподдержанный backend-контракт должен быть
    выявлен явно; тихая смена типов, усечение строк или пропуск ошибок запрещены.

## Память, время жизни и вывод

17. Приоритет МК — минимум ненужных копий и выделений. Не навязывать полный DOM,
    копирование всего документа или максимальный буфер на каждое соединение.
18. Разрешены borrowed input и token/value views, пока живы исходные байты и
    workspace. Срок жизни views должен быть явным; следующий parse/reset может
    их инвалидировать. Не обещать одинаковый zero-copy режим у всех backend.
19. Для escaped strings использовать буфер вызывающего либо явно управляемое
    in-place декодирование с разрешением на изменение входа. Не выдавать raw
    escaped text за уже декодированное значение.
20. Аргументы для отложенного исполнения получают собственное ограниченное
    хранилище или типизированную копию. Не удерживать HTTP Request/Response/Next,
    стековые данные или view переиспользуемого parser workspace.
21. Явно ограничиваются размер входа/выхода, глубина, token count, строки,
    контейнеры, workspace и очередь прикладных команд. Размеры в KiB, стек,
    аллокации и существенные копии нужно измерять и объяснять на C3.
22. Writer должен работать с ограниченным буфером или явным sink-контрактом.
    Partial write, capacity overflow и transport error не считаются успешным
    полным результатом; нельзя повторно выводить уже записанный prefix.
    Частичный JSON после ошибки не объявляется готовым ответом.
23. Compile-time или статическое хранение само по себе не означает zero-heap.
    Нужны отдельные данные о зарезервированной и фактически используемой памяти.

## Кандидаты и приоритет проверки

24. Сначала сравнить LwJSON и Frozen; также рассмотреть jsmn, cJSON, yyjson,
    ArduinoJson и собственную C/C++ реализацию. Собственный код — полноценный
    кандидат, а не обязательный или заранее выбранный путь.
25. Сравнивать чтение, запись, числовую точность, Unicode, владение памятью,
    строгую валидацию и объём необходимой адаптации. Формального списка ОС
    недостаточно. Заявление библиотеки о переносимости не является свежим C3 test.
26. Для собственного варианта учитывать весь объём строгого JSON parsing,
    escaping/Unicode, checked conversions, locale-independent double и тестов.
    Он не должен быть набором поисков подстрок под текущий MCP request.
27. Приоритет — рабочий вариант на ESP32-C3, IDF5/6. Windows/Linux используются
    для быстрых сборок и общего contract corpus. До выбора backend не обещать
    конкретный Flash/RAM budget без измерений и не начинать большие матрицы.
28. Текущий этап — запись требований, обзор исходников библиотек и выбор узкого
    контракта. Библиотеки в продукт пока не подключены; готовность embedded MCP,
    JSON abstraction и совместимость конкретного MCP-клиента не заявляются.
