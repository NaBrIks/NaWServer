# План: общая передача HTTP/WS/SSE и оформление переносимости NaWServer

Дата: 2026-11-02. Статус: реализация выполнена; P7/P8 открыты из-за отказов предельной нагрузки и незавершённых чистых замеров.
Репозиторий: `NaWServer/`.
Ветка: `feature/unified-tx-scheduler`, исходная точка `7df17e7`.

## Поручение и текущая точка

После подготовки плана владелец поручил реализовать его и проверить на всех
подключённых устройствах. P0–P6 реализованы и зафиксированы в ветке: общий TX,
источники/последовательная запись, прямые WS/SSE, переносимость/CMake и frontend
набор. Windows/Linux и сборки RP/C3/S3 проверены; три платы обновлены и прошли
функциональные LAN-проверки. Умеренные сценарии RP/C3 проходят, предельный
duplex дал закрытия WS, пропущенные echo и оборванные HTTP-файлы. P7 остаётся
открытым; успешные короткие повторы не отменяют эти отказы.

Измерения CPU/памяти, конфигурации, выполненные исправления и оставшиеся проверки:
[аппаратный отчёт 02.11.2026](../readme_20261102_unified_tx_verification_ru.md).

Дополнение 03.11: [чистые сценарии C3](../readme_20261103_clean_observer_measurements_ru.md)
выполнены: idle, rare API, WS, SSE, combined, moderate и egress stress — PASS;
duplex stress повторил отказы без внешних вкладок. Проверяется возврат памяти
после срыва. Pico после программного restart не имеет внешнего WS/SSE, но
внешний HTTP из ChatGPT продолжает загрязнять idle: его чистая матрица остаётся
открытой. Предложенный допуск по IP записан как направление, пока не реализован.

Актуальный контракт API и явные ограничения:
[руководство общей передачи](../readme_unified_transmission_ru.md).
Фиксированные шаги, существующие worker'ы и explicit API реализованы; адаптивная
гранулярность пока не включалась без доказанного измерениями выигрыша. Managed
RX/private arena остаётся явным резервом, прямой transfer MemoryBlock в TX ещё
не заменил bounded copy sendOwned. Это сохранённые ограничения текущего этапа.

Коммит `7df17e7` отделяет сетевой ввод/вывод WebSocket от последовательных
прикладных HTTP/WS callbacks. Один WS-worker обслуживает все WS-соединения
сервера. SSE имеет собственный worker. Источник описания, результатов и ограничений:
[отдельный WS-worker](../readme_tcp_ws_worker_ru.md).

Предыдущая RP-демка зафиксирована в `819a187`. В ней канонические исходники сервера
работают через локальные RP-адаптеры; потокового файлового Response ещё нет.
[Находки переносимости](../../examples/rp2350_pico2_w/compatibility.md).

В рабочем дереве до текущей задачи уже были изменения в
`docs/readme_tcp_http_ru.md` и `tests/tcp_transport_integration_test.cpp`.
Они не включены в `7df17e7`. Сохранить их, не откатывать и не включать в будущий
коммит автоматически. При необходимости дополнять интеграционный тест сначала
отделить существующие изменения от своих.

## Согласованное направление

1. Верх HTTP/router/auth/WS/SSE уже работает на Windows/Linux/ESP/RP. Сохранить
   общие протоколы и прикладные контракты; аккуратно выделять нижние зависимости.
2. Общий ограниченный набор заданий передачи для HTTP, WS и SSE. Владелец имеет
   в виду одну очередь с состояниями и выбором готового задания, а не строгую FIFO.
   Раздельные глобальные очереди «важное/неважное» не являются целью.
3. Общий бюджет и пул памяти с поддержкой предоставленного аллокатора. Приоритет
   очереди и распределение памяти — разные механизмы, оба нужны.
4. Последовательная запись обработчика с разбиением данных на блоки. Прямое
   заполнение выданного блока и публикация после заполнения, без промежуточной копии.
5. Файлы читаются по мере освобождения блоков. Отдельную полную копию файла в RAM
   устранить. Встроенные immutable ресурсы продолжают использовать заимствование.
6. Размер блока настраивается при сборке через define. Начальный ориентир —
   четыре MSS. Общий код принимает байты; конкретный профиль связывает размер
   с TCP_MSS. Это не обещание полного принятия блока одним send и не привязка
   к неизменному согласованному MSS каждого соединения.
7. Приоритет, срок и допустимость отмены/замены задаются явно. Сервер сам не
   объявляет сообщения телеметрии ненужными. Ответы команд не теряются молча.
8. Последовательные, невложенные прикладные callbacks сохраняются по умолчанию.
   Сетевая передача должна продолжаться при занятом HTTP-обработчике.
9. Привязка серверных задач к ядру допустима в проверенном профиле. Поддерживаются
   проверенные сочетания SDK/RTOS/порта/toolchain; расширение по запросам.
10. Профили, клиент и UI — отдельный необязательный набор, не часть обязательного
    HTTP-ядра. Vue нужен только готовому Vue-интерфейсу.

## P0. Уточнить контракты и зафиксировать базовую точку

- Прочитать AGENTS.md, agents/architecture.md, стиль и актуальные документы
  памяти/admission/keep-alive/закрытия. Поздние решения владельца имеют приоритет
  над историческим запретом менять core только в рамках RP-эксперимента.
- Сопоставить обычный синхронный HTTP, managed HTTP, WS TX pool и SSE Sessions.
  Общий TCP backend — первая область миграции. Native IDF HTTPD не оборачивать
  искусственно общим владельцем сокетов; сохранить рабочим.
- Описать единое задание: token соединения с generation, порядок внутри
  соединения, вид владения данными, фактическая длина, позиция передачи, приоритет,
  сроки, правило отмены и результат завершения.
- Зафиксировать смысл accepted/queued/consumed/failed. Успешный send в ОС не
  равен TCP ACK и тем более обработке приложения клиента. Собственная очередь
  ожидания TCP ACK не требуется.
- Разделить размер блока, бюджет работы за проход и лимит заранее переданных
  стеку данных. Не обещать отсутствие частичных write даже для одного MSS.
- Зафиксировать поведение HEAD, Content-Length, неизвестной длины, keep-alive,
  ошибки источника после заголовков и остановки во время передачи.
- Создать новый ADR перед существенным изменением владения и исполнения;
  исторические ADR не переписывать как будто новая схема существовала раньше.

Готовность: понятные таблицы состояний, владения и ошибок; измеримая исходная
конфигурация памяти и сценарий сравнения задержек двух WS + HTTP + SSE.

## P1. Пул блоков, задания и прямое заполнение

- Использовать существующие BufferAllocator/BufferAccount/MemoryManager и
  move-only владение. Не создавать второй независимый универсальный аллокатор.
- Поддержать три профиля: полностью предоставленная статическая память;
  начальный резерв плюс ограниченный рост; динамика с пределами байтов и слотов.
  Фиксированное выделение при старте отличать от статического массива.
- Определить состояния: свободен → выдан производителю → готов → отправляется
  → освобождён; отмена возвращает владение однозначно.
- Выданный незаполненный блок учитывается в бюджете, но не блокирует готовые
  задания. commit публикует длину; отправитель не читает незавершённые записи.
- RAII/явная отмена возвращает блок. Истечение срока не разрешает освобождать
  память, пока производитель ещё имеет право писать в неё.
- Ввести общий потолок, предел на производителя/соединение и защищённые резервы.
  Сохранить существующий контракт основного API-ключа и различие физического
  резерва памяти, admission-квот и транспортных ресурсов.
- Выделить небольшие метаданные задания отдельно от payload. Большие immutable
  данные не копировать только ради помещения в общую очередь.

Готовность: тесты заполнения/commit/отмены, исчерпания каждого лимита, владения,
выравнивания аллокатора, восстановления памяти и работы без heap в static-профиле.

## P2. Общий планировщик передачи

- Единая ограниченная таблица/очередь заданий с выбором по готовности сокета,
  приоритету, сроку и порядку соединения. Не вводить блокировку всех клиентов
  из-за одного задания, ожидающего Writable.
- Единственный владелец записи каждого сокета. Partial write хранит позицию
  внутри задания; это остаётся внутренней деталью и не требует побайтовой копии.
- Никаких сетевых ожиданий под общей блокировкой очереди/пула.
- Начать с небольшого фиксированного бюджета обслуживания и предотвращения
  голодания. Рассмотреть ограниченную адаптацию шага при конкуренции; вводить её
  только с измерением выигрыша и верхних задержек, не как автоматическую магию.
- Приоритет действует между допустимыми границами передачи. Нельзя перемешивать
  байты двух сообщений одного TCP-соединения или выкидывать остаток WS-кадра.
- Реализовать явную отмену ещё не начатого задания по сроку, а замену устаревшей
  телеметрии — только по явно выбранной прикладной политике/ключу замены.
  Частично отправленное сообщение требует завершения или корректного закрытия.
- «Отдать токен телеметрии вместо файла» означает ограничить выдачу следующих
  блоков файлу, а не отнять память у выполняющего чтение производителя.
- Уточнить модель worker'ов: общий сетевой исполнитель может заменить отдельные
  WS/SSE циклы; прикладные callbacks и блокирующее чтение источников не должны
  незаметно переехать в критический сетевой цикл. Одна очередь не требует одной
  задачи на всю программу. Не сохранять двух владельцев записи одного сокета.
- Учесть пробуждение исполнителя при новой работе; текущий polling до 20 мс —
  известное ограничение, не целевой универсальный механизм уведомления.

Готовность: scripted частичные write/WouldBlock/ошибки/таймауты; два клиента,
один нечитатель, приоритет и гарантированный прогресс остальных; stale tokens,
остановка, отказ частичного запуска и повторная очистка без потери владения.

## P3. Последовательный writer и файловые источники HTTP

- Добавить явный API последовательной записи и API acquire/commit (названия
  выбрать при реализации). Сохранить смысл существующих send/sendOwned/
  sendImmutable либо предоставить явно документированную совместимость.
- write готового большого диапазона режет данные на блоки; при нехватке памяти
  ждёт ограниченно либо возвращает определённый результат неблокирующего API.
  Нельзя принять произвольный объём мгновенно при ограниченном бюджете.
- Возврат из операции не оставляет висячих указателей на данные обработчика.
  Для отложенного источника явно определить владение, завершение и закрытие.
- Разделить синхронную запись обработчика и фоновое продвижение источника:
  первая может занимать callback worker, вторая освобождает обработчик после
  подготовки ответа. Не вызывать другие callbacks рекурсивно внутри write.
- Файловая система остаётся приложению. Общий сервер знает источник байтов,
  а адаптер LittleFS находится в RP-поддержке/демо, без монтирования FS ядром.
- Читать непосредственно в выданные блоки, ограничить опережающее чтение,
  убрать 80 КиБ массив AssetHandler. Сохранить gzip, HEAD, fallback immutable
  ресурсов и корректную длину ответа. Для известной длины chunked не обязателен.

Готовность: точная передача 5 КиБ, 160 КиБ и файла больше общего TX-бюджета;
задержанный получатель, отмена, короткое чтение/ошибка FS; расход RAM зависит
от лимита блоков, а не размера файла. Это проверка передачи, не verify прошивки.

## P4. Подключить WS и SSE к общему механизму

- Сохранить wire codecs WS и SSE encoder; адаптировать подготовленные данные
  к общим заданиям. Не переписывать протоколы ради объединения памяти.
- Перенести WS TX pool и SSE frame ownership на общие блоки с сохранением их
  ограничений, токенов, callback-последовательности и обработкой overload.
- Учитывать WS control/close, fragmented frames в пределах существующей
  поддержки, SSE heartbeat/stall/deadline и явное открытие после auth/policy.
- Не добавлять скрытого удаления/слияния SSE/WS сообщений. Политики discard и
  replace включаются приложением явно; ответы команд не являются телеметрией.
- Не сохранять рядом лишние копии прежних очередей и новые блоки без измеримого
  обоснования. Сохранять отдельную статистику по протоколам внутри общего бюджета.
- Прежний порядок остановки EventSource/HTTP сохранить либо заменить отдельным
  явным контрактом с проверенной миграцией. Библиотечные зависимости живут до
  успешного завершения всех операций, включая retained close.

Готовность: HTTP + два непрерывных WS + SSE одновременно; один медленный клиент
не останавливает других. Порядок и содержимое сообщений, close, heartbeat,
лимиты, отключение функций и повторный запуск проходят тесты.

## P5. Оформить нижний уровень и сборку

- Выделить переиспользуемый lwIP socket adapter и FreeRTOS worker; особенности
  Pico SDK/ESP-IDF оставить в малых адаптерах. Сохранить Windows/Linux и native
  HTTPD. Единицы стека upstream FreeRTOS/IDF различаются.
- Ввести только необходимый внутренний контракт mutex/RAII. Удалить зависимость
  RP-поддержки от экспериментального compat/bits/gthr.h после миграции всех
  затронутых мест. Не объявлять этим исправленной многопоточность всей libc.
- RP SDK/libc/server tasks пока CPU0. Полноценная SMP libc не входит автоматически
  в эту работу; память и errno toolchain требуют отдельной интеграции.
- Поддерживать проверенные сочетания: Pico SDK 2.3.1, FreeRTOS 11.3.3 и
  community RP2350_ARM_NTZ port из RP-демо; существующие ESP-IDF профили и host.
  Не обещать любую FreeRTOS и не обновлять зависимости попутно.
- Сохранить лицензии/уведомления MIT/BSD и поставщиков. Отдельно учесть состав
  распространяемых firmware/SDK компонентов, не перелицензировать чужой код.
- Один список исходников каждой подсистемы; верхняя CMake-конфигурация выбирает
  возможности и платформу. Нижние CMakeLists/.cmake могут добавлять файлы в цель,
  не превращая каждый каталог в самостоятельную библиотеку.
- Дать обычную SDK-независимую CMake-цель и обвязку IDF/Pico/host. Демки больше
  не перечисляют исходники NaWServer. Не использовать рекурсивный автоподхват
  всех cpp; явный список каждой части хранится один раз. Массовое перемещение
  исходников без необходимости не является целью.

Этот этап можно выполнить раньше P2, если он нужен для переносимой реализации,
но не смешивать платформенную реорганизацию и изменение планировщика в одном
большом непроверяемом коммите.

## P6. Отдельный необязательный набор для устройств и страниц

- Выделить описанные контракты, затем независимый от Vue JS/TS-клиент HTTP/WS/SSE
  и CBOR/валидации; готовая Vue-оболочка и компоненты используют этот клиент.
- Профиль задаёт страницы, подписи, расширения и сборку. Реальные возможности
  подтверждает устройство. Убрать RP build-time подстановки ESP-строк.
- CPU-компонент получает массив ядер и явно определённую общую загрузку;
  отсутствующие данные не подменяются нулём. Индикация сообщений компактная,
  подробности по запросу, без автоматических toast/banner и сдвига геометрии.
- Сохранить единый frontend, не создавать копии деревьев src для каждой демки.
  Продуктовые настройки/пины/FS/NVS остаются приложениям.
- Выполнять обязательный UI-стандарт перед любыми правками интерфейса.
  Новый репозиторий и новая система публикации пока не требуются.

## P7. Приёмка и измерения

| Область | Проверка |
| --- | --- |
| Host | Windows и локальный Linux: существующие регрессии + новые queue/ownership/lifecycle тесты |
| Профили | WS/SSE/admission on/off; обычный и managed HTTP; static/mixed/dynamic memory |
| Конкуренция | Два непрерывных WS, SSE и большой HTTP-файл; отдельно медленный/отключившийся клиент |
| Данные | Точное содержимое и порядок, partial writes, обрыв посередине, отмена по разрешённой политике |
| Память | Выделено/занято/пик/отказ; лимиты и резервы; возврат динамических блоков после закрытия |
| Задержки | До/после: p95/max, период сообщений, размер, длительность; не подменять latency средней скоростью |
| MCU | Сборки RP и доступных проверенных ESP-профилей; отдельная on-device проверка на разрешённой плате |
| UI | Реальная проверка общей страницы, WS/SSE, размеров/тем/локализации и неизменной геометрии |

Не объявлять доказанным отсутствие задержек по одному короткому прогону. Не
устраивать дневные длительные stress/soak; продолжительность fuzz не более двух
минут по действующему правилу. Длительные проверки планировать отдельно.

Не прошивать общую ESP32 MAIN/FS чужой демкой. RP-идентичность:
`<USB_SERIAL>`, работающий ранее адрес `http://192.0.2.10/`, порт 80.
Перепроверить текущую доступность/устройство перед аппаратными действиями.
Пользователь не хочет повторных физических BOOTSEL и отдельного verify/readback
прошивки: использовать существующий software reset/Flash.ps1 без `-v`.
Ничего не размещать на порту 443. Не коммитить секреты, build, firmware и raw logs.

## P8. Практические расходы и управление наблюдением, поручение 02.11.2026

Владелец заметил пилу CPU на C3 и поручил исследовать новый вариант в простое,
при редком API, обычном наблюдении, умеренной и предельной нагрузке. Старый вариант
в сопоставимых условиях не измерялся; не объявлять его быстрее или медленнее по памяти.

- Фактический C3/S3 профиль исходной проверки был `-Og`, Pico — Release `-O3`.
  Для C3 подготовлен отдельный performance-профиль ESP-IDF `-O2`; проверять
  реальные compile_commands, не выводить оптимизацию из имени папки/файла.
- Обнаружен дополнительный observer: общий frontend каждую секунду запрашивал
  summary и все страницы задач, одновременно получая WS 10 Гц и SSE 1 Гц.
  Сделать три независимых управления WS / HTTP 1 Гц / SSE с явным состоянием.
  HTTP по умолчанию выключен, запуск и ручное обновление получают один снимок.
- Счётчики задач сравнивать на границах сценария без постоянного HTTP-опроса.
  Проверять отсутствие чужих клиентов/запросов и одинаковый boot_id; фиксировать
  CPU по задачам, RAM/минимум/крупнейший блок, TX давление/отказы и задержки клиентов.
- Сценарии: простой, API примерно раз в минуту, только WS, только SSE, оба,
  два WS + SSE + HTTP, четыре WS + SSE + загрузки ресурсов. Дневные stress-прогоны
  ограниченные; длительный soak остаётся отдельной работой.
- Измерен резерв двух безусловных циклов 1 мс: TX и SSE. После базового замера
  перейти к пробуждению по работе/срокам и повторить те же сценарии, проверяя
  notify-before-wait, stop, WouldBlock, закрытие и задержку первой передачи.

P8 выполняется; первые наблюдения с меняющимся числом клиентов не являются
чистым сравнением компиляторных профилей. Фиксировать отдельно стоимость
наблюдения и фактическую стоимость обработки/передачи.

Контрольный срез: новые переключатели развёрнуты; TX/SSE пробуждаются по работе,
Flash assets Showcase используют immutable spans. Измеритель семи сценариев
находится в `tools/load/transmission-scenarios.mjs`, считает попытки и все
ответы echo, проверяет окончания потоков, ресурсы, boot и TX failures.
У старых вкладок C3/RP остаётся фоновый HTTP/WS/SSE; idle/rare API и чистая
WS/SSE-матрица ожидают их ручного закрытия/выключения. Не записывать эти сценарии
как PASS. Найденная связь пилы с HTTP-опросом и предел последовательных callbacks
зафиксированы в отчёте; причина всех обрывов пока не установлена.

## Окружение и исходные ограничения при создании плана

Пути и размеры ниже фиксируют исходную точку до реализации. Последующие hardware
сборки/прошивки и результаты текущей приёмки записываются в `local/unified-hardware/`
и итоговый отчёт; исходные BIN-размеры не описывают новую установленную прошивку.

- Windows-тесты текущей задачи: `local/ws-worker-tests`; отключённый admission:
  `local/ws-worker-noadmission`. MSVC через VS18 Enterprise, установленный Ninja.
- Независимый Linux: `local/ws-worker-linux`, `local/ws-worker-linux-off`;
  существующий Zig 0.14.1 собирает x86_64-linux-gnu, CTest запускает бинарники
  в локальном Ubuntu WSL через `local/backend26-linux-run.ps1`.
- В уже изменённом до задачи integration test managed restart запускается
  безусловно даже при compiled-out admission. В таком профиле он ожидаемо
  получает Unsupported и падает; новые worker tests on/off проходят. Согласовать
  узкую корректировку проверки профиля, не потеряв существующие изменения.
- RP build: `examples/rp2350_pico2_w/build`, текущий BIN 849600 байт. Для
  повторной компиляции достаточно cmake --build; frontend не пересобирать без
  изменения его исходников.
- C3 IDF5.5.6: `local/backend26-idf/1`, последний BIN 964544 байта. Старые scripts
  ссылаются на удалённый tool-esptoolpy; доступный модуль esptool 5.1.0 находится
  в `local/host-tools/esptool5/Lib/site-packages` и добавлялся к PYTHONPATH только
  процесса сборки. IDF6.1 cache ссылается на отсутствующее Python-окружение;
  не объявлять его проверенным и не устанавливать крупные пакеты автоматически.
- В исходной точке отдельный WS-worker ещё не был прошит. Во время реализации
  начаты аппаратные обновления и проверки; итоговая матрица должна указать
  фактически установленную версию каждой платы и оставшиеся отказы.

Работать небольшими проверяемыми этапами с отдельными коммитами. К завершению
предоставить состав изменений, воспроизводимые проверки, сравнение памяти и
задержек, реальный адрес демо и явные оставшиеся ограничения.
