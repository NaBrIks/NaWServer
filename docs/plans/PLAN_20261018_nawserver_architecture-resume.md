## Что предстоит исследовать и согласовать

1. Подробно объяснить SSE: однонаправленные события, переподключение, id/replay vs snapshot, heartbeat, ограниченные очереди, медленные клиенты, жизненный цикл. Старый experimental/sse пока исключен из сборки.
2. WS authentication: проверка до HTTP 101 и разрешения на каждую команду после подключения. Браузерный WebSocket не позволяет произвольный Authorization header; рассмотреть сессию/cookie и короткий билет, Origin, срок и отзыв.
3. В штатном проверенном ESP-IDF HTTPD native WS upgrade происходит до callback обработчика. Не обещать защищенный WS без реально проверенного pre-handshake механизма. Защищенный WS сейчас отклоняется при запуске; не убирать эту защиту ради демо. В некоторых глобальных локальных SDK найден дополнительный hook, но его наличие не подтверждено в официальных проверенных ветках; не строить переносимость на нем.
4. Исследовать handler_middleware.h и представить варианты: существующий декоратор, guards/policies отдельных маршрутов, общий pipeline. Не утверждать текущий API как окончательное решение без анализа.
5. Требование владельца: публичные показания/статистика, защищенные расширенные функции/управление, возможно роли и разные хранилища пользователей. Разделить authentication, authorization, route policy, storage. C++ pure virtual abstract classes — аналог контрактов C#, но интерфейсы вводить только там, где действительно требуется подмена.
6. Сопоставить профили: фиксированные роли/пользователи в прошивке; фиксированные permissions/роли + изменяемые пользователи в NVS; ограниченный динамический RBAC; внешняя авторизация. Динамические роли могут выбирать только известные прошивке права, а не создавать новые серверные операции. Дать аргументы применимости к MCU, бюджеты памяти/задержек и последствия хранения.
7. Начальная рекомендация (еще не решение): небольшой фиксированный набор permissions, изменяемые пользователи/назначения в NVS; storage providers вне транспортного ядра, ограниченный cache и очередь записи. Не хранить открытые пароли; salt + password verifier, стоимость KDF измерять на C3. NVS не обеспечивает произвольную транзакцию нескольких ключей: требуются версии/снимок и восстановление целостности, запрет потерять последнего администратора. Сессии обычно в RAM, не писать flash на каждом запросе.
8. Карты: внешняя граница библиотеки; слои ответственности; отдельная ось контекстов FreeRTOS (задачи, не изолированные процессы); поток с точками ожидания/передачи управления и освобождения памяти; создание/запуск/работа/остановка глазами прикладного кода; отдельный явно проектный вариант доступа.
9. Нагрузочную проверку C3 выполнять ближе к концу после согласованной реализации и готового демо. Нынешние 13 loopback и сетевой smoke не доказывают долговременную стабильность.

## Проверенные исходные сведения

- Текущий middleware — borrowed decorator над HandlerBase; Credentials также borrowed. WebServerContainer применяет общие credentials ко всем добавляемым маршрутам. Пример minimal уже вручную защищает только /private и оставляет /health и /ws публичными.
- Основная работа HTTP callbacks и очереди WS выполняется HTTPD task. Название Async не означает неблокирующую сеть. Медленная отправка может задержать другие маршруты.
- WS payload ограничен 4096 байтами, pending — 4 на клиента, очередь владеет копией, session token защищает от повторного использования fd. void send не сообщает об отказе.
- HTTP тело ограничено 4096 байтами и полностью читается до вызова прикладного handler; pre-body guard еще не реализован.
- Плата C3 COM5, последняя известная LAN DEVICE_IP:80. Нынешняя прошивка — minimal; в этой стадии новых прошивок не делали.
- Полный исходный backup: backups/c3-before-NaWServer.bin (игнорируется), SHA-256 d8ae0fe30ec3664af49b3a45ecaef3d5cfa9391457818a629441ca5ad6548471. Перед следующей записью заново проверить target/backup.
- Код новых middleware/auth/storage/SSE в этой стадии НЕ менялся.

## Уточнение владельца: статическая композиция, без legacy

2026-10-18: совместимость старого middleware не нужна. Требовать возможность
статических route descriptors, handlers/guards/providers и ограниченного runtime
состояния. Не делать обязательными builder, heap factories и старые callback hooks.
Запуск I/O/storage/tasks отделить от конструирования. Принятый ADR:
ADR_20261018_nawserver_static-composition-and-clean-api.md.
Код нового API ещё не реализован. Динамические роли — опциональные bounded данные,
а не изменение каталога операций или необходимость неограниченного heap.

## Уточнение: выбор стиля middleware ещё не принят

Владелец просит сначала подробно сравнить decorators, guards/policies, next pipeline
и static template chain, затем сам примет решение. Guards в ADR описывают прежнее
предложение агента, а не согласованный окончательный middleware engine. Не начинать
переделку core до этого выбора. Принятые требования статической композиции и отсутствия
legacy-совместимости остаются в силе. Следующее принятое решение оформить новым ADR;
существующие ADR и review не переписывать.

## Выбрано: статический next pipeline и плоские resource handlers

2026-10-18 владелец предпочёл next pipeline, Chain разной глубины, сохранение наглядной
раздачи памяти/FS/других источников. Pending-choice ограничение снято этим решением.
Принят ADR_20261018-2_nawserver_static-next-pipeline.md; код engine пока не менялся.
Основа: Chain<N> non-owning refs + общий executor, policies на маршрутах, next 0/1 раз.
Не усложнять обычный public resource auth-обёртками. Синхронный fast path допустим;
измерить latency HTTP/WS вместе и при медленном читателе, затем выбрать offload для
долгих передач. Loop send_chunk/vTaskDelay внутри callback не даёт HTTPD выполнять
другие jobs. FIFO WS queue отделяет producer от отправки, но не гарантирует latency.

## Три фасада Chain и критерии backpressure

Владелец предпочёл typed Chain и makeChain и предложил оставить все три формы.
Они должны давать один engine; counted форма получает отдельное имя FixedChain<N>.
Семантику владения и lifetime фиксируем одинаково. Предложение по slow clients
сохранено в IDEA_20261018_nawserver_chain-facades-and-backpressure.md: queue age/bytes,
socket progress, optional application ACK, snapshot/latest vs ordered/replies.
Пороговые значения пока стендовые кандидаты; код не менялся, нагрузка не запускалась.

## Scope: LAN/телефон, 2–4 клиента, disconnect при отставании

Владелец отменил усложнение обслуживания медленных клиентов. Актуален
ADR_20261018-3_nawserver_local-device-limits.md: лимиты в коде, timeout/индивидуальное
переполнение → close, excess connection → reject, освобождение bounded ресурсов.
maxConnections отдельно от maxWsClients. Не добавлять coalescing/replay/adaptive QoS
и worker pools по умолчанию. Нормальная mixed-load отзывчивость проверяется на C3.
Три фасада одного next pipeline остаются. Реализация limits/core ещё впереди.
