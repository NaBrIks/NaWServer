# 27.10.2026 — допуск клиентов и отказ при перегрузке

Статус: контракт одобрен владельцем; реализация и короткая аппаратная проверка
завершены27.10.2026, в пределах профилей из [отчёта](../readme_20261027_admission_qos_ru.md).
Основную систему определяет заранее настроенный ключ. Модуль
допуска опционален, статический; верхний слой может подсказать TCP приоритетный IP.
Текущее API и границы: [руководство](../readme_admission_ru.md).
Последующие тесты — не более120 с каждый, существующие SDK/окружение не обновлять.

## Требуемое поведение

Допущенный логический клиент получает ограниченный резерв. Новые клиенты могут
получить свободный резерв либо явный отказ; вытеснения допущенных из-за прихода
новых клиентов нет. «Одна страница» включает несколько HTTP-запросов и, при
использовании, WS/SSE. Один TCP socket или IP не определяет такую сессию.

REST-клиент определяется стабильной идентичностью между запросами. Владелец
выбрал заранее заданный приложением ID/ключ основной системы. Идентификатор
резерва сам по себе не заменяет проверку доступа.

| Условие | Ответ |
|---|---|
| Нет свободного резерва для нового клиента/запроса | HTTP503 с короткой причиной и Retry-After |
| Клиент превысил свою частоту запросов | HTTP429 с причиной и Retry-After |
| Нет резерва для нового WS/SSE | HTTP503 до101/начала SSE; поток не создаётся |
| Некорректный запрос/превышен размер | Существующие протокольные ошибки и пределы; не маскировать под503 |
| Допущенный клиент работает в своих пределах | Его резерв сохраняется, новые клиенты его не расходуют |
| Собственная очередь отправки заполнена | Явный результат backpressure вызывающему коду; чужие сессии не закрываются |

Если уже открытый WS сам нарушает оговорённые пределы или перестал читать,
возможен ограниченный по времени Close с подходящим кодом, например1013 для
временной нехватки возможности продолжить. Это отдельный случай от отказа
новому подключению; рабочий WS нельзя закрывать ради нового клиента.

HTTP503/Retry-After: RFC9110 §15.6.4; HTTP429: RFC6585 §4;
WS1013: IANA WebSocket Close Code Registry. HTTP200 с сообщением о нехватке
ресурсов не считать успешным обслуживанием или корректной заменой503.

## Резерв и границы библиотеки

- Публичная библиотека оперирует группами маршрутов/клиентов и квотами. Понятия
  «страница демо», LCD и «наша основная система» в ядро не попадают.
- Для профиля приложения можно задать отдельно UI-сессию1 и API-клиентов N,
  с собственными пределами одновременных запросов, очередей и зарезервированных
  байтов. Неиспользованный защищённый резерв другие клиенты не занимают.
- Готовый объект WS и крупные body/JSON/response buffers создаются после допуска.
  Таблица резервов и небольшой путь отказа ограничены и выделены заранее.
- Отказ также требует ресурсов: оставить отдельный запас для приёма/чтения
  ограниченных заголовков и короткого ответа. Системные TCP структуры ОС/lwIP
  не обещать свести к нулю; их пределы и запас учитывать отдельно.
- Резерв освобождается явно либо после ограниченного простоя с окном возврата
  того же клиента. Новое постороннее подключение действующий резерв не отнимает.
- Гарантия касается защиты от других клиентов при работающей сети и соблюдении
  собственных лимитов/контракта обработчика. Бесконечный handler или недоступную
  сеть нельзя исправить одним admission counter.

## Исходный разрыв до реализации

В `src/backends/tcp/http_backend.cpp` после accept вызывается весь синхронный
`executeHttpConnection`. В `http_connection.cpp` writer отправляет ответ целиком
до возврата. В это время тот же HTTP/WS owner не принимает следующий запрос и
не выполняет WS callbacks. Проверка quota после ожидания этого места не является
ранним отказом. При полном registry сейчас новое соединение просто закрывается;
дополнительного гарантированного резерва для ответа503 нет.

Нужны ранний допуск до чтения body/handlers и ограниченное обслуживание сетевого
ввода-вывода, сохраняющее доступность отказов и защищённых клиентов при крупном
ответе. Не вводить повторный вход в callbacks приложения из HTTP write: сейчас
у приложений общие буферы. Время жизни данных и сохранение синхронного callback
контракта должны быть явно решены до такого изменения планировщика.

## Приёмка реализации

1. Обычные1/2/3 клиента с подходящим общим лимитом: прежняя семантика, отсутствие
   новых ошибок/разрывов, сопоставление p95/max и RAM с контрольным прогоном.
2. Защищённые UI/API заняты, приходят лишние: все классифицированные лишние
   запросы получают503/429; допущенные не теряют соединения/ответы.
3. Измерять admission decision, полный отказ, задержки защищённого клиента и
   пик памяти отдельно. Численный deadline отказа согласовать/зафиксировать
   до приёмки; таймаут или обрыв вместо ожидаемого503 не считать PASS.
4. Многократный отказ не увеличивает прикладные payload allocations/квоты;
   проверить rollback, освобождение, повторное подключение и исчерпание
   небольшого пула отказов. Исчерпание ОС/TCP учитывать отдельно от HTTP503.
5. Проверять C6 и S3 отдельно; перегрузку и обычные профили не смешивать.
   Каждый прогон максимум120 с; результаты и конфигурацию дописать в журнал.
