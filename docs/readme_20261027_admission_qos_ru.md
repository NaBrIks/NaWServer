## Что реализовано

Независимый статический `Admission<N>`, необязательный middleware и отдельное
включение раннего TCP допуска. Настроенный основной ключ и каждый принятый
общий клиент получают свои квоты. Неиспользованный основной резерв не занимает
гость. Нет квоты —503, превышена собственная частота —429. При отказе не
выделяются крупные payload buffers/WS objects. Входные места/HTTP jobs/WS arenas
резервируются при старте; small control allocations и ресурсы ОС учитываются отдельно.

Старый TCP путь отправлял HTTP целиком в единственном HTTP/WS owner, поэтому
одного позднего счётчика/middleware было недостаточно. Опциональный scheduler
читает ограниченные заголовки, допускает до body и выдаёт ответы порциями.
Callbacks остались последовательными. Обычные ответы копируются до возврата;
неизменяемые assets используют явный `sendImmutable`, без копирования большого тела.
SSE endpoints исправлены: нехватка ресурса `NoMemory`, `Full`, `Stopping` →503,
а не400. Проверка доступа остаётся у приложения.

Приложение может после проверки ключа отметить IPv4 как приоритетный через
callback. TCP оставляет ему входное место до чтения HTTP; квота основного API
всё равно определяется ключом. На ПК проверено: обычный клиент удерживает
неполные заголовки, приоритетный получает вход, но неправильный ключ не получает
основной резерв. На платах этот IP callback выключен: все managed клиенты имеют
один адрес ПК и по IP неразличимы. Самостоятельного доверенного IP cache в ядре нет.

API/статическая инициализация/границы: [руководство](readme_admission_ru.md).

## Верификация и ограничения

- Windows CTest52/52; Linux7/7 admission/middleware/TCP QoS/stream/IDF variants.
- Host admission OFF: scheduler source отсутствует в build graph, HTTP/WS/SSE3/3.
- SDK5 C6/S3 — сборка и прошивка; SDK6 C3 — только сборка, без прошивки.
- Go test/vet PASS. Host slow-reader4MiB immutable response не блокирует основного
  клиента; repeated503 не увеличивают used/peak payload ledger. Middleware не
  списывает ранний допуск повторно; проверены expiry, stale/double release и cleanup.
- При **полном** заполнении preallocated ingress новое TCP-соединение закрывается;
  это отдельная finite TCP граница, не503. Бесконечный SYN/slow-header flood и
  абсолютная QoS при недоступной сети/блокирующем endpoint не обещаются.
- Анонимные вкладки имеют одну общую идентичность; разделение страниц/куки
  задаёт приложение. Автоматического per-tab reservation этот тест не доказывает.
- Первые host-smoke выявили неверный размер registry в test fixture и отсутствие
  отправки SSE rejection в тестовом endpoint. Позже EOF-aware IP ingress check
  устранил ошибочное повторное использование ещё закрывающегося единственного
  ingress slot в самом тесте. Исходные failed logs сохранены, итог52/52 отдельный.
