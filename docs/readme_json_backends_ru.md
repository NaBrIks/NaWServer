# JSON-backends: выбор, ограничения и измерение

JSON-backend выбирается при сборке. Переключение не меняет MCP JSON-RPC,
инструменты приложения или прикладной CBOR. Встроенный сервер не требует Node.js,
страницы браузера или внешнего посредника.

## Выбор реализации

При `NAWSERVER_MCP=1` должна быть выбрана ровно одна реализация:

| Define | Backend в метаданных | Подпись в INFO / MCP |
|---|---|---|
| `NAWSERVER_JSON_BOUNDED=1` | `nawserver_bounded` | NaWServer bounded JSON |
| `NAWSERVER_JSON_YYJSON=1` | `yyjson` | yyjson |
| `NAWSERVER_JSON_RAPIDJSON=1` | `rapidjson` | rapidjson (RapidJSON SAX) |

Неактивный define задаётся как `0` либо не задаётся. Отсутствующий
`NAWSERVER_MCP` означает `0`; выбор JSON-backend сам по себе не включает MCP.
При выключенном MCP его маршруты, реестр и рабочие буферы не создаются.
Независимая JSON-зависимость самого приложения может остаться в сборке.

Начальный выбор — наш bounded reader. Первой внешней реализацией добавлен
yyjson: адаптер использует её reader и allocator, сохраняя общий контракт
точных целых чисел и ограничений памяти. Ночью 26/27 октября добавлен RapidJSON
SAX; состояние аппаратных проверок и измерений фиксируется отдельно в
[ночном отчёте](readme_overnight_json_load_ru.md).

`yyjson` — внешняя библиотека чтения JSON. Зафиксирована версия **0.13.0**,
commit `6447536015f3d600f3d65323b10976103b337ca7`; исходники и MIT-лицензия
сохранены в [third_party/yyjson](../third_party/yyjson/README.md).
Это не установка или обновление SDK/пакетов окружения.

Приложение может передать существующий совместимый CMake target через
`NAWSERVER_YYJSON_TARGET`, чтобы не создавать вторую копию той же зависимости.
Версией и опциями такого target управляет приложение; общий набор контрактных
проверок обязателен и для него.

RapidJSON закреплён на commit `24b5e7a8b27f42fa16b96fc70aade9106cf7102f`.
Сохранены upstream-лицензии и отдельная локальная поправка raw-number exponent:
исходный reader преждевременно отвергал допустимый `0e10000` до передачи
raw number адаптеру. Данный путь передаёт проверку диапазона общему `from_chars`;
грамматика остаётся у RapidJSON. См. [происхождение и patch](../third_party/rapidjson/README.md).
`NAWSERVER_RAPIDJSON_TARGET` может предоставить существующий совместимый target
с заголовками, но он должен содержать эту поправку или эквивалентное исправление
upstream и проходить общий corpus. Произвольная версия RapidJSON не считается
совместимой автоматически. LwJSON/Frozen в продукт не добавлены:
[обзор ограничений](readme_json_candidate_review_ru.md).

## Настройки ESP-IDF и host

В `menuconfig` раздел **NaWServer optional MCP** включает endpoint, затем
предлагает choice **JSON reader/validator**. По умолчанию выбран bounded.
Эквивалент для yyjson в sdkconfig/defaults:

```ini
CONFIG_NAWSERVER_MCP=y
# CONFIG_NAWSERVER_JSON_BOUNDED is not set
CONFIG_NAWSERVER_JSON_YYJSON=y
```

Для RapidJSON вместо yyjson выбирается `CONFIG_NAWSERVER_JSON_RAPIDJSON=y`
и начальная арена `CONFIG_NAWSERVER_JSON_WORKSPACE_BYTES=8192`.
Готовые overlay находятся в `examples/common/sdkconfig.{yyjson,rapidjson}.defaults`.

Host CMake требует явного единственного backend. Примеры из корня репозитория
с уже настроенным подходящим C/C++ компилятором:

```text
cmake -S host -B local/json-bounded -DNAWSERVER_MCP=ON -DNAWSERVER_JSON_BOUNDED=ON -DNAWSERVER_JSON_YYJSON=OFF
cmake -S host -B local/json-yyjson -DNAWSERVER_MCP=ON -DNAWSERVER_JSON_BOUNDED=OFF -DNAWSERVER_JSON_YYJSON=ON
```

Обе реализации и yyjson собираются из имеющихся исходников. Эти команды не
устанавливают компилятор, SDK или пакеты. Требуется реализация floating
`std::from_chars`, поддерживающая контракт; локальный Zig/libc++19 такого overload
не предоставил. Сборку MCP off через него нельзя считать проверкой JSON-backend.

| SDK setting | C++ define / host CMake setting | Начальное значение |
|---|---|---:|
| `CONFIG_NAWSERVER_JSON_INPUT_BYTES` | `NAWSERVER_JSON_INPUT_BYTES` | 4096 |
| `CONFIG_NAWSERVER_JSON_STRING_BYTES` | `NAWSERVER_JSON_STRING_BYTES` | 512 |
| `CONFIG_NAWSERVER_JSON_CONTAINER_ITEMS` | `NAWSERVER_JSON_CONTAINER_ITEMS` | 32 |
| `CONFIG_NAWSERVER_JSON_DEPTH` | `NAWSERVER_JSON_DEPTH` | 8 |
| `CONFIG_NAWSERVER_JSON_VALUE_CAPACITY` | `NAWSERVER_JSON_VALUE_CAPACITY` | 256 |
| `CONFIG_NAWSERVER_JSON_WORKSPACE_BYTES` | `NAWSERVER_JSON_WORKSPACE_BYTES` | 2048 / 16384 / 8192 |
| `CONFIG_NAWSERVER_MCP_OUTPUT_BYTES` | `NAWSERVER_MCP_OUTPUT_BYTES` | 2048 |

В строке workspace числа относятся к bounded, yyjson, RapidJSON. В host override
передаётся как `-DNAWSERVER_JSON_WORKSPACE_BYTES=16384`; при прямой компиляции
аналогичный define имеет то же имя. В SDK параметры преобразуются в публичные
C++ defines. Нельзя уменьшить фактическую арену приложения ниже настроенного
контракта и считать endpoint готовым.

`INPUT_BYTES` — предел приёма, не дополнительный входной буфер. HTTP должен
отдельно разрешать соответствующий размер тела. `STRING_BYTES` относится к
декодированным UTF-8 строкам и ключам. Tools вправе устанавливать меньшие
пределы: у echo это 256 UTF-8 байт. Увеличение `DEPTH` не увеличивает стек HTTP
worker. `VALUE_CAPACITY` включает ключи объектов; `OUTPUT_BYTES` вмещает весь
ответ JSON-RPC, включая схемы tools и id.

Стек обработчика на ESP настраивается отдельно:
`CONFIG_NAWSERVER_TCP_HTTP_STACK_SIZE` для TCP и
`CONFIG_NAWSERVER_HTTPD_STACK_SIZE` для native HTTPD. Начальный размер с MCP —
8192 байта, без MCP — 6144 байта. Сохранённый sdkconfig сохраняет прежний выбор;
при миграции его нужно проверить. В полной C6-демо 6144 байта переполнялись
как с yyjson, так и при `device_info` с bounded; обе MCP-конфигурации используют
8192. Это отдельная от reader arena память задачи, а не дополнительный JSON DOM.

INFO и страница MCP используют `firmware.json_backend` / `mcp_enabled`,
переданные работающей прошивкой. Подпись не вычисляется из имени платы или
выбранного demo. Неизвестное строковое имя backend показывается буквально.

## Общий контракт и память

Приложение использует общий публичный JSON-интерфейс, не DOM-типы yyjson.
Backend действительно разбирает документ выбранной реализацией. Writer остаётся
общим ограниченным C++ encoder; готовый результат проходит проверку выбранным
backend. Использование yyjson не означает применение её mutable writer DOM.

Одинаково проверяются строгая грамматика JSON, UTF-8/Unicode escapes,
дубликаты ключей, вложенность, переполнение ёмкости, конечные double и точные
int64/uint64. Неверные значения не превращаются в успешные округлённые числа.
Идентификаторы JSON-RPC сохраняют значение; исходное написание escape/числовой
лексемы не является отдельной гарантией.

Рабочую арену передаёт вызывающий код с требуемым выравниванием. Автоматического
перехода к системному heap при её нехватке нет. Выходной буфер отдельный;
срок жизни borrowed views ограничен исходным вводом и текущим разбором.
Настройки памяти относятся к выбранному backend и профилю, а не к каждому
подключению. Проверять следует и JSON-арену, и буфер результата MCP.

Исходный ресурсный профиль: вход 4096 Б, строка 512 Б, контейнер 32 элемента,
глубина 8, ёмкость представления 256 значений, вывод MCP 2048 Б.
Начальная настройка арены — 2048 Б для bounded, 16384 Б для yyjson,
8192 Б для RapidJSON. RapidJSON SAX декодирует строки на месте в одной копии
неизменяемого входа внутри арены и сохраняет компактные дескрипторы значений.
Это **настройки ёмкости, не результаты измерения потребления памяти**.
Фактические значения необходимо читать из конфигурации конкретной сборки;
допустимый документ может потребовать увеличения арены.

На S3 demo общее хранилище может выделяться в PSRAM без fallback во внутреннюю
RAM. Это политика приложения, не требование общего JSON/MCP к ESP32 или PSRAM.
`System.Text.Json` в C# simulator — отдельная реализация симулятора;
её подпись не означает использование MCU C++ backend.

## Как сравнивать стоимость

Использовать одну плату C6, одинаковые SDK, TCP-профиль, компилятор, оптимизацию,
Wi-Fi-конфигурацию и один упакованный frontend с зафиксированным SHA-256.
Сравнивать MCP off, MCP bounded и MCP yyjson. Не менять assets между вариантами.

Раздельно записывать:

- Flash-секции и link map: код, константы, `.data`, `.bss`, отброшенные символы.
- Зарезервированные размеры и выравнивание арены/вывода, место хранения.
- Runtime high-water арены, free/min heap и остаток стека после одинакового
  короткого корпуса запросов и отклонённых превышений лимитов.

Размер зарезервированной арены не равен её high-water; успешная сборка не
доказывает runtime fit. Не выводить потребление всего приложения из размера
одного JSON parser.

Для оценки повторного использования yyjson нужна дополнительная пара сборок:
приложение **в обоих вариантах** реально вызывает тот же yyjson reader на
фиксированном документе и использует результат. Link map должен подтверждать,
что вызовы не удалены оптимизатором. Тогда разница показывает дополнительную
стоимость MCP-backend при уже существующей зависимости, отдельно от стоимости
первого подключения библиотеки. Не добавлять writer DOM только ради такого теста.

Измеренные результаты и точные профили сохраняются в
[журнале сборок и памяти](readme_build_memory_log_ru.md); этот документ не
подменяет их оценками. Требования к контракту:
[readme_mcp_json_requirements_ru.md](readme_mcp_json_requirements_ru.md).

## Измерено на C6, 26.10.2026

Один и тот же короткий корпус: шесть документов, 1200 разборов,
ESP-IDF 5.5.6, GCC 14.2, `-Og`, 160 МГц. Изолированный fixture без Wi-Fi/LCD:

| Reader | BIN, Б | Арена: резерв / наблюдаемый peak, Б | Время, мс |
|---|---:|---:|---:|
| bounded | 285408 | 2048 / 1016 | 334,462 |
| yyjson | 400528 | 16384 / 4216 | 243,340 |

Когда само приложение уже реально вызывает тот же yyjson, пара образов
составила 401296 Б (app yyjson + bounded) и 400688 Б (общий yyjson):
**экономия 608 Б Flash ценой дополнительных 14336 Б арены**. Наш reader
оставлен начальным выбором. Результат зависит от приложения и опций сборки;
peak этого корпуса не гарантирует размещение любого допустимого документа.

Оба reader прошли одинаковые контрактные проверки. На физической C6 проверена
полная MCP-цепочка с обоими; S3/yyjson в этой фазе проверена сборкой.
После измерений C6 и S3 возвращены на TCP + bounded, MCP list/read/write
проверены на обеих платах. Подробные Flash/RAM, контрольные суммы, config,
heap/stack и промежуточные сбои сохранены в журнале.


## Ограничения браузерного tester

Поля `firmware.json_workspace_bytes`, `mcp_input_bytes` и `mcp_output_bytes`
показывают настройки работающей прошивки; `0` допускается при выключенном MCP,
отсутствующее поле старой прошивки остаётся неизвестным. Это не runtime high-water.

У browser tester собственные пределы: отправка до 4096 Б, чтение ответа до
16384 Б. Показанные в INFO бюджеты автоматически не меняют эти клиентские пределы.
Сырой ответ сохраняется без числового округления; целые аргументы вне безопасного
диапазона JavaScript отклоняются до отправки. Этот tester не заменяет общий
проверенный MCP/JSON-клиент для всех поддерживаемых прошивкой размеров и типов.
