# Проверки 18 октября 2026

Базовое выделение и smoke-проверка завершены. Это проверка начального компонента,
а не приёмка для эксплуатации и не подтверждение всех ESP32.

Подключенный экспериментальный чип идентифицирован через esptool: ESP32-C3 rev 0.4,
один core, встроенная flash 4 МБ; USB Serial/JTAG на COM5.
Исходная flash считана полностью, 4194304 байта; SHA-256:
`d8ae0fe30ec3664af49b3a45ecaef3d5cfa9391457818a629441ca5ad6548471`.
Резервная копия хранится локально, исключена из Git. Реальный файл и команды
восстановления записываются в игнорируемом `local/hardware.md`.

Исходная разметка: NVS `0x9000..0xe000`, otadata `0xe000..0x10000`,
app0 `0x10000..0x290000`, eeprom `0x290000..0x291000`, littlefs
`0x291000..0x3e1000`. Для C3 пример сохраняет эти границы. При записи не следует
стирать NVS, otadata, eeprom или littlefs.

## Сборка

Использованы PlatformIO Core 6.1.19 / Python 3.13.2, изолированный каталог Core,
платформа Espressif32 **6.10.0**, framework-espidf **3.50400.0 / IDF 5.4.0**,
GCC RISC-V и Xtensa **14.2.0+20241119**. Глобальное окружение не обновлялось.

| ESP32 | compile_check | PASS | не выполнялась |
| ESP32-S2 | compile_check | PASS | не выполнялась |

Первая S3-сборка завершилась внутренним падением GCC в стороннем
`esp_lcd_panel_rgb.c`; повтор с `-j 2` прошёл. Причина сбоя компилятора не установлена,
библиотека ради этого не менялась. Сетевой пример требует встроенного Wi-Fi;
для H2/P4 транспорт предоставляет приложение. Версии IDF вне 5.4.0 не проверены.

## C3

- Запись bootloader, таблицы разделов и приложения проверена esptool по хешам.
  Границы и числовые подтипы исходных разделов данных сохранены; NVS не стиралась.
  Драйвер PHY записал свои калибровочные данные в NVS при запуске — побайтовую
  неизменность NVS после работы приложения не обещаем. Исходная полная копия сохранена.
- Последний boot: `selftest: RESULT passed=13 failed=0 free_heap=248020`.
  Проверены HTTP health/404, URL decode, missing/empty/truncated/valid Basic,
  DELETE auth, частичный POST, лимит тела, WS text 128, пустой text и binary 4096.
  Это значение heap получено до старта Wi-Fi, а не после нагрузочного теста.
- STA подключилась и получила DHCP-адрес; ручной допуск на роутере не понадобился.
  Текущий адрес находится в игнорируемом `local/hardware.md` и serial-логе.
- `tools/smoke_test.py` с компьютера завершился успешно: HTTP, form GET/POST,
  варианты отказа auth и успешный доступ, частичный POST, oversized-body rejection,
  WS text/binary размером 0/1/127/128/256/4096, пять reconnect и HTTP после WS.
- При первоначальном `WIFI_PS_MIN_MODEM` наблюдались сетевые задержки и таймауты.
  После `WIFI_PS_NONE` полный прогон прошёл примерно за пять секунд. Связь с
  энергосбережением — рабочая гипотеза, длительный A/B-тест не проводился.

При отказе от слишком большого тела сервер отправляет 400 и закрывает соединение,
не дочитывая неограниченный ввод. По TCP клиент может увидеть reset раньше ответа;
тест принимает явный отказ/закрытие и затем проверяет работоспособность `/health`.

Сырые логи сборки, прошивки и serial сохранены только в `local/`, исключены из Git.
Исходники выделенного проекта сверены с использованной при сборке копией по SHA-256.
Дополнительно C3 успешно собран заново непосредственно из `каталога проекта до переименования`
с чистым каталогом сборки. Исходники TPMS для этой сборки не использовались;
повторно использован только изолированный кэш инструментов. Лог:
`local/build-independent-c3.log`.

## Ограничения

Не проверены длительная работа, давление на очередь/heap, медленные клиенты,
конкурентный stop/restart и несколько одновременно передающих клиентов. WS-отправка
имеет лимит четыре ожидающих сообщения на клиента и старый `void` API: перегрузка
может приводить к потере сообщения. TLS и авторизованный WS не реализованы.
SSE исключён из сборки; публичный API ещё не стабилизирован. Исходная TPMS-прошивка
не пересобиралась и на новую библиотеку не переключалась.
