# Общий TX: аппаратные проверки и расходы, 02.11.2026

Ветка `feature/unified-tx-scheduler`, основа `4e80b37`, исправления
диагностики/fairness `fd8ebc7` и профиль Showcase, описанный ниже.
Реализация доступна на трёх платах; **предельная смешанная нагрузка приёмку
не прошла**. Короткие успешные повторы не отменяют последующие отказы.
Длительный soak не выполнялся.

Дополнение 03.11: [чистая матрица C3, повторение stress и состояние Pico](readme_20261103_clean_observer_measurements_ru.md).

## Воспроизводимый измеритель

`tools/load/transmission-scenarios.mjs` — ограниченный Node-инструмент для семи
сценариев: idle, rare_api, ws, sse, both, half, stress. Команды и методика:
[инструкция](../tools/load/transmission-scenarios.md).

CPU вычисляется по разности накопленных runtime-счётчиков задач на границах,
без добавления постоянного HTTP-наблюдателя. На RP это нормированная общая
занятость обоих ядер, а не сумма процентов до 200%. Каждый echo учитывается по ID;
после остановки нагрузки допускается ограниченное ожидание последних ответов.
Проверяются размеры ресурсов, незапланированные закрытия, boot identity и рост
TX failures. Затем добавлена SHA-256-проверка каждого ресурса, отдельно проверенная
fixture с повреждением без изменения длины. Дополнительный C3 egress-прогон
10 с: 39/39 ресурсов совпали по SHA-256, TX failures +0, max summary gap 144 мс;
он не заменяет неудачные 30-секундные duplex проверки.
Полученные gzip тела Node уже распаковал: decoded bytes не равны
wire Content-Length. Пропущенный echo или оборванный файл означает FAIL.

Полные JSON и USB-логи находятся только в игнорируемых `local/transmission-bench/`
и `local/unified-hardware/`; в Git они не добавляются. Настройки устройства и
чужие клиенты измеритель не изменяет. Свои потоки закрывает после прогона.

## Практические замеры текущего профиля

В приведённых сериях оставалась старая пользовательская вкладка на каждой плате:
один WS, SSE и HTTP-опрос. Отчёты явно помечены `contaminated`. Это измерения
добавленной нагрузки поверх этой вкладки, **не чистые WS-only/idle сравнения**.
Длительность основной части — 30 секунд плюс завершение уже начатых запросов.

| Плата / добавленная нагрузка | Общий CPU | Данные и задержки | Результат |
| --- | ---: | --- | --- |
| C3: ещё 1 WS, без собственных HTTP/SSE | 13,91% | 301 summary, max gap 132 мс; HTTP counter +49, из них только 3 граничных запроса инструмента | PASS с внешним наблюдателем |
| C3: 2 WS, SSE, HTTP summary 1 Гц, echo 2 Гц/клиент | 20,02% | 29/29 HTTP, 118/118 echo, max RTT 98 мс, max summary gap 143 мс; TX failures +0 | PASS с внешним наблюдателем |
| C3: 3 WS, SSE, 2 непрерывные загрузки JS, без echo | 61,88% | 121/121 JS по 78606 Б gzip (226275 Б decoded), max summary gap 169 мс; TX failures +0 | PASS с внешним наблюдателем |
| C3: тот же bulk + echo 5 Гц/клиент | CPU-граница не получена | 99/101 JS, два timeout; 56 echo остались без ответа, закрытия WS/SSE | FAIL |
| C3: повтор duplex stress | 42,05% за окно со срывом | 67/71 JS, TX failures +10, 52 echo без ответа, max summary gap более 11 с | FAIL |
| RP: 2 WS, SSE, HTTP summary 1 Гц, echo 2 Гц/клиент | 16,90% | 28/28 HTTP, 118/118 echo, max RTT 77 мс, max summary gap 193 мс; TX failures +0 | PASS с внешним наблюдателем |
| RP: 3 WS, SSE, 2 непрерывные загрузки JS, echo 5 Гц/клиент | 38,09% за окно со срывом | 73/75 полных JS; WS 1013, два оборванных файла, TX failures +4, 12 echo без ответа | FAIL |

Первый неудачный C3 duplex-прогон выполнялся отдельно. Последующие строки
C3 repeat и RP stress выполнялись одновременно в общей сети; это дополнительное
внешнее условие, а не строгое сравнение плат. На повторе C3/RP boot identity
не менялась. После остановки перегрузки обе платы отвечали на HTTP.

Ранее два коротких C3 stress-прогона дали 120/129 полных ресурсов без новых TX
failures; они сохранены как наблюдения, но **устойчивость ими не доказана**.
Новый измеритель строже учитывает завершение каждого echo и потока SSE.

Пик payload нашей TX-очереди на текущем C3 был около 7,5 КиБ; это не вся сетевая
RAM. Минимум свободного internal heap в неудачных сериях доходил до 3644 Б.
Этот минимум накопительный за boot, его нельзя приписывать следующему успешному
сценарию. На RP при неудачном stress оставалось более 144 КиБ heap: один лишь
объём свободной памяти не гарантирует отсутствие задержек/перегрузки.

## Что объясняет пилу CPU

Старая страница одновременно получала WS summary 10 Гц, SSE 1 Гц и каждую секунду
снова загружала summary и страницы списка задач по HTTP. Это был реальный
дополнительный трафик, а не только отрисовка в браузере.

В C3-прогоне с одним дополнительным WS из 300 последовательных уникальных
100-мс образцов 40 совпали с ростом HTTP counter: средний CPU в них **47,20%**.
В остальных 260 средний CPU — **8,59%**. Внешняя вкладка дала 46 дополнительных
HTTP-запросов за окно. Это сильная временная связь пилы с пакетами HTTP-опроса;
полное причинное отделение требует повторения после выключения вкладки.

Текущая страница имеет независимые **WS INFO / HTTP 1 Hz / SSE**. По умолчанию
HTTP выключен; при старте запрашивается один снимок, ручное обновление остаётся.
Выключенный поток закрывается и не переподключается. Старой вкладке требуется
обновление, чтобы загрузить эти изменения.

При egress stress C3 распределение общего CPU было таким:

| Задача | Доля CPU, процентных пунктов |
| --- | ---: |
| lwIP `tiT` | 26,81 |
| `wifi` | 15,97 |
| TX | 7,90 |
| HTTP | 7,39 |
| main / сбор и кодирование телеметрии | 2,22 |
| WS | 1,51 |
| SSE | 0,05 |

Ожидание в `QueuedTransport::wait` уже содержит уступку 1 мс при writable native
socket; гипотеза о полностью непрерывном spin без yield не подтвердилась кодом.
Остаются частые проверки готовности/места при настоящем давлении очереди.

## Исправленные расходы и найденные ограничения

- **TX/SSE в простое:** безусловные циклы 1 мс заменены ожиданием сигнала/срока.
  У SSE на наблюдавшихся профилях CPU стал около 0,02–0,05%; первоначально
  наблюдалось несколько процентов. Одновременно менялись оптимизация/клиенты,
  поэтому точный общий выигрыш CPU в процентах не объявляется.
- **Flash assets Showcase:** `sendImmutable` сохраняет явный lifetime массивов
  и убирает payload-копии в TX. В раннем unpaced stress пик TX был 17876 Б,
  после перехода наблюдались примерно 6,5–7,5 КиБ. Скорость и объём нагрузки
  изменились, поэтому это не равный A/B замер общего CPU/heap.
- **Диагностика:** policy timeout/cancel теперь сбрасывает старый native errno;
  иначе новый stall мог ошибочно выглядеть как прежний ECONNRESET. Есть регрессия.
- **Fairness:** каждая четвёртая уступка считается по реальным native write
  попыткам, а не по пустым/отложенным сканам. Причиной всей перегрузки это
  исправление не объявляется.
- **Сроки Showcase/C3:** initial TCP RTO в выбранном SDK — 1500 мс, а прежний
  прикладной stall/frame timeout был 1000 мс. Проверяемый профиль демо использует
  3000 мс для no-progress/WS/TX stall/TX close. Общие defaults библиотеки не менялись.
  Это даёт место одной повторной передаче, не гарантирует восстановление при
  backoff и не устранило весь stress. Close grace может дополнительно удерживать
  владельца за пределами HTTP exchange deadline; жёсткая общая граница 5 с не обещается.
- **Последовательные callbacks:** отдельный WS I/O и общий TX позволяют
  исходящей телеметрии идти параллельно HTTP. Входящие прикладные WS-команды
  всё ещё ждут возврата синхронного HTTP callback. При непрерывных крупных
  ответах это даёт накопление echo и секунды задержки. Это отдельное ограничение,
  не лечится только приоритетом TX. Не вводился повторный вход в callbacks.
- **SDK RAM:** меньше Wi-Fi TX buffers (32→8), меньше TCP send buffer
  (4→2 MSS) не дали устойчивого stress и возвращены к исходным 32/4 MSS.
  `TCP_OVERSIZE_DISABLE` отвергнут проверкой SDK при `NETIF_TX_SINGLE_PBUF`;
  исходники SDK не правились. TCP sndbuf в байтах не равен всей памяти pbuf.
- **Stacks:** C3 TX имеет 3484 Б свободного минимума из 4096 Б — возможный
  резерв после отдельной проверки ошибок/остановки. У HTTP минимум около 1096 Б,
  у main 476 Б: одинаковое уменьшение всех stacks не обосновано. На S3 ранее
  обнаружен реальный overflow HTTP при SSE; увеличены только stacks Minimal,
  последующие SSE/LAN проверки проходят.

## Что остаётся проверить

1. Чистые idle 30 с, rare API 65 с, WS-only, SSE-only, combined после выключения
   внешних вкладок. Попытки idle отвергнуты самим инструментом из-за внешнего WS;
   старый rare-API прогон имел 105 фоновых HTTP и также не принят.
2. Предельный duplex отдельно на каждой плате, с контролем Wi-Fi и ограниченной
   входной частотой. Разделить задержку callback, давление native TCP и закрытия.
   Полная первопричина всех обрывов пока не установлена.
3. Резервы CPU: убрать из повседневного наблюдения дублирующий HTTP; измерить
   более редкие heap/RSSI/task details; сравнить более крупный TX step при
   одинаковой, дозированной нагрузке. Это кандидаты, ещё не доказанный выигрыш.
4. Резервы RAM: проверка уменьшения TX stack; отдельно бюджет pbuf/Wi-Fi.
   Не уменьшать всё по общему heap минимуму.
5. Если частые входящие WS-команды во время длинного HTTP должны иметь малую
   задержку, нужен отдельный этап продолжения HTTP-ответа вне callback либо
   другой явно согласованный callback-контракт. Единая исходящая очередь сама
   по себе этого свойства не обеспечивает.

Проверка физического UI через управление Chrome была остановлена защитой,
поскольку текущий адрес окна не удалось надёжно определить. Страницы пользователя
не изменялись. Браузерный fixture проверен отдельно; чистые измерения требуют
ручного закрытия вкладок или выключения трёх observer-переключателей.
