# Краткий обзор кандидатов JSON

Дата обзора: 2026-10-26. Это чтение закреплённых upstream-исходников и документации, не результат сборки или выполнения тестов. Ни один из рассмотренных кандидатов здесь не подключался к NaWServer и не проверялся на C3. Текущий выбранный для отдельной реализации RapidJSON вне рамок этого обзора.

## LwJSON

- Upstream: [MaJerle/lwjson, commit `bbcf52055fd2f0c935fef3fa09f907de2db349c8`](https://github.com/MaJerle/lwjson/tree/bbcf52055fd2f0c935fef3fa09f907de2db349c8); лицензия репозитория — [MIT](https://github.com/MaJerle/lwjson/blob/bbcf52055fd2f0c935fef3fa09f907de2db349c8/LICENSE).
- Это C-библиотека со статическим массивом токенов и без обязательного выделения heap, но её модель токена хранит преобразованное целое/вещественное значение, а не исходный фрагмент числа ([`lwjson.h`, строки 89–106](https://github.com/MaJerle/lwjson/blob/bbcf52055fd2f0c935fef3fa09f907de2db349c8/lwjson/src/include/lwjson/lwjson.h#L89-L106)). Типы по умолчанию — `long long` и `float` ([`lwjson_opt.h`, строки 59–72](https://github.com/MaJerle/lwjson/blob/bbcf52055fd2f0c935fef3fa09f907de2db349c8/lwjson/src/include/lwjson/lwjson_opt.h#L59-L72)). Парсер накапливает цифры во внутреннем знаковом типе и сам вычисляет вещественное число ([`lwjson.c`, строки 254–339](https://github.com/MaJerle/lwjson/blob/bbcf52055fd2f0c935fef3fa09f907de2db349c8/lwjson/src/lwjson/lwjson.c#L254-L339)). Это не даёт нужной общей конвертации исходных числовых лексем, точной поддержки всего `uint64_t` и double без изменения парсера.
- `lwjson_parse_ex` принимает только корневой объект или массив ([`lwjson.c`, строки 554–593](https://github.com/MaJerle/lwjson/blob/bbcf52055fd2f0c935fef3fa09f907de2db349c8/lwjson/src/lwjson/lwjson.c#L554-L593)); общий контракт также включает корневые примитивы и точные числа.
- **Вывод:** для этой задачи отклонён. Для соответствия контракту понадобились бы изменения хранения токенов и числового пути парсера; это уже отдельная адаптация upstream, а не тонкий backend-wrapper.

## Frozen

- Upstream: [Cesanta/frozen, commit `a42fc3365d7d4e96a5be146b88870dabc794bbc8`](https://github.com/cesanta/frozen/tree/a42fc3365d7d4e96a5be146b88870dabc794bbc8); в репозитории указана Apache License 2.0 ([`LICENSE`](https://github.com/cesanta/frozen/blob/a42fc3365d7d4e96a5be146b88870dabc794bbc8/LICENSE)). Если исходник будет внесён в проект, нужно сохранить предусмотренные лицензией notices и проверить комплект поставки; эта заметка не является юридическим заключением.
- Callback `json_walk` передаёт тип и исходный указатель/длину значения, включая числа ([`frozen.c`, строки 93–107](https://github.com/cesanta/frozen/blob/a42fc3365d7d4e96a5be146b88870dabc794bbc8/frozen.c#L93-L107)). `json_walk_args` возвращает длину разобранного префикса ([строки 780–804](https://github.com/cesanta/frozen/blob/a42fc3365d7d4e96a5be146b88870dabc794bbc8/frozen.c#L780-L804)). Эти API допускают небольшой индекс callback-токенов в caller-owned arena и общие конвертеры чисел; сами по себе они не подтверждают соответствие контракту.
- Неподходящие строгому JSON места в **нетронутом upstream**: числовой разбор допускает hex и ведущие нули ([`frozen.c`, строки 243–274](https://github.com/cesanta/frozen/blob/a42fc3365d7d4e96a5be146b88870dabc794bbc8/frozen.c#L243-L274)); ключи объектов могут быть не заключены в кавычки ([строки 367–376](https://github.com/cesanta/frozen/blob/a42fc3365d7d4e96a5be146b88870dabc794bbc8/frozen.c#L367-L376)); циклы объектов и массивов пропускают завершающую запятую ([строки 278–300](https://github.com/cesanta/frozen/blob/a42fc3365d7d4e96a5be146b88870dabc794bbc8/frozen.c#L278-L300), [396–410](https://github.com/cesanta/frozen/blob/a42fc3365d7d4e96a5be146b88870dabc794bbc8/frozen.c#L396-L410)). Строковый разбор проверяет форму `\\uXXXX`, но не пару суррогатов ([строки 173–192](https://github.com/cesanta/frozen/blob/a42fc3365d7d4e96a5be146b88870dabc794bbc8/frozen.c#L173-L192)); проверка многобайтных UTF-8 определяет ожидаемую длину по старшим битам и не проверяет корректность продолжений, overlong, surrogate или верхнюю границу code point ([строки 208–241](https://github.com/cesanta/frozen/blob/a42fc3365d7d4e96a5be146b88870dabc794bbc8/frozen.c#L208-L241)). `json_walk_args` возвращает позицию сразу после одного значения, поэтому вызывающий должен отдельно проверить оставшиеся байты ([строки 799–804](https://github.com/cesanta/frozen/blob/a42fc3365d7d4e96a5be146b88870dabc794bbc8/frozen.c#L799-L804)). Публичный `json_unescape` не декодирует `\\uXXXX` вне ASCII-диапазона ([строки 845–874](https://github.com/cesanta/frozen/blob/a42fc3365d7d4e96a5be146b88870dabc794bbc8/frozen.c#L845-L874)).
- **Вывод:** отклонён для ночного добавления второй библиотеки. Raw-span callback перспективен, однако соблюдение уже заданного строгого корпуса потребовало бы менять сам парсер и отдельно реализовать проверку UTF-8/суррогатов, NUL с длиной и дубликатов декодированных ключей. Добавлять upstream как есть и компенсировать несовместимости вторым полным парсером нельзя.

## Рекомендация

Добавить только RapidJSON, как выбрано для отдельной реализации. Не добавлять сейчас LwJSON или Frozen: один не сохраняет необходимую числовую точность/лексемы и не принимает корневые примитивы, второй требует форка строгой грамматики и Unicode-пути до принятия общего корпуса. Этот обзор не утверждает, что выбранный RapidJSON backend уже собран, протестирован на C3 или прошёл общий корпус.
