# Лимиты соединений: настройка, резерв и диагностика

Одна вкладка демки — WS + SSE + HTTP polling/загрузка ресурсов. Три тестовые
вкладки плюс открытая страница владельца — четыре браузерных клиента, а число
TCP-сессий может быть больше восьми из-за keep-alive и перекрытия reload.
Состояние существующих страниц нужно учитывать в каждом аппаратном тесте.

[Почему выбран резерв и как работает отказ](adr/ADR_20261019_nawserver_connection-admission-and-reserve.md).

## Где регулируется

| Настройка | Источник | S3 сейчас | Когда применяется |
|---|---|---:|---|
| Общий pool | examples/touch_lcd7/sdkconfig.defaults, CONFIG_LWIP_MAX_SOCKETS |24| Сборка SDK |
| Active TCP PCB | CONFIG_LWIP_MAX_ACTIVE_TCP |32| Сборка SDK; отдельный от sockets предел |
| HTTPD TCP capacity | NetworkPolicy::httpd_connections → ServerOptions::max_connections |21| До server.begin() |
| Служебные сокеты HTTPD | ESP-IDF: listener + два control UDP |3| Не прикладной резерв |
| Резерв ответа об отказе | NetworkPolicy::rejection_reserve |3| Прикладная политика |
| Порог приёма | HTTPD capacity − резерв |18| Вычисляется из политики |
| WS clients | NetworkPolicy::websocket_clients |4| Авторитетная проверка на S3 |
| SSE clients | NetworkPolicy::sse_clients |4| Не выше sse::client_capacity |
| Retry-After | NetworkPolicy::retry_after_ms |2000мс| HTTP503/WS объяснение |

Политика находится в examples/touch_lcd7/main/network.hpp. Библиотечный
ServerOptions по умолчанию сохраняет7; S3 передаёт собственное значение явно.
Профиль не является доказательством поддержки этого числа на C3 или другой плате.
Для другого приложения reserve/admission не включаются автоматически.

Неравенства: HTTPD capacity +3 ≤ LWIP_MAX_SOCKETS; HTTPD capacity ≤ LWIP_MAX_ACTIVE_TCP; 0 < reserve < capacity.
В S3 эти границы проверяются static_assert. Существующий ignored sdkconfig.s3
может сохранить старое значение: изменение defaults само по себе его не заменяет.
После настройки проверить фактический sdkconfig, собрать явно -e s3, записать
прошивку и отдельно проверить многовкладочный сценарий и свободную RAM.

Пул SDK и таблица HTTPD имеют заданные границы, а не расширяются по free heap.
Сейчас UI показывает значения; изменение лимитов через UI не реализовано.
NetworkPolicy можно менять в коде до запуска; общий SDK pool требует пересборки.
Горячую смену capacity работающего HTTPD не обещаем.

## Что видно в runtime

На странице «Плата и дисплей» — «Сеть · лимиты и резерв», а также
GET /api/v2/network (text-key CBOR). Те же данные приходят в summary.network
по HTTP и WS: pool, HTTPD занято/предел/свободные места, reserve, WS/SSE
занято/предел, число и последняя причина отказа, retry_after_ms, captured_ms.

httpd_free означает свободные записи таблицы HTTPD, а не свободные сокеты
всего lwIP и не свободную память. lwIP pool показывается как настроенный предел:
другие компоненты могут пользоваться сокетами вне HTTPD. Текущий диагностический
HTTP-запрос также включён в tcp_open. Выборка обновляется HTTPD-задачей при
запросах и примерно раз в секунду; producer читает только копию.

## Управляемый отказ

- http_reserve: reached admission threshold; сохранить возможность ответа.
- ws_limit: WS клиенты достигли своего предела.
- sse_limit: SSE клиенты достигли своего предела или старый поток ещё закрывается.

Обычный HTTP получает503 с Retry-After и JSON, открытие корня — понятный HTML
без внешних ресурсов. Соединение отказа закрывается. Диагностический endpoint
доступен в резерве и под давлением тоже закрывает своё соединение после ответа.
GET /api/v2/admission?kind=ws|sse позволяет frontend показать причину до потока;
это проверка, не бронь места. Между запросами остаётся гонка, поэтому сервер
повторно проверяет admission на самом подключении.

В используемом SDK нельзя заменить уже выполненный WS upgrade ответом503.
При обходе preflight/гонке WS получает Close1013 и причину. Браузер не раскрывает
тело отказа handshake через WebSocket API; поэтому HTTP preflight нужен отдельно.
SSE frontend явно восстанавливается после503, а не полагается на native retry.
При полном физическом истощении или TCP-клиентах без HTTP гарантии503 нет:
прикладной резерв не заменяет admission на уровне TCP accept.

## Проверка

Сначала измерить baseline /api/v2/network, включая открытую страницу владельца.
`examples/touch_lcd7/frontend/tests/multitab-smoke.mjs` открывает ещё три вкладки,
проверяет адресное WS echo, одновременные HTTP/WS/SSE, повторные reload, принудительный
однократный503 и рост телеметрии. Он не закрывает страницы владельца.
Проверку исчерпания выполнять только в пределах мягкого порога: занять обычные
HTTP keep-alive до первого503, проверить Retry-After/причину и освободить только
тестовые соединения. Не занимать весь pool молчащими raw TCP клиентами.
Успешный build, flash, boot/IP и протокольные результаты — отдельные свидетельства.


При проверке отказа выявлен ещё один независимый предел: при socket pool24
active TCP PCB оставались SDK default16. Новое соединение зависало ещё на TCP,
когда HTTPD показывал16 / 21: обработчик503 не вызывался. После согласования
MAX_ACTIVE_TCP=32 мягкий порог18 должен срабатывать раньше транспортного
истощения. TCP PCB включают также другие активные/закрывающиеся TCP соединения;
состояние TCP stack не равно одному лишь HTTPD client list. На странице платы
оба SDK предела показываются отдельно, без выдуманного глобального free count.
