# Отдельная задача сетевого обслуживания WebSocket

Дата: 2026-11-02. Область: общий TCP backend NaWServer.

## Задача и границы

Синхронная обработка HTTP не должна останавливать отправку уже подготовленных
сообщений существующим WS-клиентам. Для сервера с WS-маршрутами выделяется одна
задача сетевого обслуживания всех его WS-соединений. Отдельных задач на каждого
клиента нет. Native ESP-IDF HTTPD сохраняет собственную модель исполнения.

HTTP worker по-прежнему последовательно вызывает прикладные HTTP- и WS-обработчики.
WS worker обслуживает сетевой ввод/вывод и служебные кадры, но не вызывает
прикладные обработчики. Он не ждёт освобождения блокировки, удерживаемой на время
HTTP-обработчика. Отдельный SSE worker сохраняется.

Это изменение не добавляет потоковый файловый Response и не устраняет целиком
буфер чтения LittleFS в RP-демо. Общий отправитель HTTP/WS/SSE, плавающая гранулярность,
новая абстракция mutex и перестройка CMake являются отдельными изменениями.

## Последовательность и владение

HTTP worker выполняет handshake, opening callback и обработку уже прочитанного
WS-префикса, затем публикует соединение для WS worker. После публикации сетевые
операции соединения выполняет WS worker. Очередь исходящих сообщений остаётся
ограниченной; сообщения владеют своими блоками до завершения или отмены передачи.

Для отложенного входящего вызова используется отдельный буфер размером
`max_message_size`, учитываемый существующим пулом памяти. Пока HTTP worker
обрабатывает сообщение, следующий законченный кадр может оставаться в существующем
буфере декодера. При занятости этих мест чтение приостанавливается: применяется
TCP backpressure, а не молчаливый пропуск команды или закрытие из-за обычной пачки
кадров. Данные прикладного вызова не перезаписываются сетевой задачей.

Приложение получает входящие сообщения последовательно после освобождения HTTP
worker. Поэтому длительный HTTP-обработчик всё ещё задерживает прикладной ответ
на входящую WS-команду. Ping/pong может обслуживаться независимо, пока его чтению
не мешают предшествующие данные того же TCP-потока. Обходить порядок TCP нельзя.

Закрытие согласуется с существующим владельцем квот и памяти: WS worker сначала
прекращает сетевые операции соединения, затем HTTP worker выполняет
последовательное отсоединение клиента от endpoint и освобождение ресурсов. Нельзя
освободить арену QoS, пока другая задача или callback ещё пользуется её данными.
Остановка сервера должна дождаться обеих задач до уничтожения runtime; при
незавершённой очистке зависимости остаются живыми для повторной попытки.

## Ограничения производительности

Само выделение задачи не резервирует полосу Wi-Fi и не гарантирует отсутствие
задержек при переполнении канала. Размеры очередей и сроки передачи остаются
ограниченными. Медленный клиент не должен удерживать общую блокировку на время
сетевого ожидания. Порядок сообщений каждого соединения сохраняется.

Дополнительная память включает стек и служебные данные WS worker, его таблицы
ожидания и по одному буферу `max_message_size` на активное WS-соединение.
Стек новой задачи: ESP-IDF — 4096 байт, приоритет 5; RP — 1536 элементов стека,
6144 байта, приоритет 3, существующая привязка к CPU0. Стандартная частная арена
managed WS увеличена с 12 до 16 КиБ для сообщения максимум 4096 байт. Явно заданные
меньшие лимиты, в том числе сохранённый sdkconfig, автоматически не увеличиваются:
при нехватке памяти upgrade отклоняется с 503 до отправки 101.

Отложенный callback опрашивается HTTP worker с интервалом ожидания до
`wait_ceiling_ms` (по умолчанию 20 мс). Отдельного уведомления о готовом callback
пока нет. Аналогично новая исходящая работа может ждать следующего обхода WS.
Это предел отдельного ожидания, а не гарантия полной задержки доставки.

## Проверка

На Windows/MSVC прошли 55 активных тестов полного набора; добавленный после этого
тест отказов запуска также прошёл (всего 56 различных активных тестов). Три ранее
отключённых теста не включались. После последних изменений проверок отдельно
повторены два новых теста: 2/2 PASS. С отключённым admission — новые тесты 2/2 PASS.

Независимая сборка Linux выполнена существующим Zig/Clang 19.1.7, исполняемые файлы
запущены в локальном WSL Ubuntu: 14/14 профильных TCP/WS/SSE/lifecycle тестов PASS.
При отключённом admission новые worker/lifecycle тесты — 2/2 PASS. Полностью
выключенные WS/SSE/admission также прошли строгую компиляцию трёх TCP translation
units с `-Wall -Wextra -Werror -pedantic`.

Новый тест удерживает HTTP callback заблокированным, пока два WS-клиента получают
24 сообщения и 25 pong. После освобождения HTTP проверяется последовательная
доставка трёх входящих сообщений; отдельно проверяются три кадра в upgrade-prefix,
отказ маленькой арены до 101, остановка с активным WS и занятым HTTP с повторной
очисткой, ошибки запуска обеих задач и отсутствие WS worker у HTTP-only маршрутов.
Измеренный на Windows максимум одного раунда «отправка двум клиентам + два pong»:
31 мс при polling 20 мс и 15 мс при polling 2 мс. Это короткие наблюдения,
не гарантии задержек, измерение скорости большого файла или нагрузочная приёмка.

Сборки микроконтроллеров: RP2350/Pico SDK 2.3.1/FreeRTOS 11.3.3 — BIN 849600 байт;
ESP32-C3/ESP-IDF 5.5.6 — BIN 964544 байта. Устройства в этой задаче не прошивались.
IDF 6.1 не проверен: старый build cache ссылается на отсутствующее Python-окружение.
Для IDF5 переиспользован уже установленный модуль esptool 5.1.0 из локального
tool environment; SDK/пакеты не устанавливались и не изменялись.

Отдельно обнаружено ограничение существовавших до этой задачи изменений
`tests/tcp_transport_integration_test.cpp`: добавленный цикл managed restart
безусловно запускается и при compiled-out admission, где backend закономерно
возвращает Unsupported. В таком профиле весь этот тест FAIL; шесть unmanaged
restart-сценариев перед ним проходят с возвратом учтённой памяти к нулю.
Исходник этого теста оставлен без изменений. В штатном admission-enabled профиле
он проходит полностью.

Локальные журналы: `local/ws-worker-tests/`, `local/ws-worker-noadmission/`,
`local/ws-worker-linux/`, `local/ws-worker-linux-off/`; последние два содержат
независимые проверки. Длительный soak, аппаратные задержки и новая файловая
передача этим отчётом не заявляются.
