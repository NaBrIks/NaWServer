## SSE: поток показаний от сервера к браузеру

Server-Sent Events — длительный HTTP ответ с типом `text/event-stream`. Браузерный
`EventSource` получает текстовые события и умеет переподключаться. Для отправки команды
браузер использует отдельный HTTP запрос. Формат события, например:

```text
id: boot7:42
event: readings
data: {"temperature":23.4}

```

Пустая строка завершает событие. Многострочные данные требуют отдельных строк `data:`;
heartbeat можно передавать комментарием. Для двоичного payload понадобится текстовое
кодирование либо другой транспорт. Эти правила определены в
[стандарте HTML](https://html.spec.whatwg.org/multipage/server-sent-events.html).

`id` и переданный при переподключении `Last-Event-ID` помогают приложению определить
пропуск. Хранение истории и её повторная выдача остаются задачей сервера. Для показаний
часто достаточно последнего snapshot; для событий с обязательной доставкой нужны
bounded history, обнаружение разрыва и явный способ восстановления. После перезагрузки
удобно менять идентификатор эпохи, чтобы старый номер события не означал новую историю.

SSE хорошо подходит для показаний/состояния и отдельных HTTP команд управления. Но
длительный ответ нельзя реализовывать бесконечным циклом внутри обычного HTTPD handler:
он удержит серверную задачу. Будущий adapter должен владеть отдельным async request,
иметь ограниченные очереди, timeout медленного клиента и согласованный shutdown.

Кандидат для исследования — публичные `httpd_req_async_handler_begin/complete`:
исходный callback возвращается, а async request завершается ровно один раз после
остановки отправок. Общая задача транспорта обычно экономнее задачи на каждое
соединение. Неблокирующую отправку и синхронизацию этого adapter ещё нужно реализовать
и проверить; наличие API само по себе не делает старый SSE безопасным.
См. [ESP-IDF HTTP server](https://docs.espressif.com/projects/esp-idf/en/v5.4/esp32c3/api-reference/protocols/esp_http_server.html).

## Что означает защита WS

Есть две отдельные проверки:

1. Допуск соединения до HTTP `101 Switching Protocols`.
2. Допуск конкретной команды или подписки в уже открытом соединении.

Пользователь с правом читать показания не обязательно может менять настройки.
Смена прав, блокировка пользователя и истечение сессии должны влиять и на открытый
WS: нужен отзыв/проверка revision, а не вечная копия прав в момент подключения.

Конструктор браузерного `WebSocket` принимает URL и protocols, произвольный
`Authorization` header через него не задаётся. Для браузера рассматриваются HTTP
вход с session cookie либо короткий одноразовый ticket. Требуются проверка Origin
для cookie-сценария, срок жизни, ограничение попыток и исключение секретов из логов.
Cookie не заменяет проверку прав и CSRF для изменяющих HTTP операций. См.
[стандарт WebSocket](https://websockets.spec.whatwg.org/).

В текущем pinned ESP-IDF native маршрут с `is_websocket=true` делает handshake до
вызова handler: см. `components/esp_http_server/src/httpd_uri.c` в SDK и
`src/http/web_server.cpp`. Поэтому HTTP-декоратор над `onConnect` не способен отказать
до upgrade. Старые auth-декораторы и контейнер удалены. Новый HTTP Route не
регистрирует native WS upgrade, поэтому HTTP middleware не выдаётся за защиту WS.

## Варианты backend

| Вариант | Что даёт | Цена и ограничения |
|---|---|---|
| Проверенный pre-handshake hook в закреплённом backend | Обычный HTTP отказ до 101, единые guards | Нужно подтвердить API и поддерживать версию/patch; не полагаться на случайно изменённый глобальный SDK |
| Отдельный stream adapter на публичных async HTTP API | Контроль auth до собственного upgrade и жизненного цикла | Значительно больше ответственности: framing, mask, fragmentation, control/close, лимиты и совместимость |
| Post-upgrade authentication | Ограниченная неаутентифицированная сессия до первого auth сообщения | Это иной контракт: соединение уже принято; нужны timeout и запрет данных/команд до входа |
| Внешний gateway | Можно централизовать TLS и identity | Появляется внешняя зависимость и отдельная граница доверия |

Предварительно предпочтителен первый вариант, если удастся закрепить небольшой
поддерживаемый adapter/hook. Самостоятельный RFC6455 engine ради одной проверки не
следует выбирать без оценки готовых компонентов и затрат сопровождения. Ни один
новый вариант здесь ещё не реализован или измерен.

## Общие требования к realtime

- Различать `Accepted`, `QueueFull`, `Closed`, `TooLarge`, ошибку выделения и доставку.
- Ограничивать клиентов, payload, pending на клиента и общий объём очереди.
- По решению владельца timeout или индивидуальный overflow заканчиваются close; специальные slow-client режимы ядру не нужны.
- До `httpd_stop` прекратить producers, завершить/cancel транспортные операции и
  освободить их память. Не уничтожать заимствованные handlers раньше этого.
- Для auth проверять допуск до передачи чувствительных данных, затем каждую команду
  и изменение подписки; тестировать отзыв и смену прав во время соединения.

HTTP Basic в нынешнем примере использует публичную тестовую пару. Base64 не шифрует
credentials: защита канала — отдельная задача HTTPS/TLS или доверенного gateway.
Новый credential store должен хранить salt/verifier, а не открытый пароль; это также
не заменяет защищённый канал. См. [RFC 7617](https://www.rfc-editor.org/rfc/rfc7617).
