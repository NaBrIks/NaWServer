# Резерв соединений и явный отказ при перегрузке

Дата: 2026-10-19. Статус: принято по прямому запросу владельца.
Дополняет ADR_20261018-3_nawserver_local-device-limits.md; числовой профиль ниже
относится только к самостоятельному S3 примеру, не ко всем ESP32.

## Контекст

Три вкладки демки держат три WS и три SSE, дополнительно используя HTTP polling
и browser keep-alive пулы. SDK default HTTPD=7 при lwIP=10 оставлял только одно
место сверх шести постоянных потоков. Проверка воспроизвела зависающие WS/HTTP.
Подсчёт вкладок не равен подсчёту TCP-сессий. Страница владельца остаётся открытой
во время тестов и также расходует реальные места.

При полностью занятом пуле нельзя принять очередной TCP-запрос и гарантированно
отправить ему HTTP-объяснение. Увеличение физического лимита без admission и
резерва переносит проблему, но не определяет поведение при достижении предела.

## Решение

1. Разделить общий пул сокетов lwIP, предел активных TCP PCB, таблицу HTTPD,
   резерв для отказа и ограничения WS/SSE. Общий пул — compile-time верхняя
   граница; ServerOptions::max_connections задаётся до begin(). Для S3 выбор
   политики сосредоточен в main/network.hpp, SDK pool в sdkconfig.defaults.
2. Текущий профиль S3: sockets24, active TCP PCB32, HTTPD21, три служебных сокета HTTPD;
   внутри21 зарезервировать ещё3 для ответов об отказе, порог admission18.
   WS4 и SSE4 — отдельные ограничения, не число доступных TCP-сессий.
3. На уровне приложения новые запросы при достижении мягкого порога получают
   HTTP503 + Retry-After + объяснение. Корневая навигация получает автономный
   HTML, API — JSON. Отказ закрывает своё соединение, не оставляя его keep-alive.
   Диагностика доступна в резерве и при перегрузке также освобождает соединение.
4. WS frontend сначала получает HTTP admission. Проверка не резервирует место:
   между ней и upgrade возможна гонка. Авторитетная проверка остаётся на сервере.
   В ESP-IDF5.4 используемый WS callback вызывается после handshake; при обходе
   preflight или гонке сервер закрывает WS кодом1013 с причиной. Не заявлять,
   что callback способен отклонить upgrade HTTP503 до handshake.
5. SSE admission возвращает объяснённый503. EventSource после такого ответа
   может прекратить попытки: frontend явно повторяет с задержкой1..10с;
   ручное отключение/уход со страницы отменяет таймер. Аналогично WS повторяет
   admission с задержкой. Ограничения не обходятся бесконечным ростом очередей.
6. Показывать текущие HTTPD/WS/SSE, пределы, резерв, число/последнюю причину
   отказа и время выборки. HTTPD session list перечисляется только на его задаче;
   producer читает копию. Максимум одно задание выборки ожидает в HTTPD queue.
7. Не вытеснять работающий WS/SSE случайным LRU ради нового клиента.

## Последствия и пределы

Резерв не является защитой от SYN flood, клиентов, открывающих TCP без HTTP,
или произвольного одновременного всплеска сверх физического пула. Application
admission срабатывает после принятия TCP/разбора запроса; при полном физическом
истощении транспорта HTTP-ответ принципиально не гарантирован. Для штатных
браузерных запросов резерв позволяет отдать управляемый отказ и восстановиться.

Дефолт active TCP PCB16 способен остановить TCP раньше HTTPD21; общий pool
сокетов и TCP PCB обязательно согласуются независимо.

Политика не вычисляется из free heap и не раздувается автоматически. Изменение
пула lwIP требует пересборки. Изменение HTTPD capacity требует перезапуска
сервера; S3 выбирает её статически при сборке. WS/SSE значения должны укладываться
в транспортные/библиотечные верхние границы. Точные значения и способы проверки
приведены в ../readme_connection_limits_ru.md. Реальные результаты приёмки
поддерживаются в руководстве S3, а не дописываются в это решение.

## Отклонённые варианты

- Заполнить все места и затем пытаться объяснить отказ: нет сокета для ответа.
- Только увеличить pool: нет определённого admission/восстановления.
- Считать три вкладки тремя TCP-сессиями: игнорируются SSE/WS/HTTP keep-alive.
- Универсальный подсчёт устройств по IP/cookie: не решает транспортный предел.
- Динамический бесконечный pool/сложный slow-client QoS: против локального scope.
