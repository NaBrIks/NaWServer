# Статическая композиция и новый API без legacy-совместимости

Дата: 2026-10-18. Статус: принято по прямому уточнению владельца.
Реализация нового API ещё предстоит; этот документ фиксирует её требования.

## Контекст

Владелец хочет собирать приложение статически в C++ коде, задавать доступ отдельно
для маршрутов, выбирать фичи и backend при сборке и при необходимости менять
пользователей и роли во время работы устройства. Он явно отменил требование
совместимости старого middleware: «совместимость не обеспечиваем».

Ранее review предложил рассмотреть временный legacy adapter. Этот вариант не принят.
Review остаётся неизменным снимком исследования; текущая директива задаётся этим ADR.

## Решение

1. **Статическая композиция — обязательный поддерживаемый способ использования.**
   Приложение может объявить объекты, таблицу routes, таблицу известных permissions,
   guards и ссылки на providers заранее в коде. Для этого не нужны runtime builder,
   service locator, выделение каждого handler через new или изменяемый список routes.
   API не должен требовать owning std::function для обычного статического callback.

2. **Доступ привязан к операции.** Method/path, endpoint и политика public /
   authenticated / required permission могут быть неизменяемыми descriptors.
   Новый API должен маршрутизировать по metadata до чтения body. Это освобождает
   реализацию от поддержки старых body-dependent canHandle predicates.

3. **Роли и пользователи — данные.** Прошивка фиксирует каталог операций и permissions.
   Фиксированный профиль использует const таблицы. Динамический профиль допускает
   ограниченные изменения имён ролей, назначений, enabled/revision и наборов известных
   permissions. Эти изменения не требуют runtime генерации кода или новых handlers.
   Dynamic RBAC остаётся опцией, а не обязательной стоимостью публичного HTTP сервера.

4. **Пределы ресурсов известны.** Число users/roles/sessions/jobs и размеры payload
   ограничиваются конфигурацией. Изменяемые данные могут находиться в статических
   массивax/пулах; слово dynamic не требует неограниченных контейнеров или malloc.
   При исчерпании ресурсов возвращается явная ошибка. Изменение прав публикуется
   согласованно, с revision и влиянием на уже открытые sessions/subscriptions.

5. **Конструирование отделено от запуска.** Constructors связывают зависимости и
   сохраняют descriptors. Storage load, Wi-Fi, tasks, HTTPD start и другой I/O выполняются
   явно после необходимой инициализации SDK, с проверяемым результатом. Глобальный
   static объект с побочными эффектами не равен constant initialization.

6. **Новый middleware API без совместимых обёрток.** Маленькие route guards, небольшой
   request context и явный результат continue/reject/error. Наблюдение завершения,
   transport invariants и прикладной handler имеют отдельные роли. Не переносить
   старые handleUpload/handleBody/isRequestHandlerTrivial и decorator forwarding
   ради совместимости. Полный произвольный next pipeline не является исходным требованием.

7. **Подмена и статическая сборка совместимы.** Нужные границы можно выражать узкими
   C++ abstract interfaces либо конкретными типами. Provider передаётся ссылкой/
   не владеющим handle и может иметь статическое время жизни. Virtual dispatch
   не требует фабрики, new или включения всех реализаций в firmware. Kconfig/CMake
   выбирают только нужные исходники и SDK dependencies.

8. **Миграция ограничена независимым проектом.** Примеры проект до переименования переводятся на
   новый API вместе с реализацией. Основной TPMS остаётся на своей in-tree версии
   до отдельной команды владельца. Legacy-совместимость нового компонента для него
   не является требованием.

## Следствия и ограничения

Статические descriptors могут лежать в read-only памяти, runtime auth state требует
RAM и, если выбрано, persistence. Для фиксированных и динамических профилей используется
один принцип проверки прав; отключаемые modules не навязывают storage/crypto всем.

Статическое владение объектами не является обещанием нулевого heap у всей прошивки.
Текущий adapter, HTTPD/lwIP и SDK используют динамические ресурсы. Требование zero-heap
для конкретного участка требует отдельного контракта и измерения. Для нового API
важны возможность статической композиции и предсказуемый bounded runtime footprint.

Init order и constructors описаны в
[ESP-IDF startup flow](https://docs.espressif.com/projects/esp-idf/en/v5.4.2/esp32/api-guides/startup.html).
Глобальные C++ constructors вызываются до app_main; их наличие само по себе не
подтверждает готовность прикладных storage/network dependencies.

## Отвергнутые варианты

- Сохранять legacy adapter и старые callbacks ради обратной совместимости.
- Требовать runtime route registration, DI container или heap factory для обычного приложения.
- Считать изменяемые роли несовместимыми со статическим размещением ограниченных таблиц.
- Загружать storage или запускать сервер скрытым побочным эффектом глобального constructor.
- Объявить весь SDK zero-heap только потому, что server/handlers объявлены static.

Имена новых типов, wire format записей, KDF, protected WS backend и точная реализация
синхронизации остаются отдельными задачами. Этот ADR не объявляет их реализованными.
