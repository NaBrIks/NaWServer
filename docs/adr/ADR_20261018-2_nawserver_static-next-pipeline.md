# Статический next pipeline и плоские обработчики ресурсов

Дата: 2026-10-18. Статус: направление выбрано владельцем после сравнения вариантов.
Новый middleware engine пока не реализован.

## Контекст

Владелец предпочёл pipeline с next(), возможность цепочек разной глубины и сохранение
плоской наглядной раздачи ресурсов из памяти, filesystem и прикладных источников.
Требования статической композиции и отсутствия legacy-совместимости остаются в силе.

Этот ADR заменяет рекомендацию ограничиться guards-only engine в пункте 6
ADR_20261018_nawserver_static-composition-and-clean-api.md. Остальные ограничения того
решения сохраняются. Guards и route policies остаются возможной логикой внутри
pipeline, а не отдельным взаимоисключающим transport engine.

## Решение

1. Middleware вызывается как before/next/after pipeline. Route policy остаётся
   декларативной metadata: public, authenticated либо required permissions.
   Authentication/authorization middleware читает policy выбранного маршрута.

2. Поддержать статические цепочки разной длины, включая пустую. Предпочтительная
   простая форма — Chain<N> с фиксированным массивом non-owning MiddlewareRef и общим
   исполнителем. Типы callbacks адаптируются при сборке; runtime route builder,
   owning std::function, heap allocation на каждый middleware/request не обязательны.
   Variadic typed chain возможен позднее при доказанной пользе; не требовать отдельного
   полного engine instantiation для каждого endpoint и набора типов.

3. Next действует только в текущем вызове, вызывается не более одного раза и не
   сохраняется для отложенного вызова. Middleware может вернуть результат без next.
   Результат, начатый ответ и право завершить ответ имеют явный контракт. Отложенный
   transport handoff должен быть отдельной операцией с управляемым временем жизни;
   он не реализуется сохранением ссылки на Next/stack Context.

4. Простые static-memory/text/binary/gzip/file/source handlers сохраняют плоский API.
   Публичный ресурс не требует ручной auth-обёртки или chain. Несколько маршрутов могут
   использовать одну цепочку и общие неизменяемые middleware instances; данные конкретного
   запроса находятся в Context, а не в mutable fields общего объекта middleware.
   Неподдержание старых имён/ABI не отменяет требование удобства и эквивалентных функций.

5. Источник данных, политика доступа и исполнение передачи разделены. Embedded
   resources заимствуются с определённым временем жизни, file provider читает порциями,
   mount и выбор FS принадлежат приложению. MIME, Content-Encoding и длина задаются
   явно. Не загружать весь большой файл в RAM ради унификации интерфейса.

6. Preemptive FreeRTOS и async transport рассматриваются раздельно. В нынешнем backend
   обычный static HTTP handler и queued WS transmit исполняются одной HTTPD task.
   Producer WS send копирует/ставит job и возвращается, однако queued transmit ждёт
   освобождения HTTPD task. Чтение/запись сокета может блокировать эту задачу; другие
   готовые FreeRTOS задачи при обычном ожидании продолжают работать.

7. Маленькие ресурсы могут иметь простой синхронный fast path. Для долгой передачи
   требуется ограниченный async-request/worker либо continuation design, если тесты
   показывают неприемлемую задержку HTTP/WS. Цикл send_chunk или vTaskDelay внутри
   одного handler сам по себе не возвращает управление циклу HTTPD.

8. Для пользовательской публикации данных определить bounded queue/pool и явный
   результат постановки: accepted/full/closed/too-large/error. Принятие в очередь
   отделено от передачи в сокет и получения клиентом. Медленные клиенты имеют limits,
   timeout и явную политику drop/coalesce/disconnect в зависимости от типа данных.

## Следствия и проверки

next() не создаёт задачи, coroutine или сетевую параллельность. Синхронный возврат
из handler не равен завершению SSE/WS lifetime или доставке данных клиенту. Для
долгих передач нужен отдельный completion contract. Stop/cancel должен завершать
операции до уничтожения заимствованных ресурсов.

В проверенном исходнике original consumer явно использует embedded text/binary/gzip
handlers. Готовый filesystem-serving handler в проверенных handler_static.* не найден;
полноценную FS возможность следует проверить/реализовать отдельно, не приписывать
наличие готовой реализации ссылке на FS в комментарии. Новый API должен её поддержать.

Проверять на C3 одновременно: загрузку страниц/FS, частую публикацию WS, несколько
клиентов, медленного читателя, заполнение очереди и disconnect/reconnect. Измерять
задержку producer call, задержку до получения клиентом, состояние очереди и heap.
Требуемые численные пределы latency ещё не заданы; текущие smoke tests не доказывают
их выполнение. Нагрузочная проверка остаётся ближе к концу после реализации/демо.

Сведения о native server task и async handlers:
[ESP-IDF HTTP Server](https://docs.espressif.com/projects/esp-idf/en/v5.4.2/esp32c3/api-reference/protocols/esp_http_server.html).
В текущем SDK также проверены httpd_main.c: httpd_process_ctrl_msg и httpd_ws.c:
httpd_ws_send_frame_async; последний выполняет socket send непосредственно.

## Отклонённые варианты

- Исключить next() только на основании того, что целевая платформа — MCU.
- Сделать сложную цепочку обязательной для обычного публичного static resource.
- Считать queued WS send гарантией немедленной передачи независимо от занятости HTTPD.
- Переносить управление сетью/FS mount в middleware ядро.
- Создавать неограниченную задачу/очередь для каждого запроса или клиента.
