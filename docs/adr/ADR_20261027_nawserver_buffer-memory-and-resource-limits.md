# Память буферов и жёсткие пределы ресурсов

Дата: 2026-10-27. Принято по прямому поручению владельца.

## Решение

Публичная библиотека не знает о LCD, конкретных демках, Wi-Fi настройках и
пользовательской автоматизации. Приложения выбирают её настройки.

1. Две группы принадлежащего библиотеке хранилища: TCP HTTP/WS и SSE frames.
   Для каждой задаются allocator и жёсткий предел суммы запрошенных байтов.
   Размеры буферов, таблиц и незанятой части пулов учитываются при резервировании,
   до вызова allocator. Метаданные allocator, небольшие управляющие объекты,
   стеки и память ОС/SDK не входят в этот показатель.
2. Обычный allocator остаётся начальным выбором. В ESP-IDF отдельно доступны
   system, internal-only, PSRAM-only, prefer-internal и prefer-PSRAM.
   Строгие варианты не переключаются на другую память. Предпочтение означает
   разрешённый fallback. Kconfig задаёт defaults; параметры экземпляра — override.
   Общие заголовки не включают ESP-IDF. На Windows/Linux и других платформах
   используется системный или предоставленный пользователем allocator.
3. Конструкторы не выделяют крупные буферы. Буферы создаются при явном start;
   отказ старта откатывает выделения. Неуспешный stop сохраняет ресурсы для retry.
   JSON/MCP продолжает использовать caller-owned workspace; нового скрытого
   allocator и зависимости от выбранной JSON-библиотеки нет.
4. Ограничения соединений, WS/SSE клиентов, HTTP headers/body, размеров сообщений,
   индивидуальных и общих очередей и сроков передачи проверяются явно.
   Переполнение ресурсов возвращает отказ, не расширяет память и не создаёт
   неограниченный backlog. Число клиентов не подменяет число сокетов.
5. Ограничение памяти библиотеки не является ограничением всей RAM устройства.
   Системная сеть и обработчики приложения расходуют собственную память.
   Нужны одновременно счётчики библиотеки и замеры internal/PSRAM устройства.
6. REST-автоматизация — самостоятельный обычный профиль: 1/2/3 клиента,
   ограниченные последовательные запросы с заданной периодичностью. Посещение
   UI — отдельная загрузка ресурсов и проверка состояния. Повторный reload,
   частые команды и превышение лимитов относятся к перегрузке, не к обычной приёмке.

## Границы

Не изменять глобальный malloc, настройки SDK Wi-Fi/lwIP и размещение стеков
за пользователя. Не вводить allocator на каждый мелкий объект, универсальную HAL,
автоматическую адаптацию QoS или скрыто растущие очереди.
Native HTTPD продолжает владеть своим HTTP/WS хранилищем: настройка TCP buffer
не управляет его внутренностями. Настройка SSE frames применяется к обоим backend.

Прежний [ADR о локальных лимитах](ADR_20261018-3_nawserver_local-device-limits.md)
дополняется этими группами памяти и отдельной REST-приёмкой.
