# Локальный контроллер: жёсткие лимиты и отключение медленного клиента

Дата: 2026-10-18. Статус: принято по прямому уточнению владельца.
Реализация конфигурации и transport изменений ещё предстоит.

## Контекст

Типичный сценарий — локальная сеть и настройка с телефона, ориентир 2–4 клиента.
Владелец предпочёл отключать отстающего клиента, не создавать для него специальные
режимы обслуживания. Предложение о сложных политиках slow-client из прежней IDEA
не принимается как требование ядра.

## Решение

1. Простой bounded профиль. Лимиты задаются явно в статической конфигурации кода;
   Kconfig/CMake отвечают за состав фич и compile-time верхние границы. Изменение
   limits на работающем сервере не является исходным требованием.

2. Предусмотреть maxConnections, maxWsClients, frame/body bytes, pending на клиента,
   общий memory/job budget, ожидание socket write и максимальную длительность ответа.
   Не раздувать API десятками механизмов адаптации. Ориентир WS-клиентов по умолчанию
   4 с возможностью выбрать 2; точные сетевые/памятные значения проверить на C3.

3. TCP connections и устройства не равны. Один браузер может держать несколько HTTP
   соединений и WS; не вводить сложный подсчёт физических устройств по IP/cookie ради
   лимита «4 клиента». maxConnections и maxWsClients — отдельные понятные limits,
   согласованные с native HTTPD/lwIP и зарезервированными сокетами SDK.

4. Превышение timeout, зависшая передача либо переполнение индивидуальной очереди
   заканчиваются закрытием соединения и освобождением его ресурсов. При полном
   лимите новых соединений новые клиенты отклоняются. Producer не ждёт, пока
   получатель догонит; возвращает явный результат отказа/закрытия/переполнения.

5. Основной transport не реализует специальные медленные очереди, автоматическую
   историю/replay, универсальные adaptive QoS, per-client tasks или автоматический
   coalescing. Доменная потребность последнего snapshot, если появится, остаётся
   отдельной явной функцией приложения. Команды и ответы не теряются молча.

6. Повторное подключение — обычное новое соединение, не вечный ban. Под «отключить»
   понимается завершить текущую сессию; постоянная блокировка пользователя/IP не
   запрошена. Новое соединение снова проходит обычную политику доступа.

7. Отдельный worker pool для файлов не вводится по умолчанию ради редкого клиента.
   Маленькие ресурсы используют простой fast path. Если смешанная нагрузка покажет
   неприемлемые задержки при нормальных клиентах, исполнение долгих передач обсуждается
   по измерениям. Queue сама по себе не гарантирует отсутствие блокировки HTTPD.

## Следствия

Socket wait timeout и total response deadline — разные пределы: понемногу передающий
клиент может избегать отдельного no-progress timeout. Абсолютный deadline должен
проверяться в bounded transport steps; не считать его реализованным внешним guard
вокруг непрерываемого долгого send. Фактическая задержка закрытия ограничена backend
возможностями и проверяется тестом.

Переполнение общей очереди из-за занятости самого сервера нельзя автоматически
приписывать конкретному клиенту. Не добавлять сложную диагностику в пользовательский
flow: достаточно ограничений, явных результатов и небольших счётчиков/логов.

Сохранить один pipeline engine для typed Chain, makeChain и FixedChain. Политика
лимитов принадлежит transport/server и одинакова для всех фасадов.

## Проверки

На C3: нормальная загрузка UI и WS при 2 и 4 клиентах, читатель с искусственным
ограничением/полной остановкой чтения, достижение лимита соединений, индивидуальной
очереди и общего budget, корректное освобождение при disconnect/reconnect/stop.
Проверить, что producer не ждёт медленного клиента и память не растёт. Значения
таймаутов сначала задаются конфигурацией, затем уточняются по результатам.

## Отвергнутые направления

- Обслуживать долго отстающего клиента отдельными растущими ресурсами.
- Вводить полноценный интернет-серверный QoS/replay framework в транспортное ядро.
- Считать четыре телефона четырьмя TCP sockets.
- Добавлять permanent IP/user ban как побочный эффект сетевого timeout.
