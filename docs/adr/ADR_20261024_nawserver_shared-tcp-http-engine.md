# Общий HTTP-движок поверх TCP и выбор IDF HTTPD

Дата: 2026-10-24.
Статус: принято направление по прямому поручению владельца; реализация предстоит.

## Основание

Владелец выбрал общий собственный HTTP-движок для Windows, Linux и ESP32,
сохранив на ESP32 альтернативный backend через `esp_http_server` ESP-IDF.
Поддержка должна охватывать IDF 5 и 6. Экономия отдельных байтов не является
целью; расходы в килобайтах Flash/RAM должны быть видимыми и обоснованными.
В собственном коде необходимо избегать лишних копирований и выделений памяти.

Это решение заменяет ограничение «только ESP-IDF backend» из
[ADR о границах компонента](ADR_20261018_nawserver_component-boundary.md)
только в части платформ и транспорта. Прикладные границы, статическая композиция,
явный lifecycle и [локальные лимиты](ADR_20261018-3_nawserver_local-device-limits.md)
сохраняются. Универсальная HAL, управление Wi-Fi и продуктовые сервисы не вводятся.

## Решение

1. Сохранить `HttpBackend / HttpExchange / HttpRequestHandler` как границу между
   транспортной реализацией и общим dispatcher/маршрутами/middleware/Response.
2. Добавить собственный TCP HTTP backend с общей обработкой HTTP wire protocol
   и WebSocket. Переиспользовать существующие SSE encoder/Sessions/bridge.
3. Под ним выделить узкий интерфейс TCP: listener, accept, частичное чтение/запись,
   ожидание готовности, shutdown/close, нормализованные результаты и ошибки.
   Реализации: Winsock, Linux sockets, ESP-IDF lwIP BSD sockets.
4. `EspIdfHttpBackend` продолжает использовать native HTTPD. Он не должен быть
   обёрнут новым TCP-слоем: сокетами этого пути владеет HTTPD.
5. Выбирать backend при сборке и статической композиции. В TCP-only прошивке
   NaWServer не требует и не линкует HTTPD, его WS/SSE adapters и native facade.
   Если HTTPD требует другой компонент приложения, это отдельная зависимость:
   NaWServer не обещает удалить чужую зависимость.
6. Общие публичные HTTP/WS/SSE заголовки не включают platform SDK. Конкретные
   backend headers остаются явными. Приложение инициализирует сеть до `begin()`.
7. Работать с ограниченными буферами и представлениями данных. Копии допустимы
   при необходимости владения, преобразования или независимого времени жизни.
   Каждая крупная копия и динамическая аллокация должна иметь владельца, предел,
   срок жизни и объяснение. Не заменять безопасное владение висячими указателями.
8. Синхронный Response заимствует данные до возврата send; отложенный WS/SSE
   сохраняет owned данные. `Queued` не означает доставку. Полный zero-copy или
   zero-heap всей прошивки не обещается.
9. Сравнивать варианты на C3 при одинаковых функциях, конфигурации и нагрузке;
   публиковать Flash, static RAM, heap, стеки и память соединений. Меньший размер
   собственного движка — проверяемая гипотеза, а не следствие абстракции.

## Границы решения

IDF/lwIP/ОС остаются зависимостями. Отказ от HTTPD не означает собственный TCP/IP,
Wi-Fi или TLS. HTTPS, keep-alive, streaming upload, защищённый WS и новый async
HTTP API не становятся автоматически реализованными или обязательными для
первого этапа. Поддержка IDF 5/6 подтверждается конкретными версиями, а не одним
`#if ESP_IDF_VERSION_MAJOR`.

Владелец разрешил полную программу тестирования; текущая задача — исследование
и документация без изменения исходного кода. Linux-проверки можно выполнять
отдельным ограниченным процессом на машине с ioBroker. Полные stress/fuzz/OOM
проверки выполняются на изолированном Linux стенде; условия совместного размещения
и прекращения теста указаны в плане. Этот ADR не требует изменения ioBroker.
