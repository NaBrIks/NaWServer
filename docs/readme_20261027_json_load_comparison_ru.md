## JSON: воспроизводимая база сравнения

Физическая C6, IDF 5.5.6, GCC 14.2, 160 МГц, `-Og`, main stack 8192 Б,
без Wi-Fi/LCD. Шесть документов × 200 = 1200 разборов.
Общий writer вне таймера. Все размеры ниже — байты.

| Reader | Полный BIN теста | Разница BIN к bounded | Арена резерв / наблюдаемый пик | Время, мс |
|---|---:|---:|---:|---:|
| bounded | 285408 | 0 | 2048 / 1016 | 334,462 |
| yyjson | 400528 | +115120 | 16384 / 4216 | 243,340 |
| RapidJSON SAX | 295296 | +9888 | 8192 / 2126 | 347,419 |

Арена — только рабочая память reader, не вся RAM/стек приложения.
Пик относится к этому корпусу, а не ко всем допустимым документам.
Скорость относится к закреплённым исходникам/опциям, не является общим рейтингом.

## Нагрузка: каждый этап по 4 часа

Только TCP + bounded. Четыре логических клиента: 2 WS + 2 SSE,
HTTP pool до 3 соединений; шаг 250 мс/клиент, HTTP header deadline 2 с,
WS echo deadline 3 с. Reload постоянно скачивает JS/CSS; cached скачивает
их один раз, затем читает summary. Пользовательские фоновые соединения оставлены:
для C6 с registry 7 / sockets 10 это дополнительное давление на соединения.

| Плата / профиль | HTTP ответов | Завершённых точных WS echo | SSE событий | Ошибок / таймаутов | Перезагрузок | Восстановление health/info |
|---|---:|---:|---:|---:|---:|---|
| C6 reload | 135205 | 46776 | 28798 | 2045 / 2029 | 0 | 200 / 200 |
| C6 cached, наблюдение | 235407 | 78888 | 28798 | 2139 / 2134 | 0 | 200 / 200 |
| S3 cached, наблюдение | 247068 | 108910 | 28241 | 1354 / 1346 | 0 | 200 / 200 |

Cached-контроль на 60 секунд не прошёл: C6 — 2 dial timeout, S3 — 1.
Дальнейшие четыре часа были диагностическим наблюдением и этот отказ не отменяют.
WS-счётчик учитывает только успешные завершённые обмены; равенство sent/received
не доказывает отсутствие потерь всех попыток. Общий знаменатель для процента ошибок
разнородных HTTP/WS/SSE операций здесь не определён.

|---|---:|---:|---:|
| C6 reload | 118780 | Отдельно не сопоставляется со следующим boot | — |
| C6 cached | 108960 | 184928 | 151552 |

У S3 оставалось около 5,46 МБ PSRAM, но она не заменяет internal RAM Wi-Fi/TCP.
После завершения память вернулась; устойчивое монотонное падение не установлено.
Это не доказательство отсутствия любых утечек.

Рекомендуемый порядок дальнейшей работы:

1. Увеличить измеренный запас internal RAM S3, установив владельцев пиковых выделений.
2. Устранить длительное занятие общего HTTP/WS обработчика при отправке HTTP.
   Найден риск задержек в коде, но не каждый timeout локализован: остаются RF и лимиты сокетов.
   Не вызывать WS callback повторно из HTTP write: приложения используют общие буферы.
3. После изменения повторить тот же профиль и короткий контроль, затем отдельную ночную нагрузку.
   Сравнивать те же SDK, ELF/config, фоновые соединения, таймауты и показатели RAM.

После ночи оставлены обычные TCP + bounded + MCP: C6 `192.0.2.1`,
S3 `192.0.2.2`. Это зафиксированное финальное состояние прогона, не новая
проверка доступности на момент чтения отчёта. Наши нагрузочные процессы завершены,
эксперименты выключены, автоматизация удалена. Окружение не обновлялось.
