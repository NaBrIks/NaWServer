# Статические ресурсы, отказы WebSocket и доступность функций

Текущий контракт после изменений 19 октября 2026. Только библиотека NaWServer;
лимиты рассчитаны на локальное устройство, без повторных очередей и worker pool.

## MIME статических ресурсов

Текстовый обработчик по умолчанию сохраняет `text/html`. Бинарный теперь
использует `application/octet-stream`; для HTML из бинарного массива нужно
передать `text/html` явно. Это изменение прежнего поведения бинарного обработчика.
MIME передаётся после длины данных, а для binary необязательный gzip идёт за MIME:

```cpp
static constexpr char css[] = "body{margin:0}";
static HandlerStaticUriText style("/style.css", css, sizeof(css) - 1, "text/css");
// app_gzip — готовый gzip-массив, который живёт не меньше обработчика.
static HandlerStaticUriBin script("/app.js", app_gzip, sizeof(app_gzip),
                                 "text/javascript", true);
```

MIME описывает исходный ресурс, gzip — его кодирование; для сжатого JS нужны
`Content-Type: text/javascript` и `Content-Encoding: gzip`. Распаковки и определения
MIME по расширению библиотека не делает. Данные и строка MIME заимствуются и должны
жить не меньше обработчика. `nullptr`, пустой MIME и CR/LF отвергаются Response до
передачи; нужно исправить конфигурацию, повторять такой send бессмысленно.

## Что означает результат WS-отправки

`WebSocketClient::send` и `send_binary` возвращают `WebSocketSendResult`:

| Результат | Значение и действие приложения |
|---|---|
| `Queued` | Данные скопированы в очередь адаптера (HTTPD на ESP32). Это не доставка и не ACK. |
| `Closed` | Сессия закрыта; прекратить отправки. Не сохранять указатель клиента. |
| `InvalidArgument` | `send(nullptr)` либо binary с nullptr и ненулевой длиной. Исправить вызов. |
| `TooLarge` | Больше WebSocketLimits::max_message_size (default4096). Уменьшить сообщение или задать собственный протокол частей. |
| `QueueFull` | Достигнут max_pending_messages (default4), включая исполняемое. Не ждать и не крутить retry-цикл. |
| `NoMemory` | Не выделено задание или копия payload. Уменьшить нагрузку, учитывать отказ. |
| `QueueError` | HTTPD не принял задание. Проверить состояние приложения/сервера, учитывать отказ. |

Пустой binary (`nullptr, 0`) допустим. Для broadcast возвращается небольшая
`WebSocketBroadcastResult { queued, rejected, first_error }`. Счётчики относятся
к получателям этой попытки; `first_error` значим только при `rejected != 0`.
При отсутствии клиентов оба счётчика равны нулю, отправлять и проверять нечего.
Список результатов по клиентам не выделяется. Повтор всего broadcast после частичного
успеха продублирует сообщение для клиентов, уже принявших его в очередь.

Существующие heap-копии и очередь HTTPD сохранены. Результат не добавляет буферов,
повторов, ACK-протокола, истории или фоновых задач. Ошибка сетевой отправки после
`Queued` возникает позже: текущий транспорт просит закрыть соединение, вернуть её
задним числом из send невозможно. Даже успешно отправленные байты не доказывают,
что браузер выполнил команду.

## Шаблоны поведения приложения

**Телеметрия состояния.** Считать только принятые сообщения. Отклонённый snapshot
можно пропустить; следующий штатный период принесёт актуальное состояние. Не
накапливать старые snapshots и не логировать каждый отказ бесконечным потоком.

```cpp
const auto result = websocket.send_binary(snapshot, snapshot_size);
queued_snapshots += result.queued;
rejected_snapshots += result.rejected;
// Следующая попытка — в следующем периоде производителя.
```

**Ответ на команду.** Проверять одиночный результат внутри callback и учитывать
неотправленный ответ. Не пытаться сообщить об ошибке send ещё одним send в ту же
переполненную очередь. Минимальный вариант для локального устройства: счётчик отказов
на сервере, timeout ожидания ответа в клиенте и повторное чтение состояния по HTTP.
Операцию с побочным эффектом не повторять вслепую: она могла выполниться до отказа
ответа. Для повторяемых команд приложение может использовать request_id и собственное
ограниченное хранение результата; библиотека этого не навязывает.

```cpp
if (client->send_binary(reply, reply_size) != WebSocketSendResult::Queued)
    ++rejected_replies;
// client и входные данные за пределами callback не сохранять.
```

**Повторяющиеся отказы.** Уменьшить частоту/размер телеметрии и дать клиенту
переподключиться. Автоматическое закрытие при индивидуальном overflow, явный API
close и полноценный stop/drain остаются отдельной работой. `QueueFull` сейчас
возвращает отказ, но сам соединение не закрывает. Новая видимость отказов не означает
реализацию выбранной политики close-on-overflow. Не вызывать `server.end()` из callback.

## Динамическая доступность без изменения таблицы маршрутов

Предложение для приложения: заранее создать маршруты и переключать доступность
middleware-флагом. Пример — сервисный HTTP API, открываемый кнопкой на пять минут,
или запрет настройки во время движения. Не нужно пересоздавать сервер и его handlers.

```cpp
struct ServiceGate {
    std::atomic<bool> enabled{false};
    Result operator()(Context &context, Next &next) const {
        if (enabled.load(std::memory_order_relaxed)) return next();
        return responseResult(context.response.text(503, "Service disabled"));
    }
};
static ServiceGate service_gate;
// Для защищённых функций сохранить AuthMiddleware и AccessPolicy:
// static auto chain = makeChain(auth, service_gate, access);
// Приложение/таймер: service_gate.enabled.store(true/false, std::memory_order_relaxed);
```

Фрагмент требует `<atomic>` и `<NaWServer/pipeline.h>`. Чтение флага безопасно между
задачами; завершение уже допущенного запроса флаг не отменяет. Здесь флаг передаёт
только состояние доступности, а не публикует изменяемые данные. Выбрать 404 вместо
503 можно, если приложение хочет скрыть отключённую функцию. При текущем dispatcher
тело HTTP всё ещё читается до middleware; такой gate не ограничивает приём body.

Для WS можно отдельно прекратить публикации и обработку команд, но это не закрывает
действующих клиентов и не запрещает native handshake. HTTP gate не является
аутентификацией WS. Настоящие add/remove маршрутов во время работы требуют отдельного
контракта синхронизации, lifetime и регистрации IDF; текущий `addHandler` не изменён.

## Как проверять

Host-тест `transport` использует реальные static handlers и WS sender с подменённой
границей SDK. Проверяет MIME/default/gzip, binary с NUL, неверный MIME; копирование
payload; лимит четырёх заданий; отказы выделения задания/payload и очереди с возвратом
pending-счётчика; закрытую сессию; частичный broadcast и disconnect до выполнения
pending-заданий. Это проверка контрактов, не эмуляция scheduler/lwIP/HTTPD.

На C3 отдельно проверить:

1. Сборку `examples/minimal -e c3` и `examples/compile_check -e c3`.
2. В HTTP ответы CSS/JS/HTML/binary и gzip: MIME, encoding, точные байты после
   распаковки. `curl.exe -I` не использовать: HEAD пока не зарегистрирован.
   Подойдёт `curl.exe -D - --compressed http://DEVICE/response/static-gzip`.
3. WS echo text/binary, пустой binary, размер 4096/4097, обычный HTTP одновременно.
4. В управляемом fixture задержать выполнение HTTPD-заданий, заполнить четыре
   pending, получить `QueueFull` на пятом; затем дать заданиям завершиться и снова
   получить `Queued`. Не считать паузу чтения браузером детерминированным тестом
   очереди: сетевой буфер может принять все сообщения.
5. Два клиента: заполнить очередь одного, сделать broadcast, проверить частичный
   результат без повтора уже принятых сообщений. Disconnect с pending, reconnect,
   отсутствие старого payload у нового клиента. Учитывать результаты и heap;
   не печатать payload/секреты в serial.
6. Для предложенного ServiceGate: до/после переключения, параллельные запросы,
   истечение таймера; отключение не отменяет уже начатую команду. Сначала провести
   тест gate в приложении: в библиотеку новый специальный gate не добавлен.

Прошивка и аппаратный прогон этой правкой не выполняются. Сборка, host, flash,
boot и сетевой runtime — отдельные результаты.
