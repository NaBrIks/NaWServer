# Чистые сценарии наблюдения, 03.11.2026

Продолжение [аппаратного отчёта 02.11](readme_20261102_unified_tx_verification_ru.md).
Прошивка C3 не менялась: Showcase, IDF 5.5.6, `-O2`, общий TX,
immutable Flash assets, timeout-профиль 3000 мс. Измеритель —
`tools/load/transmission-scenarios.mjs`; длительность 30 с, rare API — 65 с.
Новых установок, записи firmware/FS или изменения разметки в этой серии нет.
Pico отдельно программно перезапущен без записи образа.

## ESP32-C3 без внешней страницы

Начальное/конечное число внешних WS равно нулю; фонового HTTP-опроса нет.
Граничные снимки и редкие дополнительные запросы мониторинга учитываются отдельно.
CPU — разность накопленных runtime задач, а не последний 100-мс образец.

| Сценарий | CPU | Проверка |
| --- | ---: | --- |
| Простой | 1,68% | PASS, TX failures +0 |
| Один health-запрос за 65 с | 1,60% | PASS, ответ 45 мс, TX failures +0 |
| Один WS, summary 10 Гц | 6,61% | PASS, 301 summary, max gap 331 мс |
| Один SSE | 2,27% | PASS, 31 событие |
| WS + SSE | 7,16% | PASS, 303 summary, 31 событие, max gap 139 мс |
| Два WS + SSE + HTTP summary 1 Гц + echo 2 Гц/клиент | 13,13% | PASS, 28 HTTP, 118/118 echo, max RTT 110 мс, max summary gap 174 мс |
| Четыре WS + SSE + две непрерывные загрузки JS, без echo | 60,46% | PASS, 126/126 ресурсов совпали по длине и SHA-256, max summary gap 151 мс, TX failures +0 |
| То же с echo 5 Гц/клиент | 40,32% за окно со срывом | FAIL, 71/75 HTTP, 260 echo без ответа, TX failures +7, закрытия WS/SSE |

Последняя строка содержит 445 отправленных echo и 185 ответов. Меньший CPU
при срыве не означает более эффективную работу: часть нагрузки уже перестала
обслуживаться. Boot identity в сценариях сохранялась.

Чистый WS: медиана мгновенного CPU 5,99%, p95 8,42%, максимум 38,69%.
Единичный всплеск остаётся; прежняя высокая регулярная пила не повторилась.
В предыдущем прогоне с внешним HTTP-наблюдателем интервалы роста HTTP counter
имели средний CPU 47,20%, остальные 8,59%. Это последовательные наблюдения с
разным набором потоков, а не равный A/B тест старой и новой библиотеки.

В простое доли задач: Wi-Fi около 0,58%, HTTP 0,48%, main 0,27%, lwIP 0,22%,
WS 0,06%, TX 0,05%. С одним WS main занимает 1,90%, Wi-Fi 1,59%, lwIP 1,51%,
HTTP 0,65%, WS 0,54%, TX 0,41%. Основной резерв обычной телеметрии — её частота,
кодирование и сбор полей, а не пустой SSE/TX цикл.

## Ограничение при входящих командах и восстановление

Чистый egress с четырьмя WS проходит, а добавление частых команд повторяет отказ
без пользовательских вкладок. Это отделяет ограничение от одного лишь скрытого
HTTP-опроса. Исходящие summary обслуживаются независимым TX; входящие прикладные
WS callbacks по текущему контракту последовательны с HTTP и ждут длинный
синхронный ответ. Каждый обход dispatch обрабатывает одну готовую команду на
соединение перед следующим HTTP. Под непрерывным bulk входная частота может
превышать частоту обслуживания. Полная причина всех сетевых обрывов ещё не доказана.

После duplex stress HTTP восстановился без перезагрузки; отдельный 30-секундный
idle дал 1,79% CPU и TX failures +0. Память при этом **не вернулась полностью
к прежней границе**: free internal 107324 Б вместо исходных 120900 Б.
Учтённые собственные dynamic buffers в обоих снимках равны 13272 Б,
TX allocated/queued равны нулю. Разница 13576 Б находится в `other_dynamic`.
Эта категория включает SDK и неучтённые собственные аллокации; её нельзя
автоматически назвать ни утечкой SDK, ни постоянным резервом. Требуется проверка
отложенного освобождения TCP и владельцев после закрытия.

После следующего успешного egress и дополнительного idle 65 с CPU составил
1,63%, свободная RAM выросла с 107112 до 107956 Б; исходные 120900 Б ещё не
восстановились. Учтённые собственные buffers остались 13272 Б, TX allocated/jobs
равны нулю, новых failures нет. То есть доступность и CPU восстановились, а
полный возврат памяти пока не подтверждён. Этот вопрос оставлен открытым.

Runtime minimum heap 3644 Б унаследован от предыдущих стрессов того же boot;
это не минимум конкретного чистого сценария. Egress проверен после recovery,
без перезагрузки C3. Короткие успешные проверки не являются soak-приёмкой.

## Pico: что помешало чистому замеру

После закрытия страницы сохранялся один WS и TCP-соединения сетевого процесса
ChatGPT. Программный переход в BOOTSEL и возврат в приложение убрал WS/SSE;
firmware, FS и разметка не записывались. Однако idle-измеритель обнаружил
43 HTTP-запроса за окно против трёх собственных граничных запросов. Он правильно
отверг прогон как загрязнённый. Полученные 5,97% CPU не являются чистым idle Pico.
Локальное наблюдение TCP также зафиксировало новые соединения от ChatGPT.
Встроенная вкладка отсутствует среди доступных этому чату browser surfaces.
Чистая матрица Pico пока не выполнена; повторная прошивка проблему фонового
HTTP-наблюдателя не решает.

## Допуск по IP: обсуждённое направление, ещё не изменение

Владелец предложил допускать ограниченное число IP, чтобы новые клиенты
получали отказ раньше, чем ресурсы закончатся у всех. Полезен полный профиль
квот на допущенного клиента, а не только счётчик адресов. Иллюстрация для
10 TCP slots: два IP, каждому 1 WS + 1 SSE + 2 HTTP, ещё два slots на общий запас.
Это пример для последующей проверки, не текущая настройка демо.

Имеющийся optional `Admission` уже ограничивает HTTP/WS/SSE по ключу. IP сейчас
служит только необязательной подсказкой приоритета ingress. Выбираемый источник
идентичности по peer IP можно развить отдельно; он не заменяет authentication.
Вкладки одного ПК делят квоту, NAT объединяет разных пользователей. Нагрузочные
клиенты из одного процесса/ПК не станут разными IP-клиентами сами по себе.
Квоты соединений не ограничивают частоту команд в уже открытом WS: это отдельная
политика, необходимая наряду с продолжением длинного HTTP вне callback.

## Термины учёта постоянной памяти

Предвыделенный при запуске heap-блок, удерживаемый до остановки, ведёт себя как
постоянный резерв. Он отдельно учитывается от linker `.data/.bss` и временных
payload-пиков. После успешного init размер предсказуем, но начальное выделение
может отказать. Называть весь такой heap-блок статической памятью ELF неверно.
