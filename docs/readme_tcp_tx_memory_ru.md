# Память TX-очереди TCP

Общая TX-очередь использует отдельные области для **метаданных** соединений и
заданий и для **payload** — передаваемых блоков. Политика размещения этих
областей независима. Метаданные резервируются один раз при создании transport;
при постановке сообщений таблицы не растут. Payload может резервироваться
сразу, выделяться по запросу или использовать предоставленную арену.

`TransmissionOptions`:

- `maximum_blocks` задаёт максимальное число заданий и payload-блоков;
- `metadata_allocator` задаёт аллокатор таблиц; пустой наследует
  `TcpOptions.buffer_memory.allocator`, а если и он не задан — платформенный
  TCP-аллокатор. Явный metadata allocator имеет приоритет;
- `metadata_max_bytes` — отдельный жёсткий предел на запрашиваемый размер
  таблиц с внутренним выравниванием; служебные байты самого аллокатора в него
  не входят. Это **отдельный бюджет**, не часть `buffer_memory.max_bytes`;
- `allocator`, `initial_blocks`, `static_payload` и `static_payload_bytes`
  управляют payload, не размерами таблиц.

Backend вычисляет число отслеживаемых handles консервативно: лимит соединений
плюс listener и один временно принятый handle, плюс ingress-слоты управляемого
режима и допустимые idle keep-alive соединения, если они включены. Это число
не равно просто числу клиентских страниц. Переполнение расчёта или нехватка
арены приводят к отказу запуска, не к неограниченному росту таблицы.

`tcp::transmissionMetadataBytes(handles, jobs)` возвращает необходимый размер
таблиц с учётом выравнивания конкретной платформы и ABI; 0 означает неверные
аргументы или переполнение. Для арены, принадлежащей приложению, выделение
должно обеспечивать `alignof(std::max_align_t)`, не пересекаться с payload и
памятью другого живого backend, а аллокатор и его контекст должны пережить
работающий backend и все незавершённые leases. При нехватке места следует
вернуть `nullptr`, не предоставлять частично пересекающийся блок. Статическая
арена для таблиц не делает автоматически статическими задачи, HTTP workspaces,
payload, lwIP или всю библиотеку.

`TransmissionStats.metadata_bytes`, `metadata_connection_capacity` и
`metadata_job_capacity` показывают фактические запрошенные байты и ёмкости.
Они не входят в `allocated_bytes`/`peak_bytes`: те относятся к payload.
При сравнении режимов необходимо отдельно учитывать всю зарезервированную
статическую арену, heap с накладными расходами аллокатора и потенциально
разные области физической памяти. Переезд массива в статическую память сам
по себе не уменьшает его общую стоимость.

## Исполнитель одной TX-очереди

`tcp::TransmissionOptions::execution` выбирается отдельно от лимитов и allocator:

```cpp
options.transmission.enabled = true;
options.transmission.execution =
    NaWServer::tcp::TransmissionExecution::Cooperative;
```

- `DedicatedWorker` — значение по умолчанию. Один TX worker самостоятельно
  обслуживает очередь; при пустой очереди ждёт уведомления. На ESP в проверенном
  профиле его стек занимает 4096 Б, отдельно выделяются TCB/worker/семафор lwIP.
- `Cooperative` — та же очередь, владение payload, приоритеты, порядок байтов,
  дедлайны и лимиты. Отдельного TX worker нет. Существующие вызовы `wait()` и
  `flushWrites()` продвигают один ограниченный шаг записи; атомарное владение
  исключает параллельное исполнение двух TX-шагов разными HTTP/SSE/WS задачами.
  Во время ожидания заполненной очереди native wait ограничен 1 мс; ожидание
  пустой очереди сохраняет заданный timeout.

Это настройка экземпляра, задаваемая до запуска, а не переключение живой очереди.
Существующие HTTP/WS/SSE задачи сохраняются. Mutex очереди тоже нужен: производителей
может быть несколько. Кооперативный режим не предоставляет ISR/timer API, не
делает пользовательские callbacks параллельными и не отменяет TCP-копирование.

Длительный callback приостанавливает обслуживание из своего потока. Новый commit
после входа другого потока в пустое socket wait может ждать его прежний timeout
(в проверяемом демо до 20 мс). Длительность native write входит в задержку вызывающей
задачи. Поэтому выбор исполнителя требует сравнения API/SSE/файлов и медленного
читателя, а не только свободной кучи. Stop ждёт уже исполняющийся шаг ограниченное
время и допускает повтор после timeout; выданные производителю Filling leases
должны быть возвращены до уничтожения их владельца в обоих режимах.
