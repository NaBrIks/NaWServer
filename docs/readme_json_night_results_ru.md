Работа завершена в ветке `codex/http-backend-adapters`: добавлен **RapidJSON SAX**
как ещё один выбираемый reader. Теперь доступны bounded, yyjson и RapidJSON;
начальный выбор остаётся bounded. SDK, инструменты и пакеты окружения не обновлялись.
Commit/push в этой фазе не выполнялись. Полные конфигурации, hashes и записи:
[матрица](readme_json_matrix_ru.md), [ночной журнал](readme_overnight_json_load_ru.md),

## JSON: измерено на физической C6

Один корпус:6 документов ×200 итераций =1200 разборов; ESP-IDF5.5.6,
GCC14.2,160 МГц, `-Og`, main stack8192, без Wi-Fi/LCD. Общий bounded writer
проверяется вне таймера. Peak относится к reader arena на этом корпусе,
не ко всей RAM/стеку и не к самому большому допустимому документу.

| Reader | BIN fixture, Б | Разница к bounded, Б Flash | Арена: резерв / наблюдаемый peak, Б | Время1200 разборов, мс |
|---|---:|---:|---:|---:|
| NaWServer bounded | 285408 | 0 | 2048 / 1016 | 334,462 |
| yyjson | 400528 | +115120 | 16384 / 4216 | 243,340 |
| RapidJSON SAX | 295296 | +9888 | 8192 / 2126 | 347,419 |

Если приложение уже реально вызывает yyjson, единый yyjson reader сэкономил
608 Б Flash против app yyjson + bounded, но потребовал на14336 Б больше арены.
Существующий RapidJSON DOM consumer дал другой результат: SAX+app321664 Б
против bounded+app311552 Б, то есть **+10112 Б Flash и +6144 Б арены**.
Разные template instantiations DOM/SAX не сливаются автоматически в один reader.
Общее использование названия библиотеки не гарантирует экономию кода.

Для текущего ресурсного профиля bounded остаётся наиболее экономным начальным
выбором. yyjson уменьшила время корпуса на27,2%, RapidJSON увеличил его на3,9%.
Это измерение конкретных исходников/опций, не общий рейтинг библиотек.

RapidJSON закреплён на upstream commit `24b5e7a8b27f42fa16b96fc70aade9106cf7102f`,
с сохранёнными лицензиями и отдельной raw-number поправкой: исходный reader
отвергал допустимый `0e10000` до вызова нашего checked converter. LwJSON/Frozen
не добавлялись ради количества: [обзор ограничений](readme_json_candidate_review_ru.md).

## Длительная нагрузка

Каждый этап ниже длился4 часа с4 логическими клиентами:2 WS +2 SSE,
максимум3 дополнительных HTTP sockets. Reload постоянно читает gzip JS/CSS;
cached заранее читает их один раз и выполняет summary на тех же HTTP-позициях.
MCP list/echo/invalid работают в обоих профилях. Cadence250 мс/клиент,
HTTP header deadline2 с, WS echo deadline3 с. Фоновые пользовательские вкладки
не закрывались. Для C6 registry7/sockets10 это отдельный фактор давления на
доступные соединения; результаты не равны приёмке четырёх изолированных браузеров.

| Плата / профиль | HTTP ответов | Точных завершённых WS echo | SSE events | Ошибки / timeout | Перезагрузки в этапе | Recovery health/info |
|---|---:|---:|---:|---:|---:|---|
| C6 TCP+bounded, reload | 135205 | 46776 | 28798 | 2045 / 2029 | 0 | 200 / 200 |
| C6 TCP+bounded, cached observation | 235407 | 78888 | 28798 | 2139 / 2134 | 0 | 200 / 200 |
| S3 TCP+bounded, cached observation | 247068 | 108910 | 28241 | 1354 / 1346 | 0 | 200 / 200 |

**Это завершённые прогоны с ошибками, не PASS по задержкам.** Cached gate S3
не прошёл из-за1 dial timeout/60 с, C6 из-за2; диагностические длительные
наблюдения не отменяют эти failures. В UART panic не обнаружено, boot IDs внутри
каждого этапа неизменны. Измеренные HTTP integrity counters равны0; это нельзя
расширять до доказательства отсутствия потерь во всех WS-попытках.

Ограничение текущего harness: `ws_echo_sent` и `ws_echo_received` увеличиваются
вместе после успешного точного echo, поэтому таблица показывает **завершённые
обмены**. Неудачные попытки остаются в errors/timeouts. HTTP integrity counters
и WS decoder/echo errors считаются отдельно; bounded reason map объединяет часть
причин в `other_capped`. Равенство двух WS-счётчиков не доказывает доставку всех попыток.

Source review выявил общий синхронный HTTP/WS owner: длинная отправка HTTP
может задерживать обработку WS. Серверные5 с общего /1 с no-progress deadline
не равны клиентским2/3 с. Независимый SSE продолжает работать. Это подтверждённый
архитектурный риск очереди, но он не локализует каждый timeout и не исключает RF
и ограничения сокетов. Reentrant WS callbacks из HTTP write не добавлялись:
у приложений есть общие буферы. [Подробности и дальнейшие проверки](readme_tcp_load_findings_ru.md).

## RAM и состояние после тестов

Уточнение 27.10.2026 после проверки исходников IDF: `min_free_bytes` ниже —
**сумма исторических минимумов отдельных heap regions**, которые могли наступить
в разное время. Поэтому 96 Б не доказывают одновременный остаток 96 Б всей
internal RAM. Минимум текущих free в сохранённых снимках S3 — 6663 Б;
largest block в этом снимке — 1536 Б. Исходные числовые записи сохранены.

| Плата / этап | SDK: сумма минимумов internal regions, Б | После нагрузки internal free / largest block, Б |
|---|---:|---:|
| C6 reload | 118780 | Отдельный boot до следующей прошивки; см. raw snapshots |
| C6 cached | 108960 | 184928 / 151552 |
| S3 cached | **96** | 46639 / 27648 |

S3 под нагрузкой имела минимальный наблюдаемый largest block1536 Б, хотя в
PSRAM оставалось около5,46 МБ. Свободная PSRAM не заменяет внутреннюю RAM Wi-Fi/
TCP. После cleanup свободная память вернулась; устойчивое монотонное падение
по снимкам не установлено, но это не доказательство отсутствия всех утечек.
Небольшой пиковый internal reserve S3 остаётся существенным ограничением.

Финальные живые MAC/ELF совпали с обычными профилями30(C6)/29(S3), оба
**TCP + bounded + MCP**, вход4096 Б, арена2048 Б, ответ2048 Б:

- C6: MAC `DEVICE-MAC`, [192.0.2.1](http://192.0.2.1/),
  HTTP task stack minimum1936 Б.
- S3: MAC `DEVICE-MAC`, [192.0.2.2](http://192.0.2.2/),
  HTTP task stack minimum1412 Б.

Прикладные эксперименты выключены. Все наши runner/load/serial/sampler/queue
процессы завершены, оба exclusive lock освобождены. Пользовательские фоновые
соединения и работающие локальные демо/портал не останавливались.

S3 по прямому поручению владельца перезапускается, если20 секунд не получает IP;
GOT_IP отменяет таймер, неудачные повторные connect не продлевают окно.
После новых прошивок наблюдалось получение IP примерно за5,2 с. Отдельно
вынужденный20-секундный отказ сети не провоцировался, срабатывание restart-ветви
этого нового правила в сохранённых UART не зафиксировано. До изменения были
NO_AP_FOUND201 и прекращение retry после10 неудач. Гарантия устранения слабого RF
или всех проблем подключения по этим данным не заявляется.

Отдельные ограничения: Linux JSON runtime не проверялся, x86 MSVC Debug fixture
остановился на alignment warning C4324 при /WX; основной x64 corpus прошёл.
Окончательную нагрузочную приёмку с нулём timeout работа не подтверждает.
