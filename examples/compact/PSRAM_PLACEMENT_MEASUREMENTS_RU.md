# ESP32-S3: размещение данных во внутренней SRAM и PSRAM

Измерения выполнены на ESP32-S3 с 8 МиБ octal PSRAM, ESP-IDF 5.5.6, PSRAM 80 МГц. Это результаты конкретной компактной демонстрации HTTP/SSE/OTA в локальной Wi-Fi сети. Они не являются паспортной полосой PSRAM и не распространяются автоматически на WebSocket, другую плату или другой SDK.

## Что именно сравнивается

Основная серия v3: P0–P3 используют один PSRAM-on SDK-профиль CAPS_ALLOC и одинаковые Wi-Fi, lwIP, стеки, лимиты HTTP, генератор данных и диагностический sampler. Три HTTP job, пять зарегистрированных соединений, три ingress-слота, семь SDK sockets. Меняются только два явных allocator. Обычные malloc/new в CAPS_ALLOC остаются internal; наличие PSRAM само по себе не переводит их наружу. Во всех sampler-вариантах v3 до нагрузки выполняется одинаковая безопасная stop/restart проба. Контроль без sampler вынесен отдельно: у него нет sampler, native UART counters и stop-пробы, поэтому это не пятое независимое размещение.

| Профиль | TX metadata | TX payload | Global malloc/new |
| --- | --- | --- | --- |
| P0 | internal | internal | internal |
| P1 | strict PSRAM | internal | internal |
| P2 | internal | strict PSRAM | internal |
| P3 | strict PSRAM | strict PSRAM | internal |
| wide, отдельная серия | default allocator | default allocator | большие запросы предпочитают PSRAM, порог 1024 Б; internal reserve 32768 Б |

Для строгих PSRAM allocator используется MALLOC_CAP_SPIRAM | MALLOC_CAP_8BIT, без скрытого fallback во внутреннюю SRAM. Выравнивание всех ESP callback allocator — alignof(std::max_align_t). В wide фактический запрос default buffer allocator включает padding для выравнивания; поэтому полезные 1024 Б могут пересечь порог 1024 Б. Классифицируется реальный адрес, без предположения только по полезному размеру. В wide SDK может применять fallback: резерв 32 КиБ не является безусловной гарантией остатка SRAM для произвольных default-запросов. Wi-Fi/lwIP opt-in, external BSS/noinit/stacks, PSRAM instructions/rodata отключены во всех этих SDK-профилях. Actual sdkconfig caps/wide различаются только политикой malloc, порогом и резервом.

Сравниваются предварительно выделенные TX payload: 3×1024 = 3072 Б, 8×4096 = 32768 Б и 12×4096 = 49152 Б. Фактический резерв проверяется через tx_bytes до нагрузки, metadata — через tx_metadata_bytes. Нельзя складывать payload и allocator overhead и называть полученное полезными данными. Static arena 1024/2048 Б — отдельная startup-серия: она удерживает SRAM в BSS и сама по себе не переносит данные в PSRAM.

Между группами 3/32/48 КиБ меняются число и размер блоков, а также выведенный из них лимит pending blocks на одно соединение. Разность goodput между такими группами не является изолированным эффектом объёма или скорости PSRAM: одновременно меняются ёмкость очереди и глубина конвейера. Вывод о размещении дают P0–P3 внутри одинаковой группы. Единственный прогон на размещение не даёт точной оценки небольшой разницы в процентах на фоне Wi-Fi и планирования задач.

## Реальная передача и методика

Это серия v3 с клиентской методикой v2. Во время измеряемой передачи нет дополнительных HTTP-запросов статистики на каждый body. После завершения и await всех API/page/bulk lane, с двумя оставшимися SSE, считывается один итоговый снимок. Device generated/internal/PSRAM и completed/released/canceled — накопительные 64-битные счётчики, передаваемые десятичными строками без потери точности JSON. Проверяются отсутствие overflow, token0→N, точное равенство device generated и суммы host-валидированных bytes, released=completed=host bodies, canceled=0 и ожидаемая область памяти. Каждое тело сразу после проверки длины и SHA записано в отдельный JSONL; ошибка наблюдателя не уменьшает число уже валидированных тел.

Для освобождения закрывающихся владельцев одинаковый quiet 2000 мс добавлен до и после HTTP-нагрузочных lane. CPU считается по накопительным device counters за указанное окно, включающее эти тихие границы, а latency/goodput/SSE основного этапа — только по traffic window. CPU нельзя напрямую сравнивать с первоначальной v1-методикой; длительность counter window дана в таблице. SSE snapshot и token boundaries фиксируются до этого ожидания.

Здесь internal — внутренняя SRAM, PSRAM — внешняя оперативная память, metadata — служебные таблицы очереди, payload — передаваемые данные, bulk — крупная передача, sampler — периодический снимок памяти, wide — широкая политика размещения. Ingress — временная обработка заголовков нового HTTP-запроса, job — задание ответа, startup — запуск, goodput — скорость полезных данных. p99 означает, что 99% измеренных успешных ответов уложились в указанное время; p95 аналогично для 95%.

Обычная страница отправляется immutable — из готовых неизменяемых данных Flash — и не доказывает быстродействие TX payload в PSRAM. Поэтому временный opt-in endpoint генерирует pattern непосредственно в менеджерский Filling WriteLease. Менеджер затем commit-ит этот же блок общей TX-очереди. Большого статического исходного массива нет. Состояние источника ограничено; одновременно допускается один генератор, размер запроса не превышает 1 МиБ. Маршруты проходят обычную защиту X-Client-Key и отключены в обычной production-сборке.

D-cache настроен на 32 КиБ,8ways,line32 Б; I-cache16 КиБ. Передачи циклически перепользуют TX arena, поэтому это практическая работа socket/queue/cache, а не измерение сырой полосы шины PSRAM.

Клиент принимает по 256 КиБ, проверяет точную длину и SHA-256. В callback проверяется принадлежность адреса реального блока internal/PSRAM; счётчики показывают объём сгенерированных байтов именно в этой области. В завершённых строках получено 503 проверенных передач, 131858432 Б. canceled=false означает лишь завершение генерации: доставку доказывают только клиентские длина/hash. Touched capacity — сумма уникальных адресов TX lease за одну передачу, а не одновременно занятая память. Peak global used — выбранная capacity занятых копируемых блоков (включая Filling и конкурирующие ответы), а не число полезных байтов; sampler вызывается до commit текущего заполнения. Это нижняя оценка пика, а не непрерывно измеренный максимальный working set.

Dense 100 мс API/page серия — перегрузочный сценарий сверх обычного режима, а не обещание обслужить любое число запросов без отказа. Частоты не меняются между размещениями; ограниченный 429/503 делает service-quality FAIL, сохраняя возможность закончить исследование остальных профилей при отсутствии panic, повреждения данных и иных ошибок.

Одновременно работают два SSE-клиента с сохранённым периодом 2000 мс и независимые API/page запросы; частоты и длительность лежат в каждом сыром report. В bulk fixture io_slice/response_body равны 4096 Б, а pending blocks на одно соединение ограничены max(1, blocks−4), чтобы оставлять ёмкость двум SSE и обычным ответам. Поэтому резерв 32/48 КиБ нельзя выдавать за полностью используемый объём: ниже приведены фактически затронутые адреса и очередь. Если клиент дополнительно ограничен по скорости чтения, этот ряд проверяет backpressure и независимость сервисов; его goodput ограничен клиентом и не измеряет максимум PSRAM.

После нагрузки выполняется OTA одного и того же production BIN с работающими SSE и API, затем проверяются фактические version/slot и сохранность ключа/настроек. Загрузка образа — во второй app slot; FS, NVS и таблица разделов не прошиваются. Panic/cache-off exception/rollback считаются FAIL, а не успешным повтором. Явный HTTP503 до 202 сохраняется отдельно как отказ admission; допускается один контролируемый повтор после спокойного периода и повторной идентификации неизменившейся production. Предыдущий 503 не удаляется.

Internal/PSRAM free/min/largest измеряются раздельно. Runtime sampler опрашивает heap раз в секунду через serial, без дополнительного HTTP polling. Табличные min free/largest — минимумы наблюдавшихся выборок выбранной фазы, не непрерывный пик; SDK lifetime minimum хранится отдельно в JSON. В исходных baseline sampler отсутствует; отдельный nosampler-контроль показывает суммарную разность отключения sampler/native diagnostics и иной последовательности lifecycle; чистая стоимость одного sampler этим контролем не изолирована. CPU берётся из разности накопительных busy/sample счётчиков по обоим ядрам, а не усреднением экранного процента. p95/p99 — наблюдавшиеся квантили с указанным числом ответов; это короткие LAN-прогоны, не оценка редких событий большого production-периода. Host-компиляции и радиотесты Pico во время этих latency-прогонов не выполнялись.

## Память: до создания, после start и при обмене

Startup dynamic (динамическая память при запуске) — разность free до создания backend и после успешного start всей Demo. Static BSS/IRAM и общий internal heap capacity находятся отдельно в JSON; не следует смешивать статический резерв с потреблением динамической кучи. Из-за фонового LocalPortal отдельные снимки могут включать краткий сетевой клиент. Точные полезные размеры и allocator placement проверяются независимо от такого шума.

Особый случай wide: SDK сообщает internalTotal=374387 Б вместо CAPS 341620 Б, разность 32767 Б. Это не дополнительная физическая SRAM. В IDF 5.5.6 функция esp_psram_extram_reserve_dma_pool сначала выделяет внутренний reserve 32768 Б из существующей кучи и регистрирует его как отдельный heap; heap_caps_get_total_size суммирует зарегистрированные диапазоны, включая этот вложенный диапазон. Поэтому wide total нельзя напрямую использовать как физическую ёмкость и знаменатель процента. Free/largest опираются на свободные блоки: занятый reserve-блок исходной кучи не является её свободным блоком, а свободное место внутри reserve учитывается дочерней кучей. SDK lifetime minimum также суммирует минимумы отдельных heap, которые могли наблюдаться в разные моменты; табличные выборочные минимумы сняты по одновременным serial snapshot.

Размер повторного учёта не вычитается из free/largest: эти показатели такого дублирования не содержат. Формулу wide total−free и проценты от такого total нельзя трактовать как физически занятую SRAM. Сам largest — максимум свободных блоков по регионам, а не сумма их размеров.

### Сколько стоит включить PSRAM в SDK

Это отдельный контроль одинаковых application flags, включая diagnostic source: меняется PSRAM SDK configuration. Его короткая нагрузка подтверждает образ и данные; её CPU/latency не используются как эквивалент 60-секундной dense серии.

| Одинаковый P0 3×1024 / 3 HTTP / 5 conn | PSRAM off | PSRAM CAPS on | On−off |
| --- | --- | --- | --- |
| Static DRAM, Б | 37244 | 38564 | 1320 |
| IRAM, Б | 92928 | 98560 | 5632 |
| Internal heap capacity, Б | 348572 | 341620 | -6952 |
| Free internal до backend, Б | 277560 | 270808 | -6752 |
| Free internal после start, Б | 233180 | 226428 | -6752 |
| Dynamic server internal, Б | 44380 | 44380 | 0 |

В этой паре включение PSRAM изменяет static DRAM на 1320 Б, IRAM на 5632 Б, internal heap capacity на -6952 Б и свободную internal после start на -6752 Б. Это расход поддержки SDK, отдельно от выбранных TX allocator. В прежнем matched v2-контроле стоимость была 1320 Б DRAM + 5632 Б IRAM, ёмкость internal heap уменьшилась на 6952 Б. Поэтому включать PSRAM только ради малой таблицы либо суммарного TX-резерва около 4 КиБ в этих образах невыгодно по internal SRAM. Если PSRAM уже включена для других потребителей, P0–P3 показывают дополнительный выигрыш выбранных allocator без повторного списания стоимости SDK. Перенос 32/48 КиБ payload может перекрывать этот фиксированный расход, если приложению действительно нужен такой резерв. В actual sdkconfig off/on не менялись Wi-Fi buffers, FreeRTOS и размеры cache; полный diff сохранён локально.

Ниже P0 стоит рядом с P1/P2/P3 каждой группы. «Освободилось internal» — P0 dynamic startup минус startup выбранного размещения; процент имеет явный знаменатель P0 dynamic startup всей Demo в той же группе, а не всю физическую SRAM платы. Для strict P0–P3 static DRAM одинаков, его изменение равно 0 Б; фиксированная стоимость включения PSRAM показана выше и повторно в эту дельту не включается. Нулевые native counters не доказывают конкретный путь закрытия внутри ingress.

Полный отказ SDK socket allocation отдельно не форсировался; увеличение ingress не объявляется универсальным исправлением всех admission ограничений.

## Воспроизводимость

Финально на C3/S3 оставляется обычная оптимизированная production: 3 HTTP job / 5 registry connections, ingress2, lazy TX3×1024, metadata internal, payload internal, PSRAM SDK off, main stack6144. Sampler/startup/full-stop/bulk/native diagnostics выключены. Это отдельный deployment, а не экспериментальная PSRAM-политика. Обычный образ проверяется API/страницей/двумя SSE и повторной OTA того же BIN в другой app slot, с сохранением ключа и настроек.
