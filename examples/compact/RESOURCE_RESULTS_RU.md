# NaWServer compact: результаты проверки ресурсов

Диаграмма всей SRAM, проценты, оценка запаса под LVGL и внешние ориентиры:
[память и LVGL](MEMORY_LVGL_RU.md).
Отдельное измерение до/после запуска и сравнение с ESP-IDF HTTPD на тех же
платах: [память при запуске](STARTUP_MEMORY_RU.md).

Срез: 03.11.2026. Короткие прогоны, OTA и продолжительная нагрузка приведены
отдельно; неуспешные опыты сохранены вместе с успешными.

C3, S3 и RP прошли отдельные 600-секундные прогоны с двумя SSE, API и загрузкой
страницы. C3/S3 отдельно прошли перегрузку вместе с OTA; уменьшенный RP-профиль —
OTA с двумя SSE/API и отдельные overload/slow-reader проверки. Универсальный
минимум RAM и многочасовая устойчивость по этим данным не установлены.

## Что именно проверяется

- Обычная нагрузка: два постоянных SSE-наблюдателя, один последовательный
  API-клиент и повторные скачивания страницы. Пауза API — 1 с **после ответа**,
  страницы — 2 с после загрузки; это не строго заданные 1 и 0,5 запроса/с.
- Период SSE: C3 — 1000 мс, S3 и RP — 2000 мс. События и максимальный промежуток
  между ними проверяются у каждого наблюдателя отдельно, включая паузу до
  конца окна. Скачивание HTML в нагрузочном runner не выполняет JavaScript
  страницы; браузерная проверка интерфейса — отдельный тест.
- Во время обычной OTA остаются два SSE и API. Дополнительные загрузки страницы
  во время OTA входят только в явно выбранный overload-сценарий.
- После OTA проверяются HTTP 202, переход в другой слот, работоспособность
  прежнего API-ключа и сохранение имени, периода и LED. Невалидный образ,
  прерывание передачи и другие отрицательные проверки не заменяются одним
  успешным обновлением.
- локальный монитор стенда продолжает работать. Он опрашивает страницу каждые 30 с и может
  добавить соединение сверх четырёх основных. Связь конкретного отказа с его
  запросом требует корреляции; совпадение состава нагрузки не является доказательством.

ESP собран с ESP-IDF 5.5.6 и оптимизацией performance. Текущая общая очередь
передачи в демке не резервирует неиспользуемый «важный» блок; начальный слот
обхода SSE чередуется. Старое голодание второго SSE при TX2 относится к
предыдущему коду и не смешивается с исправленными вариантами ниже.

## Единицы и границы учёта

Все размеры в таблицах указаны в **байтах**. 1 КиБ = 1024 Б.

| Показатель | Смысл и ограничение |
|---|---|
| `total_heap` | Ёмкость выбранной кучи; не вся физическая RAM микроконтроллера |
| Минимум по выборкам | Наименьший сохранённый `free_heap`; короткий пик между SSE может быть пропущен |
| `min_free_heap` | Исторический минимум аллокатора с загрузки; может включать более ранние операции |
| `largest_free_block` | Наибольший доступный непрерывный блок, а не весь свободный объём |
| CPU | Доля занятого времени по встроенным idle-счётчикам; у S3 нормирована на два активных ядра, у C3 и RP на одно |
| p95/p99 | Оценки задержек по ограниченной выборке runner; максимум задержки приведён отдельно |

Средняя CPU обычной фазы не объединяется со средней CPU OTA. IRQ и ожидание
во время операций Flash могут учитываться как занятость выполнявшейся задачи;
это не отдельное измерение вычислительной работы HTTP.

В ESP-таблицах CPU и min heap обычной фазы относятся к окну **до OTA**.
Выборочный минимум OTA показан отдельно. Короткие `largest`-минимумы относятся
к обеим фазам; для остальных сценариев область учёта подписана явно.

## Статическая, предвыделенная и динамическая память

`NAWSERVER_DEMO_TX_MEMORY_MODE` меняет только хранение исходящих данных TX.
Стандартные четыре блока по 1024 Б дают предел 4096 Б:

| Режим | Статическая RAM программы | Heap при запуске TX | Heap по требованию |
|---|---:|---:|---|
| `0`, lazy — по требованию | 0 | 0 | Фактический размер временных блоков, освобождение после завершения/отмены |
| `1`, предвыделенная heap | 0 | 4096 | Фиксированные блоки сохраняются на время жизни TX runtime |
| `2`, статическая BSS | 4096 | 0 | Данные размещены в массиве программы; этот RAM-расход остаётся без клиентов |

Это **не полная цена сервера**. Таблицы соединений и заданий, HTTP-буферы,
стеки задач, синхронизация, накладные расходы аллокаторов и Wi-Fi/lwIP учитываются
отдельно. Три режима не означают переключение всей библиотеки между static и heap.

`tx_reserved_bytes` уже входит в `tx_bytes`; складывать их нельзя.
`tx_limit_bytes` — потолок, а не дополнительно выделенная память.
`tx_peak_bytes` — максимум за жизнь TX runtime, не обязательно за конкретное окно.
Аналогично, предел TCP-буферов 24 КиБ не равен стартовому резерву 24 КиБ.
Прямой путь SSE использует общую TX-память, без второго независимого пула payload.

### Измеренное сравнение C3: baseline SDK, TX4

Каждая строка — отдельные 30 с обычной нагрузки и последующая OTA.

|---|---:|---:|---:|---:|---|
| По требованию | 147956 / 277416 | 143736 | 114688 | 4,45% | PASS + OTA |
| Предвыделенная heap | 145688 / 277416 | 138064 | 114688 | 4,29% | PASS + OTA |
| Статическая BSS | 146380 / 273320 | 137892 | 114688 | 4,46% | PASS + OTA |

В BSS-варианте сама heap-ёмкость меньше на 4096 Б: блок не исчез, а перешёл

одного механизма. Один прогон на вариант и различия радио не позволяют считать
небольшие различия CPU следствием способа выделения памяти.

## ESP: короткие проверки исправленного tight-профиля

Tight SDK: Wi-Fi static RX 4, dynamic RX 8, dynamic TX 8, RX BA 4;
lwIP sockets 7, TCP/IP mailbox 12, TCP send/receive окна по 2880 Б.
TX2/TX3 означает два/три блока по 1024 Б; в этой серии используется lazy TX.
`jobs` — число HTTP work slots, `TCP` — предел managed connections, включая SSE.
Предел соединений и число HTTP-заданий не взаимозаменяемы: закрывающиеся запросы

Сборка выбранного ESP-профиля из корня репозитория:

```powershell
.\examples\compact\esp\Build.ps1 -Target esp32c3 -NAWSERVER_DEMO_MEMORY_PROFILE tight -NAWSERVER_DEMO_MAIN_STACK 6144 -NAWSERVER_DEMO_TX_MEMORY_MODE 0 -NAWSERVER_DEMO_TX_BLOCKS 3 -NAWSERVER_DEMO_TX_BLOCK_BYTES 1024 -NAWSERVER_DEMO_HTTP_JOBS 3 -NAWSERVER_DEMO_CONNECTIONS 5
```

Для S3 используется `-Target esp32s3` и проверенная разметка именно этой платы.
Команда собирает образ; установка — отдельная операция. Обычные defaults
консервативнее. При другом сценарии учитывать listener, ingress, закрывающиеся
и фоновые соединения: семь SDK sockets не обещают семь прикладных клиентов.
Пять managed slots, два ingress и listener не могут одновременно целиком
поместиться в семь SDK sockets; системный предел ограничивает их суммарное
заполнение раньше. Ожидаемая защита при таком насыщении проверяется отдельно
от нормальной работы четырёх-пяти активных соединений.

### Стек и отдельная перегрузка без OTA

Tight / main6144 / TX3 / jobs3 / TCP5 прошёл диагностические 30 с и OTA.
Низшие наблюдённые остатки стеков в байтах: main 1816, HTTP 1844, TX 3472,
SSE 2156. Диагностический printf сам расходует ресурсы; это граница проверенного
пути, а не доказательство минимально безопасного стека. Проверены отказ для
настройки периода 200 и oversized-заголовок с ответом 431.

Отдельная перегрузка без OTA: 60 с, 238 успешных API, 106 страниц в нагрузке
и ещё одна в recovery, 46 намеренно
оборванных POST, по 60 SSE-событий в нагрузочной фазе; с завершающим recovery —
по 64. Ошибок и отказов обычных запросов нет, recovery PASS. CPU 12,01%, min heap
157932 / 277608 Б, min largest 114688 Б. Этот тест не является испытанием OTA
при перегрузке.

S3 tight / main6144 / TX3 / jobs3 прошёл аналогичные диагностические 30 с и OTA:
прежняя настройка вернула 200, oversized-заголовок — 431. Min остатки стеков:
main 2048, HTTP 1840, TX 2836, SSE 1472 Б. Они относятся к сборке с printf.

Отдельный S3 overload без OTA: 60 с, 236 API, 104 страницы в нагрузке + одна
в recovery, 46 прерванных POST. По 30 SSE-событий в нагрузке, по 32 с recovery;
max gap 2024 мс. Ошибок и отказов обычных запросов нет, recovery PASS, CPU
8,56% двух ядер, sampled min heap 226624 / 349356 Б, largest min 180224 Б,
дельта failed jobs 0.

- 568 API, 274 страницы, по 299 SSE-событий; ошибок и отказов обычных запросов 0.
  Максимальный gap 2052 мс при периоде 2000 мс.
- CPU 2,95% общей мощности двух ядер; sampled min heap 224120 / 349356 Б,
  historical min к концу 213660 Б, largest min 180224 Б.
- API p95/p99 — 71/87 мс, максимум 120 мс; HTML — 216/238 мс, максимум 251 мс.
- Дельта failed jobs 0, rejected jobs 2855. OTA проводилась отдельно.

600 с подтверждают этот конкретный десятиминутный сценарий, но не многочасовую
устойчивость и не произвольные условия Wi-Fi.

## RP: предварительные сравнения и проверенный уменьшенный кандидат

RP2350 Pico 2 W, Pico SDK 2.3.1, upstream FreeRTOS, сборка Release. При OTA
сохранены фиксированные LittleFS/NVS; Wi-Fi и фоновые проверки портала общие.
Строки ниже — исследовательские 60-секундные прогоны с двумя SSE, API и
страницами, затем отдельной OTA с двумя SSE и API.

| RTOS arena / режим TX | Min RTOS по выборкам, Б | Min newlib по выборкам, Б | CPU обычной фазы | Резерв TX, Б | Lifetime peak TX, Б | Передача OTA, с | Failed jobs обычной фазы |
|---|---:|---:|---:|---:|---:|---:|---:|
| 160 КиБ / по требованию | 123792 | 217792 | 4,51% | 0 | 1511 | 9,96 | 0 |
| 96 КиБ / по требованию | 58376 | 314992 | 4,56% | 0 | 1344 | 9,91 | 0 |
| 96 КиБ / предвыделенная heap | 58256 | 308936 | 4,47% | 4096 | 4096 | 10,30 | 0 |
| 96 КиБ / статическая BSS | 58376 | 308968 | 4,55% | 4096 | 4096 | 11,03 | 0 |

RTOS-профили 160/96 КиБ также различаются пулами lwIP. Уменьшение RTOS arena
увеличивает отдельную newlib arena. Поэтому общую разницу этих строк нельзя
приписывать только способу выделения TX. Более ранний код использовал один
защищённый блок и предшествовал коррекции справедливости SSE; сравнение с итоговым
профилем не является точным A/B при одинаковом коде.

В более новых 30-секундных прогонах без приоритетного резерва профиль
96 КиБ / TX3 прошёл с максимальными SSE gap около 2,01 с. TX2 формально прошёл
мягкий предел 10 с, но оба наблюдателя имели gap около 4,00 с при заданном
периоде 2 с. Эти варианты нельзя считать одинаковым качеством обслуживания.

### Точная конфигурация кандидата

| Ресурс | Значение |
|---|---:|
| FreeRTOS arena | 65536 Б |
| lwIP arena | 16384 Б |
| pbuf / TCP segments | 16 / 24 |
| TCP PCBs / netconns | 10 / 10 |
| HTTP jobs / accepted connections | 2 / 4 |
| TX | 3 блока по 1024 Б, lazy, предел 3072 Б |

Значения сверены с конфигурацией сборки. Здесь слово FreeRTOS равно 4 Б.
Вариант jobs3 / connections5 собран, но на Pico не прошивался и не проверялся
нагрузкой; его дополнительная ёмкость не заявляется.

### Idle, обычная нагрузка, stress и slow-reader

Минимумы этой таблицы относятся к указанному сценарию; OTA в эти окна не входит.

| Сценарий | Длительность | CPU | Min RTOS по выборкам, Б | Min newlib по выборкам, Б | Результат |
|---|---:|---:|---:|---:|---|
| Без SSE; API в начале, через 60 и 120 с | 120,099 с | 2,25% | 33400 | 348968 | 3/3 API; HTTP delta 8 включает metrics и фон портала |
| Два SSE + API + страницы | 600 с | 4,56% | 32776 | 346864 | PASS: 300/300 событий, 571 API, 274 страницы |
| API с паузой 200 мс, HTML 500 мс, оборванный POST каждые 5 с | 60 с | 10,01% | 32776 | 346864 | PASS: 235 API, 86 страниц + 1 recovery; ожидаемые отказы отдельно |
| Чтение второго SSE приостановлено; первый SSE + API 200 мс / HTML 500 мс | 60 с | 9,91% | 32568 | 346864 | PASS здоровых каналов: 29 событий в нагрузке, 239 API, 88 страниц |

Наблюдение без SSE не является полностью нетронутым idle: выполнялись три API,
два граничных измерения и фоновые запросы. На границах FreeRTOS было свободно
33400 / 65536 Б, newlib — 348968 / 374320 Б. Исторический минимум FreeRTOS
32360 Б накоплен с загрузки, а не только в idle-окне.

Статическая RAM обычной сборки — 149968 Б при физической SRAM 532480 Б.
Она **уже включает** FreeRTOS arena и статические пулы lwIP. Эти расходы нельзя
прибавлять к ней повторно. FreeRTOS heap и newlib/C++ heap — разные области;
уменьшение worker stacks освобождает место внутри RTOS heap, но само по себе
не уменьшает её статически зарезервированный массив.

В 600-секундном прогоне SSE maximum gap составил 2017/2031 мс при периоде
2000 мс. Ошибок и отказов API/страниц нет. API p95/p99 — 59/78 мс, максимум
105 мс; HTML — 208/228 мс, максимум 233 мс. Min largest FreeRTOS по выборкам
32656 Б, исторический минимум FreeRTOS к концу 32568 Б. Дельта failed jobs 0,
дельта retryable rejected jobs 2891. Lifetime peak TX — 1509 Б при пределе
3072 Б. Два SSE после теста закрыты отдельно; более поздний рост абсолютного
счётчика отмен не относится к этим 600 с.

В overload было 4 отказа API, 3 отказа HTML и 2 отказа среди 12 намеренно
прерванных POST. Успешные ответы и явные отказы избыточной нагрузки учитываются
раздельно. Во время нагрузки
оба SSE получили по 30 событий, max gap 2014 мс; с recovery — по 32.
Recovery API/HTML и сохранение двух потоков прошли. Дельта failed jobs за окно
равна 0; агрегат не даёт атрибуции отдельных внешних отмен.

В slow-reader читаемый поток получил 29 событий в нагрузочном окне, max gap
2012 мс; 30-е событие пришло при завершающем измерении. Отказов и ошибок API/HTML
нет. Наличие открытого приостановленного сокета не доказывает, что буферы TCP
заполнились: PASS относится к здоровым каналам, а не к доказанной работе при
исчерпанном TCP receive window.

### OTA и остатки стеков: отдельная диагностическая сборка

Диагностическая сборка добавляет 960 Б BSS: static RAM 150928 Б вместо 149968,
newlib capacity 373360 Б вместо 374320. Поэтому её free RAM нельзя напрямую
подставлять в строку обычной сборки.

Передано 1244672 Б за 9,932 с; HTTP 202, другой слот, прежние ключ и настройки
сохранены. Во время OTA — 10 API / 0 ошибок и по 5 SSE-событий. CPU 77,78%
включает повторные USB-диагностики и не является чистым сравнением production
профилей. Выборочные минимумы **в OTA-фазе runner**: FreeRTOS 32864 Б,
newlib 344872 Б. Это не гарантированные истинные пики. Исторический минимум
FreeRTOS до/после OTA оставался 32360 Б и не объявляется минимумом только OTA.

Для каждой из перечисленных задач в сохранённом USB-логе есть 42 измерения
через обычную нагрузку и большую часть OTA до перезапуска:

| Задача | Выделено, Б | Min свободных слов | Min свободно, Б |
|---|---:|---:|---:|
| HTTP | 8192 | 792 | 3168 |
| SSE | 4096 | 528 | 2112 |
| TX | 3072 | 552 | 2208 |
| lwIP | 2048 | 332 | 1328 |

Min watermark ограничивает только проверенные ветви. Само измерение и printf
увеличивают нагрузку, а перезапуск обнуляет историю задач; эти значения не
доказывают, что стек безопасно уменьшить на весь свободный остаток.

### Сохранённые ограничения и неуспешные опыты RP

Предыдущий 80 КиБ-профиль имел один API 503 во время OTA. Там runner мог добавить
metrics-соединение, пока API ещё не закрылось, то есть создать пятое соединение
поверх рассчитанных четырёх. Runner исправлен; этот опыт не используется как
чистое сравнение ёмкости с итоговым 64 КиБ-профилем.

Отдельный overload с OTA и дополнительной одновременной страницей вернул 503
для OTA. Это **отклонённое обновление**, а не успешная OTA-проверка.
Точное A/B static/preallocated/lazy при одинаковом итоговом коде и всех пулах
не выполнено; исследовательская таблица выше не заменяет его. Многочасовая
работа и работа при доказанном заполнении TCP остаются непроверенными.

## Как читать отказы и воспроизводить проверку

`tx_rejected_jobs` включает временный отказ получить TX-слот с последующей
повторной попыткой. Его рост не означает потерянный ответ или SSE-событие.
`tx_failed_jobs` считает также отмены и закрытия: в обычной нагрузке это отдельный
сигнал, а в overload/slow-reader часть роста может быть ожидаемой. Агрегат
`tx_failures` не атрибутирует ошибку конкретному соединению. Полноту доставки
подтверждают JSON/HTML, числа SSE, gap и recovery, а не один общий счётчик.

Пауза чтения второго сокета сама по себе не доказывает заполнение TCP-буферов:
данные могут оставаться в приёмных буферах ОС. Без корреляции с транспортом
такой результат не следует объявлять проверенной backpressure-нагрузкой.

Сценарий и параметры: [tests/RESOURCE_LOAD.md](tests/RESOURCE_LOAD.md).
Общие правила учёта: [MEASUREMENTS.md](MEASUREMENTS.md).
Начальная база этой сводки — предварительные ESP/RP-фрагменты и подтверждающие JSON
в игнорируемой `.local` папке; ключи, сырые логи и образы в документ не включаются.
Ключевые локальные отчёты для сверки: `c3-main6144-soak600.json`,
`s3-main6144-soak600.json`, `rp-64b3-smallstack-soak600.json`,
`c3-main6144-overload-ota.json`, `s3-main6144-overload-ota.json`,
`rp-smallstack-diag-ota-final.json`. Строгие нагрузочные счётчики SSE берутся
из `soak_streams`; `streams` после recovery/OTA может включать дополнительные
события. Числа API/HTML во время OTA берутся из отдельного объекта `ota`.
При обновлении итогового среза добавлять только подтверждённые результаты;
непроверенные области оставлять обозначенными явно. Фиксировать точные
профили/артефакты и сохранять неуспешные прогоны рядом с успешными.
