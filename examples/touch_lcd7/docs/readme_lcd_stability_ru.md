# RGB LCD: снежок, полосы и сдвиги

20.10.2026 владелец сообщил: изображение в целом нормальное, но периодически
появляются отдельные битовые/байтовые артефакты, изредка мигает весь экран,
возникают полоса или сдвиг. Это отдельный дефект S3 LCD-демки. Отчёт о
первоначально стабильном LVGL изображении не закрывает эту проблему.

## Известный механизм и ограниченная правка

[Espressif FAQ](https://docs.espressif.com/projects/esp-faq/en/latest/software-framework/peripherals/lcd.html#why-do-i-get-drift-overall-drift-of-the-display-when-esp32-s3-is-driving-an-rgb-lcd-screen)
связывает drift с недостатком полосы PSRAM/GDMA, высокой PCLK, конкуренцией
Wi-Fi/flash и длительной блокировкой прерываний. В
[документации именно IDF 5.4](https://docs.espressif.com/projects/esp-idf/en/v5.4/esp32s3/api-reference/peripherals/lcd/rgb_lcd.html#bounce-buffer-with-single-psram-frame-buffer)
описаны опоздание заполнения bounce-буфера, сдвиг и возможное мерцание при
восстановлении драйвера. Это подходящая гипотеза, не установленная измерением
причина конкретного экземпляра. Отдельные искры также могут быть следствием
питания, контактов/шлейфа и целостности сигналов.

Эффективный sdkconfig уже содержит Octal PSRAM 80 МГц, инструкции и rodata
в PSRAM, DCache 64 КБ с линией 64 B, FreeRTOS 1000 Гц. Опция
`SPIRAM_TRY_ALLOCATE_WIFI_LWIP` выключена. `SPIRAM_XIP_FROM_PSRAM` в установленном SDK — helper,
выбирающий уже включённые FETCH_INSTRUCTIONS и RODATA, отдельного отсутствующего
механизма за ним нет. Повторное включение этих настроек не является исправлением.

В `main/board.cpp` применён известный способ добавить запас:

- PCLK 16 → 12 МГц; остальные GPIO и полярности/porch сохранены.
- Bounce 10 → 16 строк. Два внутренних RGB565 буфера: 51200 B вместо 32000 B,
  то есть дополнительно 19200 B динамической SRAM. 480 кратно 16.
- При заданных таймингах развёртка примерно 39,0 → 29,3 Гц. Окно для одного
  заполнения примерно 0,51 → 1,09 мс. Это запас, не гарантия отсутствия underrun.

Синхронизация LVGL frame completion/VSYNC и два PSRAM framebuffer сохранены.
Правка только в приложении S3, без изменений NaWServer, C3 или общего frontend.
На первом этапе постоянный restart на каждом VSYNC не включался: он может
давать собственное мерцание и не устраняет нехватку полосы. Дополнение ниже
фиксирует следующий этап после подтверждения сохраняющегося артефакта.

## Проверка и статус

`pio run -e s3 -j 4`: SUCCESS. Static RAM 72688 B, flash sections 1347948 B.
Дополнительные bounce-буферы выделяются во время исполнения, поэтому не видны
в показателе static RAM сборки.

Записано на повторно идентифицированную ESP32-S3 DEVICE-MAC / COM12.
Свежая таблица разделов совпала с built partitions.bin. Только app,
`[0x10000,0x159300)`, 1348352 B; esptool подтвердил hash. SHA-256:
`2736fcc1c85d1115d8e4b909120c9d4bd9372207cdeb560a8e71afadb5615ecc`.
Bootloader/таблица/NVS не записывались. Установленная esptool 4.5.1 не смогла
работать с native USB этой платы; использована отдельная ignored venv с
esptool 5.1.0 без изменения build environment. После первого boot Wi-Fi
исчерпал reconnect на временном отказе AP; повторный reset восстановил сеть.
Исходный HTTP endpoint до правки также не отвечал; это не измерение эффекта LCD.

Аппаратные проверки после reset:

- 20 HTTP/CBOR/WS/SSE проверок PASS, включая LCD ready и native bytes echo.
- 40,86 с наблюдения через API: 21 snapshot, 1196 frame events и 1196 VSYNC,
  фактическая частота 29,27 Гц; uptime без регресса, новых touch errors нет.
- Параллельно четыре загрузки основного JS asset и смена bars/grid/red через
  очередь команд; исходный pattern=0 восстановлен и подтверждён GET /api/status.
- Минимум свободной внутренней SRAM в выборке 66823 B; LCD ready=true,
  два framebuffer, PSRAM доступна. Это короткий smoke, не нагрузочная приёмка.

Сырые логи, deploy-state и runtime samples: ignored `local/lcd-stability-*`.
Визуальный результат пока не подтверждён владельцем; дефект остаётся открытым.

## Сохраняющаяся полоса справа и IP на LCD

После обновления владелец сообщил: после перезагрузки справа полосы не было,
потом она появилась скачком. Такая полоса не предусмотрена рисунком: в bars
красная полоса слева, чёрная справа, и только в области тестового шаблона.
Постоянная неожиданная полоса соответствует гипотезе оставшегося сдвига RGB;
её точная причина пока не измерена.
Повторное уточнение владельца: после перезагрузки полосы нет, она появляется
позже в некоторый момент. Чистый экран сразу после reset не подтверждает
исправление; для визуальной проверки нужно дождаться потенциального повторения.

Уточнение характера артефакта: в некоторый момент весь растр смещается влево,
включая текст, который становится ближе к левому краю. Правая «красная полоса»
наблюдается вместе с этим смещением. Владелец оценил шаг как «байт или два»;
это визуальная оценка, величина сдвига пока не измерена. В RGB565 один пиксель
занимает два байта, поэтому пиксельный сдвиг нельзя автоматически считать
сдвигом ровно на один байт.

Приоритетная гипотеза — рассинхронизация считывания DMA и развёртки LCD,
описанная в документации IDF как shifted image после задержки доставки данных.
Появление справа начала строки при таком сдвиге правдоподобно, но перенос
пикселей через границу строки пока отдельно не подтверждён. Гипотеза не
устанавливает причину: необходимо отличить изменение содержимого framebuffer
от смещения при выводе. Следующая диагностика должна сравнить содержимое/CRC
неизменяемого статичного framebuffer до и после события и изображение LCD;
после этого проверять underrun, ISR, тайминги и vendor demo. Простая проверка
цветов или чистого экрана сразу после reset этого различия не показывает.

В экспериментальной S3 сборке включали `CONFIG_LCD_RGB_RESTART_IN_VSYNC=y`
в defaults и эффективном sdkconfig. Это штатная [защита IDF от постоянного сдвига](https://docs.espressif.com/projects/esp-idf/en/v5.4/esp32s3/api-reference/peripherals/lcd/rgb_lcd.html#bounce-buffer-only):
на границе каждого кадра перезапускаются GDMA и FIFO LCD. Это восстановление
синхронизации, а не устранение исходной нехватки полосы; редкие вспышки
или пиксельный шум всё ещё возможны. PCLK 12 МГц и bounce 16 строк сохранены.

Владелец после прошивки подтвердил: «IP виден, полоса остаётся или вернулась».
Следовательно, этот эксперимент не решил наблюдаемый дефект. Постоянный
restart убран из итоговой конфигурации, чтобы не оставлять не помогший режим.
Полоса остаётся открытой проблемой; считать её причиной именно underrun
по имеющимся данным нельзя. На этой демке дальнейшая диагностика отложена
согласно ограничению объёма работ владельцем.

По запросу владельца в верхней строке справа добавлен IPv4 адрес интерфейса
WIFI_STA_DEF: `IP: 192.0.2.2` либо `IP: offline`. Адрес не зашит в прошивку:
worker раз в секунду проверяет реальный активный netif и получает его IPv4.
LVGL label меняется только при изменении адреса, в том же LCD worker;
Wi-Fi callbacks не рисуют и не касаются framebuffer. Размер/позиция подписи
постоянны, новая строка не добавлена. Изменения адреса также пишутся в UART.

Вывод IP визуально подтверждён владельцем. UART также зарегистрировал
`lcd7_graphics: LCD IP: 192.0.2.2`; IP получен через DHCP и выведен
в течение секунды после события. Экспериментальная сборка прошла 20 проверок
HTTP/CBOR/WS/SSE и 40-секундный runtime smoke: 27 снимков, 29,26 Гц,
минимум SRAM 57371 B, шесть загрузок JS asset, смена шаблонов и восстановление
исходного pattern. Первый WS-запрос после boot закрылся 1006; повтор прошёл.
Эти проверки не отменяют отрицательный визуальный результат по полосе.

Итоговая сборка сохраняет только IP и прежние 12 МГц / 16 строк. Сборка PASS:
static RAM 72704 B, flash sections 1348356 B. На той же повторно проверенной S3
записан только app `[0x10000,0x159490)`, 1348752 B. Свежая таблица совпала
с built, esptool hash verification PASS. SHA-256 итогового образа:
`9a0e23641305355946b4e5bf2b958e739f433b17d4a3c7f41aef18167b568e35`.
Эффективный `LCD_RGB_RESTART_IN_VSYNC` выключен. После финальной записи
20 HTTP/CBOR/WS/SSE проверок PASS, LCD ready=true; UART снова подтвердил
`LCD IP: 192.0.2.2`. Открытый визуальный дефект этим не закрыт.

## Что остаётся проверить

Физические артефакты нельзя оценить по `frame_events`, `vsyncs`, HTTP 200
или скриншоту веб-интерфейса. Нужны наблюдение самого LCD: статичный кадр,
движение пальца, смена шаблонов и несколько загрузок вебки параллельно.
Сравнивать частоту и тяжесть артефактов с прежней конфигурацией.

Если правка не помогает, задача остаётся открытой, но не расширяется сейчас
в отдельный графический проект. Следующая короткая диагностика: питание/кабель,
разъёмы и шлейф; сравнение офлайн и Wi-Fi/HTTP; привязка RGB ISR/worker к ядру;
измерение задержек ISR и underrun, затем проверка vendor demo той же ревизии.
Дальнейшие настройки ISR/IRAM, оптимизации и SDK подбирать по результатам,
не включать весь набор одновременно. Для продуктового применения потребуется
отдельная визуальная проверка под нагрузкой.
