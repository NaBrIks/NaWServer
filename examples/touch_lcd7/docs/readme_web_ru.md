# Полная веб-оболочка S3

19.10.2026 по запросу владельца в отдельный S3 пример перенесена полная копия
Vue/TypeScript интерфейса C3 showcase. Это копия исходников и ресурсов,
а не подключение sibling frontend при сборке. Библиотека NaWServer общая;
приложения, состояния, GPIO, credentials и firmware независимы.

Сохранены Cream/Dark/Emerald/Light, Nano/Mini/Norm, RU/EN, фиксированная шапка,
левое меню, правая изменяемая панель задач, графики с фиксированными шкалами,
поиск/сортировка/подробности задач, лаборатория HTTP/WS, эксперименты CPU,
RGB, доступ и SSE. Настройки S3 хранятся в отдельном ключе localStorage.
Полный обязательный стандарт: [ui-principles.md](ui-principles.md).

Новая страница «Плата и дисплей» объединяет LCD/LVGL, PSRAM, frame/VSYNC counters,
состояние и карту GT911, смену изображения, подсветку и схему подключения RGB.
Карта — координаты физического тача, не видеопоток LCD.
Исправлен унаследованный перехват кликов всплывшей подсказкой: tooltip остаётся
видимым, но не перехватывает pointer events соседних элементов меню.

## Контракт и аппаратная адаптация

- `/api/v2/info`, `/api/v2/summary`, `/api/v2/tasks` — CBORv2 со строковыми ключами.
- `/ws` — binary CBOR summary и echo; прежний text-only WS echo заменён.
- Summary содержит две core_busy_pct, internal RAM и PSRAM, плюс map `display`.
- Display поля сохраняют названия из `/api/status`; UTF-8 имена передаются
  непосредственно в CBOR map, без таблицы числовых ID.
- WS summary —1Гц в покое, до10Гц при касании, CPU эксперименте или RGB анимации.
- `/api/v2/events` и `/api/v2/events/private` — библиотечный SSE, JSON diagnostic1Гц.
- `/api/status` JSON и `/api/display` POST сохранены для LCD совместимости.
- Доступ: открытая учебная пара demo/showcase-only, permissions1;
  protected HTTP/SSE проверяются до вызова endpoint. Admin требует2 и даёт403.
  Authenticated WS по-прежнему не поддерживается библиотекой.
- π/pulse задачи подготовлены для обоих ядер; не запускаются автоматически.
  CPU определяется по idle runtime каждого ядра, task shares нормированы на
  суммарную ёмкость двух ядер. Snapshot ограничен32 задачами, страницей8.
- WS2812 перенесён на Sensor AD GPIO6, RMT/SPI;10 GRB, старт выключен.
  Обычный GPIO LED не назначен. [Документация и проводка](board/README.md).

LVGL worker и двойная кадровая синхронизация не менялись. Веб-обработчики
передают LCD команды через прежнюю ограниченную очередь.

## Сборка

Из examples/touch_lcd7:

```powershell
npm.cmd ci --prefix ../.. --no-audit --no-fund
npm.cmd run build --prefix frontend
go run tools/pack-assets/main.go
$env:PLATFORMIO_CORE_DIR='<repo>/local/pio-core'
pio run -e s3 -j 8
```

Go tool детерминированно сжимает собственные frontend/dist ресурсы в
main/assets.hpp и пишет device-manifest.json с SHA-256 исходных assets.
SimulatorPanel chunks не входят в device assets. Все шрифты/иконки/лицензия локальны.
После изменения UI сначала пересобрать assets, затем firmware.
Для sdkconfig, созданного до этой версии, включить trace facility, runtime stats,
ESP timer runtime counter и vTaskList core IDs согласно sdkconfig.defaults;
локальная sdkconfig.s3 уже настроена. Build не означает runtime приёмку.

## Три вкладки и IDLE (19.10.2026)

Исходная конфигурация HTTPD использовала SDK default 7 TCP-сессий при
lwIP MAX_SOCKETS=10. Каждая вкладка открывает WS, SSE и HTTP polling;
три вкладки занимают шесть постоянных сессий, оставляя одну для HTTP.
После чистого старта воспроизведены неподключающиеся WS и HTTP timeouts.

В библиотеке добавлен ServerOptions::max_connections (default7), передаваемый
конструкторам сервера после ResponseOptions. S3 явно выбирает21; её
sdkconfig.defaults и локальная sdkconfig.s3 задают LWIP_MAX_SOCKETS=24.
Это отдельный бюджет всех TCP-сессий, не лимит только WS клиентов.

После увеличения бюджета три вкладки одновременно получали HTTP/WS/SSE и
собственные echo. Reload выявил вторую проблему: при временном заполнении
четырёх SSE слотов запрос получал503, после которого native EventSource
больше не подключался. S3 frontend теперь закрывает неудачный EventSource и
явно повторяет подключение с задержкой1..10с. Отключение SSE/уход со страницы
отменяет таймер. Лимит SSE и обработка WS не увеличивались.

IDLE0 и IDLE1 закреплены первыми в порядке номера ядра независимо от CPU,
стека, имени и поиска. Остальные задачи сортируются и фильтруются как раньше.

Аппаратный сценарий: `node frontend/tests/multitab-smoke.mjs`.
Три вкладки одного браузерного контекста, три сортировки и поиск,
адресное echo, три перезагрузки средней вкладки, восстановление после
однократно принудительного503 (перехват только в тесте), продолжение
телеметрии соседей, отсутствие перезапуска устройства и ошибок GT911.
Локальный отчёт: local/multitab/report.json.


## Резерв и управляемый отказ

[Общее руководство по настройке и наблюдению](../../../docs/readme_connection_limits_ru.md).
[Принятое решение и ограничения гарантии](../../../docs/adr/ADR_20261019_nawserver_connection-admission-and-reserve.md).

NetworkPolicy в main/network.hpp: HTTPD21, резерв3, WS4, SSE4, Retry-After2000мс.
SDK pool24. На странице платы добавлены текущие TCP/WS/SSE, пределы и отказы.
HTTP admission отклоняет запросы на пороге18, освобождая соединение отказа.
Core ResponseOptions поддерживает типизированный ConnectionPolicy::Close; сырой
Connection header остаётся запрещённым. S3 дополнительно запрашивает закрытие
нативной сессии после отправки ответа, чтобы резерв не стал keep-alive.
GET /api/v2/network доступен в резерве; /api/v2/admission?kind=ws|sse — preflight.
Пятый WS при обходе preflight получает Close1013 с причиной; SSE —503.

Проверка отказов: node frontend/tests/admission-smoke.mjs. Скрипт измеряет baseline,
учитывает страницу владельца, открывает только собственные тестовые потоки и
обычные HTTP до первого503, затем освобождает только их. Не закрывает вкладки
владельца и не заполняет весь пул молчащими TCP.

TCP PCB: CONFIG_LWIP_MAX_ACTIVE_TCP=32, отдельно от socket pool24.
Значение16 приводило к TCP timeout при HTTPD16 / 21, раньше admission18;
эта независимая граница также включена в политику сборки и runtime-таблицу.
